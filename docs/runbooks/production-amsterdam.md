# Рабочая площадка в Амстердаме

Перенос #1575 от 20 октября 2026 года выполнен по прямому назначению владельца.
[ADR 0036](../adr/0036-amsterdam-production-placement.md) фиксирует решение о размещении.
Это один рабочий экземпляр, без GeoDNS, второго пишущего кластера и автоматического failover.
Соответствие требованиям к персональным данным остаётся открытым вопросом, изложенным в
[исследовании](../research/issue-1575-ams-personal-data-placement.md) и отдельной задаче
[#1599](https://github.com/sachkov-inside/platform/issues/1599). Перенос не обновляет
принятые политики и не подтверждает наличие необходимых уведомлений.

## Текущая схема

```text
sachkov.dev / www / inside / auth / telegram → Timeweb AMS 147.45.166.174
  Caddy → Platform + Logto + Telegram
  PostgreSQL 18 + RabbitMQ, единственные рабочие данные и обработчики

Caddy принимает публичный HTTPS напрямую на 443, без HAProxy и PROXY protocol.
```

Новый сервер в панели называется Wise Finch, Ubuntu 26.04.1, 2 CPU, 4 ГБ RAM, 50 ГБ диска.
Прямой SSH: `ssh root@147.45.166.174`, по проверенному существующему ключу.
На Mac `inside-production` теперь указывает на AMS; `inside-production-ru` сохранён только для аудита отключённого старого сервера.
Пять A-записей сохранены с новым IP, TTL 600. После проверки распространения DNS и
пользовательских подключений временные старые входы отключены 20 октября 2026 года.
MX/TXT/CNAME и NS не меняются. После переходной задержки все четыре NS подтвердили новую
зону: 104 проверки A/MX/TXT/CNAME по IPv4 и IPv6 прошли. Подписки и Xray на Aeza сохранены.

Публичные и внутренние URL приложения прежние. S3, Kinescope, почта, платёжный провайдер и хранилище
резервных копий не переносились и не заменялись. Внешние файлы не копировались на локальный диск.
Регион приложения не определяет страну хранения всех его зависимостей.

## Единственный писатель и сохранение данных

На время операции обе штатные deployment-блокировки удерживались на обоих хостах.
До копирования остановлены Platform, Logto, Telegram, PostgreSQL и RabbitMQ на RU.
Холодная копия сохранила целиком PG volume и RabbitMQ volume вместе с cookie и nodename
`rabbit@rabbitmq`. После восстановления и до запуска приложений совпали количество записей
и хэши **всех 292 таблиц** трёх баз. Миграции приложения не запускались повторно.

Во время подготовки вышли новые релизы. Перенесены именно актуальные Platform **v45** и Telegram
**v21**, source `2f5300026c5a3e946f30596262a02747c6f48827`, с исходными manifest и image digests.
Первоначальная репетиция v44/v20 не стала production.

На RU у всех 14 старых контейнеров `restart=no`, они остановлены. Caddy замаскирован, backup,
watchdog и image cleanup timers отключены. Deployment authorized_keys обоих ограниченных
пользователей сохранены в закрытом снимке и заменены неисполняемым комментарием. Старые
deployment-доступы не должны оживить устаревших писателей.

## Транспорт, Telegram и обслуживание

Временные HAProxy receiver/forwarder на AMS, RU и Aeza отключены и замаскированы.
Порт 8443 не слушает, разрешения UFW для старых peers удалены. На RU нет слушателей
80/443/8443. Caddy AMS использует штатный [host Caddyfile](../../infra/production/host/Caddyfile)
без PROXY protocol. Исторические профили и порядок установки сохранены в
[entry](../../infra/production/entry/README.md), но не являются текущей конфигурацией.

На Aeza возвращён исходный Nginx на 443, удалён application HTTP relay, отключён Telegram relay
на 88 и удалены его два правила UFW. Личный Xray, служба подписок и их общие credentials сохранены;
они не принадлежат платформе. Probe Nginx на AMS замаскирован, его отдельный certbot timer отключён;
сертификатами рабочих доменов управляет Caddy.

GitHub environments `Production` и `Production-Telegram` получили новый `PRODUCTION_SSH_HOST`
и проверенный `PRODUCTION_SSH_HOST_KEYS`. Приватные deployment keys не менялись.

Telegram работает напрямую в обычной egress-сети. В host-owned override нет VLESS, `extra_hosts`
для Bot API и зависимости от старого transport. Webhook:
`https://telegram.sachkov.dev/webhooks/telegram`, pinned IP `147.45.166.174`, порт 443.
При регистрации сохранены allowed_updates, max_connections, секрет и ожидающие обновления;
`drop_pending_updates=false`. Регистрация не удалялась. Старый URL с портом 88 не является текущим.

На AMS включены три pgBackRest timers. RU больше не архивирует WAL.
После переноса `pgbackrest check`, полный backup и изолированное восстановление новой копии
`20261020-080918F_20261020-081840I` прошли. Восстановлены `inside`, `logto`, `inside_telegram`,
без сети, published ports и рабочих consumers. Совпали хэши 276 стабильных таблиц;
16 таблиц менялись на рабочей базе во время backup и исключены из этого сравнения.
Это отдельная проверка от полного сравнения холодной копии перед запуском.

Env-файлы заново зашифрованы SOPS для нового host age key и прежнего offline recipient;
значения 19 текущих файлов проверены после расшифрования новым host key. Проверка offline
private key не выполнялась. Доступ к секретам закрыт; приватный age key в репозиторий не попадает.

Watchdog включён, использует явную настройку в `/etc/inside/watchdog/watchdog.env`:

```dotenv
WATCHDOG_TELEGRAM_RELAY_ADDRESS=
```

Пустая строка и отсутствие настройки означают прямой DNS-маршрут Bot API. Исторический relay
используется только при явно заданном непустом адресе. Сигналы пока остаются в systemd и локальном signals.log:
каналы Telegram/SMTP у этого watchdog не настроены. Это не внешнее наблюдение за DNS/TLS и не
подтверждение доставки тревоги владельцу. Image cleanup не включён до проверки доступности
всех защищённых предыдущих образов.

## Проверки и известное ограничение

[Доказательства](../evidence/issue-1575/ams-migration-2026-10-20.json) объединяют фактические результаты.
38 HTTPS-запросов сайта и OIDC с принудительным AMS IP из девяти стран дали 200 и валидный TLS.
Это доступные сети Globalping, а не все пользовательские VPN. После отключения прежних входов
проверка через обычный DNS дала 37/38; один узел G-Core Labs в Алматы (AS202422) повторно
не завершил TLS авторизации за 15 секунд, хотя DNS и TCP прошли. Отдельная проверка Казахстана
дала 5/6, с тем же отказом; остальные проверенные сети Казахстана и России прошли. Причина
этого частного маршрута пока не установлена, результат не считается полностью зелёным.
В Chrome существующая сессия сохранилась; чистый контекст загрузил сайт и видимую форму входа
за 2618 мс. Полный новый вход, платёж, вступление/исключение участника не выполнялись.

На RU ещё до остановки существовали overdue=1/unapplied=1 в community operation. После переноса
этот же backlog сохранён, см. [#1595](https://github.com/sachkov-inside/platform/issues/1595).
Из-за него строгая Platform verification и расширенная проверка нулевых очередей Telegram
не зелёные. Дополнительные Platform reads после обновления проверяющего инструмента: 58 из 59 прошли, исключение billing-worker operator
attention; Telegram основные проверки проходят, за 30 секунд новые ошибки не выросли, backlog=1
сохранился. Записи не исправлялись вручную ради зелёной проверки.

На переходном этапе отрицательные PROXY-пробы проверили loopback/private/mapped claims и недоверенный peer.
На том этапе двенадцать служебных портов были недоступны с RU, TLS проверялся через AMS и оба
прежних IP. После отключения старых маршрутов Caddy reload прошёл, старые listener отсутствуют. Полная перезагрузка хоста не проверялась.
Исторический PROXY marker больше не используется. Фактический XFF внутри backend временным
echo после миграции не измерялся.

## Безопасный возврат

**Не включать старую RU-базу и не выполнять прежний DNS-only rollback из истории второго входа.**
После запуска AMS она устарела. При сетевом отказе можно подготовить другой вход, сохраняя актуальную AMS-базу; старые relay
теперь отключены и автоматически не включатся.
При возврате площадки остановить новые входящие изменения и все AMS writers, сохранить актуальные
PG и RabbitMQ volumes, перенести согласованную холодную копию на изолированные новые volumes RU,
сверить данные и только затем включить единственный комплект workers с теми же релизами.
Назад не переносить одни только веб-контейнеры без анализа их соединений и состояния.

До начала такого возврата определить место актуальных данных, backup label, единственного WAL
archiver, deployment target и порядок обновления webhook/DNS. Исходные RU volumes сохраняются
как снимок перед переносом. Новый rollback обязан сохранить записи, принятые AMS после перехода.
Закрытые снимки и протокол операции: `/root/inside-ams-migration-20261020` на AMS и
`/var/lib/inside/1575-ams-migration-20261020` на RU. Изолированный restore proof имеет отдельный
каталог `/var/lib/inside/1575-ams-post-cutover-20261020`; его временные cluster, repository и cipher
удалены после проверки. Закрытые снимки не публикуются в GitHub.

## Окончательное отключение прежних входов

[Протокол завершения](../evidence/issue-1575/ams-retirement-2026-10-20.json) дополняет исторический
протокол переноса. После отключения старых маршрутов GitHub Deploy production для v45 прошёл
вместе с Production access pass; Deploy Telegram для v21 и External production check тоже прошли.
Это проверка существующих релизов на новом SSH target, а не выпуск новых образов приложения.
Старые writers и deployment keys остаются отключёнными; удаление прежнего RU VPS выполняет владелец
после итогового подтверждения. Снимок старой базы не является актуальным резервом для новых записей.
