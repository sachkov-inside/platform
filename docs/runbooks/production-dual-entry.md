# Второй публичный вход через Aeza

Эксперимент #1575, 19 октября 2026. Второй HTTPS-вход установлен и проверен;
основные DNS-записи пока ведут на Timeweb. GeoDNS и автоматическое переключение **ещё не включены**.
Это один экземпляр приложения и базы, а не резервная площадка приложения.

## Устройство

```text
сейчас DNS sachkov.dev / auth / www / inside → Timeweb 201.24.126.23:443 → Caddy
проверяемый второй вход → Aeza 185.125.101.90:443 → HAProxy
  разрешённый SNI → Timeweb:8443 → HAProxy → 127.0.0.1:443 → тот же Caddy
  прочий SNI / без SNI → существующий Nginx 127.0.0.1:14443 → прежняя служба /sub/
```

Состав конфигурации — [infra/production/entry](../../infra/production/entry/).
HAProxy не расшифровывает TLS. Ключи сайта, сертификаты, Logto, маршруты приложения,
maintenance и ACME TLS-ALPN остаются у Caddy. Порт 80 Aeza передаёт HTTP-01 challenge на
Timeweb с исходным Host; прочие HTTP-запросы к четырём именам перенаправляются на HTTPS.
Почта, Telegram и его webhook не переводятся на второй вход.

IP посетителя передаётся через PROXY v2, а не доверенный HTTP-заголовок:

1. Порт 8443 origin доступен только от Aeza через UFW. HAProxy дополнительно проверяет
   **исходного** socket peer в `tcp-request connection`.
2. В `tcp-request session` проверяется уже разобранный адрес посетителя: loopback,
   частные и другие непубличные диапазоны блокируются до Caddy.
3. Локальный backend всегда `127.0.0.1:443`, исходящий адрес — `127.0.0.2`.
   Заявленный PROXY destination не выбирает backend.
4. Caddy принимает PROXY metadata только от `127.0.0.2/32`. Входящие HTTP XFF остаются
   недоверенными; существующая проверка socket peer удаляет внешний служебный marker.
   Настоящая локальная production-проверка сохраняет своё исключение.

Семантика фаз описана в [HAProxy accept-proxy](https://www.haproxy.org/download/2.8/doc/configuration.txt).
IPv4 ACL также проверяют IPv4-mapped IPv6. Нельзя добавлять `::ffff:0:0/96` в список запретов:
сопоставление HAProxy заблокирует этим **всех** IPv4-посетителей.

## Состояние установленных машин

- Origin: HAProxy 3.2.9 из Ubuntu; Aeza: HAProxy 2.8.16 из Ubuntu.
- На обеих машинах: `/etc/inside-entry/haproxy.cfg`, `inside-entry.service`, автозапуск включён.
  Пакетная `haproxy.service` отключена, чтобы не было второго владельца конфигурации.
- На origin: `/etc/inside-entry/non-public-clients.lst` и PROXY wrapper в `/etc/caddy/Caddyfile`.
- На Aeza: Nginx подписок слушает только `127.0.0.1:14443 ssl proxy_protocol`, доверяет
  PROXY адресу от `127.0.0.1`; HTTP-конфигурация — `/etc/nginx/conf.d/inside-entry-http.conf`.
  Изменение исходного server block записано в `nginx-subscription.patch`.
- UFW Aeza: 80/443 TCP ALLOW для IPv4/IPv6 вместо прежнего LIMIT. Это убирает лимит новых
  соединений на общий выходной IP VPN; HTTP-ограничения приложения сохранены. Остальные
  правила VPN не менялись. Дополнительной защиты от DDoS эта схема не предоставляет.
- Xray и его порты сохранены. Корень и пустой `/sub/` IP-службы возвращают прежний 404.
  Проверка рабочей подписки с личным токеном не выполнялась.

Конфигурация транспорта принадлежит хосту. Обычная выкладка приложения заменяет
`active.caddy`/maintenance внутри прежнего Caddy и не должна менять HAProxy или Nginx Aeza.
Хостовая переустановка Caddy использует версионный `infra/production/host/Caddyfile`;
для восстановления отдельного receiver нужны файлы транспорта из этого раздела.

## Проверки и восстановление

Порядок установки из версионных файлов и код отката — в
[инструкции транспорта](../../infra/production/entry/README.md).
Перед изменениями сохранить текущие файлы и правила UFW. Валидировать кандидаты до замены:

```sh
haproxy -c -f /etc/inside-entry/haproxy.cfg
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile # origin
nginx -t # Aeza
systemctl is-active inside-entry
```

Обычный запрос ниже не меняет системный DNS или VPN. Сверять соединение с журналом
HAProxy: некоторые VPN переписывают адрес назначения по SNI и обходят `--resolve`.

```sh
curl --fail --resolve sachkov.dev:443:185.125.101.90 https://sachkov.dev/ -o /dev/null
curl --fail --resolve auth.sachkov.dev:443:185.125.101.90 \
  https://auth.sachkov.dev/oidc/.well-known/openid-configuration -o /dev/null
```

`probe.py` выполняет ограниченную TLS-проверку с проверкой сертификата, включая PROXY v1/v2.
С Aeza можно проверить receiver; с другой машины firewall должен не пропустить соединение.
Timeout не считается доказательством отказа на уровне протокола.

```sh
python3 probe.py 201.24.126.23 --port 8443 --proxy v2
python3 probe.py 201.24.126.23 --port 8443 --proxy v2 --source 127.0.0.1 --expect rejected
python3 probe.py 201.24.126.23 --port 8443 --proxy v2 \
  --source ::ffff:127.0.0.1 --destination 2001:4860:4860::8888 --expect rejected
```

Снимки и первоначальные проверенные скрипты отката этой операции находятся на каждой машине в
`/root/inside-entry-backup-1575/`. На Aeza `rollback-edge` возвращает прежний Nginx на 443,
LIMIT и удаляет HTTP relay; на origin `rollback-origin` возвращает Caddyfile, закрывает 8443
и отключает receiver. Пакеты остаются установленными. Скрипты не трогают приложение или базу. Их версионный преемник — `rollback-entry.sh`,
который принимает роль и каталог снимка; личные снимки не коммитятся.
Откат обеих сторон и повторное включение выполнены 19 октября; прямой сайт сохранил 200,
IP-служба — 404. После будущей смены DNS сначала вернуть DNS на origin и дождаться истечения
TTL: немедленное удаление второго входа оборвёт посетителей с закэшированным адресом.

Файрвол закрывает временный 19443; staging unit и диагностический HTTP echo остановлены.
Автоматические таймеры аварийного отката остановлены после проверки здоровья.
Проверка перезагрузкой обеих машин не выполнялась; службы включены в systemd.

## Результаты и ограничения

[40 внешних запросов](../evidence/issue-1575/aeza-globalping-2026-10-19.json): сайт и OIDC
через Aeza дали 200 с валидным TLS из RU, DE, FI, NL, US, KZ, TR, GB, FR, включая AS9009.
Это выборка доступных сетей Globalping, не проверка конкретных VPN жаловавшихся людей.
[Негативные пробы](../evidence/issue-1575/origin-proxy-negative-2026-10-19.jsonl) проверяют
private/loopback/mapped адреса; детали локального опыта — в
[сводке](../evidence/issue-1575/transport-summary-2026-10-19.json).

Caddy сохраняет HTTP/3 для прямого входа. Aeza передаёт только TCP, но сквозной ответ пока
рекламирует `Alt-Svc: h3`. Проверены первая и повторная загрузка в Chrome по HTTP/2 и переход на страницу Logto;
дополнительно [curl_cffi](../evidence/issue-1575/quic-fallback-2026-10-19.json) получил H3 напрямую,
таймаут H3-only на Aeza и успешный fallback на H2 за 1.325 с.
[Chrome с сохранённым Alt-Svc](../evidence/issue-1575/chrome-quic-fallback-2026-10-19.json)
отправил QUIC-пакеты для сайта и загрузил страницу по H2 за 665 мс. Это проверка двух клиентов,
не всех VPN и браузеров. Перед массовым переключением нужны пробы пользователей.
Полный вход владельца, платёж и принудительный выпуск нового ACME-сертификата не выполнялись.
[Синтетический HTTP-01 token](../evidence/issue-1575/acme-http-relay-2026-10-19.json)
успешно прошёл через Aeza к origin для всех четырёх имён; диагностический маршрут удалён.

## Следующий этап: GeoDNS

Целевая политика для apex, www, inside и auth: RU → origin; остальные и неизвестные → Aeza.
Нельзя включать простой round-robin из двух A-записей: он выдаст недоступный адрес части людей.
GeoDNS не знает фактическую доступность из каждого VPN: обычно он видит DNS resolver,
а при EDNS Client Subnet — переданную подсеть. Раздельная DNS/HTTP-маршрутизация VPN может
дать несовпадение. Нужны проверки разных людей и возможность быстро поменять default.

Timeweb Cloud показывает обычную зону с 15 пользовательскими записями, TTL 600, без AAAA.
NS сменить в этой панели нельзя; [RDAP](https://rdap.org/domain/sachkov.dev) показывает PDR.
Для изменения NS нужен отдельный вход в [панель PDR](https://timeweb.myorderbox.com/), тип
«Клиент» ([инструкция Timeweb](https://timeweb.cloud/docs/domains/dostup-v-panel-upravleniya-registratora)).
Доступ владельца и выбор GeoDNS-провайдера пока не получены.
[15 пользовательских записей](../evidence/issue-1575/timeweb-user-records-before.zone) выгружены
с авторитетного NS через origin. Обычные DNS-запросы Mac в текущем VPN дали ложные пустые MX/TXT;
[аудит](../evidence/issue-1575/dns-before-2026-10-19.json) выполнен через SSH и DoH вместо них.
Из-за несовпадения DNS/HTTP-маршрутов владельцу предложен также общий вход через Aeza без GeoDNS;
это изменение плана пока не принято, основной DNS не переключён.

Перед сменой NS перенести **всю** зону: MX, SPF, DKIM, DMARC, Telegram и остальные имена;
сверить DS/DNSSEC и отсутствие нежелательных AAAA/HTTPS/SVCB. Проверить новые NS напрямую,
затем делегировать, проверить региональные ответы и откат. Регистратора переносить не нужно.
Отдельно настроить проверки здоровья: работающий Aeza без доступа к origin не означает здоровый сайт.
Пока этих проверок и доступа нет, этот документ не объявляет задачу #1575 завершённой.
