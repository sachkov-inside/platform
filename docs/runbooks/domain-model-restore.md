# Проверка восстановления доменной модели

Эта процедура проверяет синтетические изолированные базы Backend и Telegram. Она не запускает
восстановление production, публикацию, банковские операции или отправки Telegram. Production
recovery требует отдельного поручения владельца и проверки конкретного архива и окружения.

## Что доказывает проверка

У приложений разные базы, владельцы соединений и журналы миграций. Backend начинает с первых
103 неизменяемых migrations. Их registry identity:
`sha256:4202eac8e733fe5f60198130a06eb9a4b4b46aafa05c7f2ebf642c78cf8e4468`.
Исторические Product находятся в `materials.series`. Telegram начинает с собственной migration
`035-waitlist-confirmations`, до `036-material-announcements`, сохраняя настоящий `kysely_migration`, а не выдуманный общий ledger.

Каждая проверка создаёт собственный PostgreSQL 18.4 по закреплённому digest. `pg_dump` и
`pg_restore` запускаются внутри этого же контейнера. Базы и имена архивов случайные, подключение
доступно только на случайном loopback port, данные синтетические. Проверка не использует Compose,
общий стенд, host PostgreSQL tools или production credentials.

Проверки исполняются так:

1. На исторической схеме записываются смешанные финансовые, юридические, учебные и
   коммуникационные факты. Снимается полный архив в custom format, включая схему, данные,
   функции, triggers, sequences и migration ledger.
2. Источник обновляется настоящими migrators до текущего registry. Новые владельцы соединений
   выполняют восстановление незавершённых операций. Первый проход может завершить разрешённую
   первую выдачу или отправку. Второй сохраняет результат без повторного эффекта.
3. Снимается второй полный архив уже восстановленного состояния. Отдельная совершенно пустая
   база принимает его через `pg_restore --exit-on-error --single-transaction --no-owner --no-acl`.
   Перед restore проверяется отсутствие пользовательских таблиц и sequences. Непустая цель
   отвергается без попытки её заменить.
4. После reconnect сравниваются все строки всех пользовательских таблиц и состояния sequences.
   Проверяются настоящие migration ledgers, повторный migrator ничего не применяет. Два прохода
   новых публичных владельцев сохраняют права, историю, неопределённые исходы и внешний журнал
   эффектов. Этот журнал остаётся вне восстанавливаемой базы и не очищается при reconnect.
5. Первый, исторический архив отдельно восстанавливается в ещё одну пустую базу, сравнивается
   с точкой резервного копирования и обновляется вперёд. Старые финансовые и юридические
   условия, UUID, Task versions, сдачи и архив migration audit остаются проверяемыми фактами.

После `0113_historical_authoring_contract` Backend сравнивает все исходные строки Practice
с `materials.historical_practice_definitions` и оригиналы Source (включая оба значения
`showInFeed` и неизвестный commit) с `materials.historical_source_records`.
Публичное чтение Source возвращает version 2 и `productId` в memberships. Исторические
Source и Practice receipts читаются только для исходного автора, ключа и fingerprint;
изменённый запрос, чужой автор или новый ключ не создают записей. Эти проверки повторяются
после восстановления обоих архивов, включая удерживаемую legacy-базу.

Исторические строки `member_profiles` сравниваются целиком с `account_profiles` после
переименования схемы: private active и disabled Profile, opaque identifiers, avatar rendition
checksums и protected object keys, состояние cleanup и события disable/restore. Текущий
`AccountProfiles` возвращает владельцу только private projection, другой Account не получает
чужой avatar, disabled Profile не активируется при recovery. `AccountNames` возвращает только
имя active Profile. Это проверка сохранности данных и границ чтения; avatar upload и выполнение
cleanup worker здесь не запускаются, обращений к object storage нет.

Хеш и размер архива связывают доказательство с конкретными bytes. Они не заменяют фактический
restore и вызовы приложения. Копирование latest template или data-only dump не являются этой проверкой.

## Запуск и доказательства

Использовать закреплённые Node и pnpm из `.node-version` и `packageManager`. Требуется работающий
Docker. Две тяжёлые проверки занимают обычные слоты машины; отдельное разрешение стенда им не нужно.

```bash
pnpm --filter @inside/backend test:integration domain-model-mixed-restore.test.ts
bash scripts/heavy-check.sh pnpm --filter @inside/telegram exec vitest run --config vitest.mixed-restore.config.ts
```

Не добавлять `--` перед именем Backend test: этот аргумент может передать фильтр после разделителя
Vitest и запустить весь набор. Telegram config пропускает setup чужой общей базы, поскольку этот
test сам владеет контейнером и обеими сторонами restore.

Для сохранения machine-readable manifest задать `DOMAIN_RESTORE_EVIDENCE_DIRECTORY` в отдельный
каталог текущей проверки. Manifest содержит image/server/tools versions, команды и их exit codes,
размеры и SHA-256 архивов, результаты публичного восстановления и синтетический журнал эффектов.
Рядом сохранить stdout/stderr, immutable Git commit, хеши изменённых test sources и фактический exit.
Архивы удаляются вместе с собственным контейнером. Manifest сохраняется после joined cleanup.

## Необратимая граница и удержание отправок

Contract удаляет прежние writable aliases и физические имена после переноса потребителей.
Нельзя запускать прежний application artifact поверх такой базы и нельзя обещать обратную
миграцию новых записей. Возврат к backup восстанавливает состояние на момент backup. Он не
отменяет последующие списания, выдачи, сообщения или изменения личной истории.

Особенно различаются два архива:

- Архив после завершения recovery содержит receipts уже выполненных эффектов. Его обычное
  повторное восстановление проверяется с неизменным внешним журналом и без новой отправки.
- Исторический архив может содержать pending очередь, внешние эффекты которой уже произошли
  после backup. Восстановление этого архива не возвращает потерянные receipts автоматически.
  Автоматическая повторная отправка такой очереди запрещена до сверки.

Перед recovery старого архива остановить ingress и все отправляющие workers обоих приложений.
Для Telegram сохранить `TELEGRAM_DELIVERY_MODE=disabled`, `TELEGRAM_MARKETING_ENABLED=false` и
закрытое admission уведомлений. В изолированной проверке два публичных прохода WaitlistConfirmations
и SequenceScheduler дают ноль отправок, NotificationProvider получает unavailable authorization,
сохраняет pending/accepted и прежние sent/unknown outcomes. Чтение receipts не требует отправки.
Один только marketing flag не отключает служебные уведомления или сообщения о waitlist.

При восстановлении Backend сначала оставить банк отключённым и billing workers остановленными.
Сверить retained bank references с банком, подтверждения и уже выданные Product Access. Не повторять
`Init` или charge ради получения потерянного ответа. Неопределённый ответ остаётся неопределённым.
Отзыв владельца не снимается восстановлением fulfillment. Возврат денег и отзыв доступа остаются
отдельными действиями.

До включения отправок оператор сверяет post-backup bank/Telegram результаты, идентичности
операций, ссылок и revisions, сохраняет исходные receipts и unresolved cases, затем проверяет
готовность отдельно собранных текущих Backend/Web/Telegram artifacts. Сначала читатели и
проверенные владельцы, затем разрешённые producers. Проверка синтетического restore не означает
выполненный production rollout. Если конкретный эффект нельзя доказать как неотправленный,
нельзя придумывать receipt, очищать started barrier или объявлять его безопасным для повтора.
