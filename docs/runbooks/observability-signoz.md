# SigNoz: функциональная проверка на Linux

Этот сценарий относится к #1566 и проверяет запасной вариант мониторинга на отдельном
GitHub-hosted `ubuntu-24.04` с настоящей архитектурой Linux amd64. Он не устанавливает
мониторинг на рабочий сервер. [Основной сценарий](observability-pilot.md) сохраняет свои
пороги и проверку полного приложения.

## Что проверяется

[Workflow](../../.github/workflows/observability-signoz.yml) является источником команд запуска.
Он проверяет исходники, получает семь закреплённых образов и запускает одиннадцать ролей,
включая три вспомогательные роли, PostgreSQL, ClickHouse Keeper, ClickHouse, migrator,
collector, SigNoz server, native MCP и отдельный ограниченный клиент. Базовый профиль по умолчанию
`signoz-native-4096m-v1` сохраняет суммарные ограничения 2 CPU и 4096 MiB памяти.
Остановленные init-контейнеры также входят в эту сумму. Существующий workflow явно выбирает
следующий отдельный опыт `signoz-native-mcp512-4480m-under8g-v1`: только память MCP и
соответствующий `MemorySwap` увеличены со 128 до 512 MiB. Выделенная сумма равна
4480 MiB (4.375 GiB, 4697620480 bytes), экспериментальный потолок отдельно равен 8192 MiB.
Оставшиеся 3712 MiB никому не выделяются. У каждого контейнера `MemorySwap` равен `Memory`,
дополнительный swap запрещён. Остальные десять ролей, общий CPU, pids, образы и функции
сохраняются. Профили закрыты и неизменяемы; произвольных значений памяти из CLI или env нет.
`--profile` принимает только эти два имени; без него используется исходный базовый профиль.
Клиент получает 0.05 CPU/64 MiB из прежних 0.1 CPU/128 MiB `histogram-init`;
у `histogram-init` остаются 0.05 CPU/64 MiB. Остальные лимиты сохраняются; MCP базового профиля остаётся 128 MiB, отдельного опыта 512 MiB.

У worker один внешний срок 600 секунд, включая получение образов и инициализацию.
Завершение процессов и удаление зарегистрированных ресурсов имеют отдельный общий срок
90 секунд. Обычная готовность receiver/server сохраняет срок 55 секунд. Чтение двух
таблиц миграций PostgreSQL использует read-only transaction, `statement_timeout=1000`,
`lock_timeout=1000` и native CLI не более 10 секунд. Отсутствующая таблица, ошибка SQL,
дедлайн или неверный ответ означают недоступность наблюдения. Они не означают ноль миграций.

Успешный результат требует одновременно:

- завершённых миграций ClickHouse и положительного фактического числа миграций PostgreSQL;
- готовности collector и server, native MCP `/readyz`, `initialize`, полного `tools/list`
  и фактического вызова `signoz_execute_builder_query`;
- сохранённых 400 отдельных точек метрики со значениями 1…400, одного trace и одного log
  с общими `traceId`/`spanId`, положительного запроса корреляции и пустого контрольного trace;
- созданного managed `signoz-viewer` service account, проверки его идентичности,
  отказа `403` на административное чтение и последовательности revoke `204`, затем `401`;
- четырёх разрешённых HTTP-over-Unix чтений из отдельного клиента, девяти `403` для
  запрещённых gateway paths, delete, SQL, параметров и неверного ключа;
- явного kernel `ENETUNREACH` при десяти TCP попытках клиента к настоящим IP/ports
  PostgreSQL, ClickHouse, Keeper, collector, server, MCP и backend helper;
- полного состояния всех одиннадцати ролей до удаления: init jobs завершены с кодом 0,
  остальные роли работают, ни у одной роли нет OOM или неожиданного restart;
- подтверждённой очистки собственных containers, volumes и network.

Gateway представляет границу тестового клиента внутри disposable fixture. Его единственный
runtime listener является Unix socket, TCP control endpoint отсутствует. Его интерфейс
принимает только имя одной из четырёх операций и пустой объект параметров. Он не является
готовым production gateway. Полный native MCP имеет более широкую поверхность инструментов,
поэтому его ключ не выдаётся этому клиенту.

## Изоляция и доказательства

Runner связывает commit/tree, SHA выполнения, head/base PR, run/attempt и хеши всех входных
файлов с чистым checkout. Mac и эмуляция amd64 не допускаются. Выбранный профиль связан с тем же source SHA в source/owner/Compose/registry/outcome и
передаётся worker, recovery и collector. Несовпадение профиля или plan digest запрещает
native-команды и очистку по неверному контексту. До запуска основной проверки и после
конечной проверки состояний сохраняются фактически проверенные ограничения всех одиннадцати
контейнеров. Collector сверяет каждую роль, память, swap, CPU, pids, source commit/tree,
профиль и план. Он не заменяет точное равенство лимитов проверкой «сумма меньше потолка».
`witness.json` schema 2 явно различает `profile_id`, `aggregate_memory_bytes` выделенной суммы
и `experimental_ceiling_memory_bytes`; `resource_profile` содержит только закрытые числовые
наблюдения и исходные хеши. `inspection_stage` различает начальный допуск и конечную проверку;
успех требует конечной проверки, начальное наблюдение сохраняется при раннем отказе.
При отсутствующем или смешанном доказательстве профиль недоступен,
общий результат неуспешен. Новый профиль не отменяет ни одного прежнего функционального,
изоляционного, state или cleanup условия и не делает `capacity_acceptance` истинным.
Замораживаются локальные Docker CLI, Compose plugin, socket, daemon и файловые системы хранения. До получения образов
проверяется существующая политика свободного места; во время работы сохраняются её
ограничения роста, минимального остатка и запаса для очистки. Это мягкий ограничитель
хранения, а не отдельная файловая квота.

Каждый ресурс имеет случайный project/nonce и проверенные native ID, время создания,
image/platform, ограничения, mounts и labels. Очистка отказывается удалять заменённый
или чужой ресурс. Нет опубликованных host ports, Docker socket внутри контейнеров,
production credentials и внешнего telemetry payload. Backend сеть внутренняя; native MCP использует
встроенную документацию release с отключёнными плановыми обновлениями.

У ограниченного клиента `network_mode: none`, отдельный network namespace и единственный
интерфейс `lo`. Native inspect связывает CID, PID/start time, mounts и namespaces клиента,
helper и host; namespace клиента отличается от двух остальных. Клиент получает только
source driver, минимальный admission с finite token и адресами проверяемых backend,
а также RO mount отдельного socket-only volume. У него нет `/private`, DSN, viewer key,
probe volume и Docker socket. Семь volumes, включая отдельный gateway volume, имеют
точное владение и входят в cleanup. Перед и после соединения клиент сверяет inode/device,
тип, владельца и `0600` socket; kernel peer credentials должны совпадать с ожидаемым uid/gid.

Изолированный agent запускается после создания, регистрации и проверки всех ролей, до
инициализации backend. Его resident process только загружает модули и ожидает. Проверка
готовности Unix socket выполняется отдельной конечной командой `agent_probe.py socket-identity`
в cgroup agent с прежними `0.05 CPU / 64 MiB` и сроком команды 10 секунд. Так она не конкурирует
с functional и дисковым наблюдателем в cgroup disk `0.1 CPU / 96 MiB`. Admission записывается
только после проверки socket и исходной проверки изоляции namespaces перед запуском клиента.
Срок дисковой команды остаётся 3 секунды; этот порядок сам по себе не доказывает прохождение
native witness и не является оценкой мощности для production.

Успешное TCP соединение, даже если backend вернул бы `401`, является ошибкой проверки.
Timeout, `ECONNREFUSED` и необъяснённая ошибка не считаются доказанным сетевым запретом.
Единственное положительное основание для backend IP denial здесь является `ENETUNREACH`
в подтверждённом network-none контексте. Диагностический DNS probe имеет отдельные поля:
`EAI_AGAIN` и незавершённый probe означают недоступность наблюдения. DNS не объявляется
успешным запретом и не подменяет доказательство kernel IP denial.

Каталоги fixture создаются с правами `0700`, файлы с паролями и private evidence с `0600`.
Учётные данные генерируются на каждый запуск. Ответы HTTP, ключи, email, DSN, raw SQL
и container logs не публикуются. Ошибка CLI сохраняет до 32 KiB каждого потока только
в private evidence, вместе с настоящим nullable exit status до завершения процесса.
Публичный `witness.json` содержит только проверенные поля, числовые наблюдения, исходные
хеши, выбранные image IDs и состояние очистки. Он создаётся и при раннем отказе.
Публичный отчёт не заменяет private evidence, которое upload шага не выбирает.
При отказе native CLI отчёт сохраняет закрытую категорию фактически вызванной операции
и формы аргументов, nullable exit status, размеры и хеши private stdout/stderr.
Последняя логическая операция `Engine.call` после проверки identity отмечена как
`started`, `succeeded` или `failed`. Внутренние raw-вызовы freeze/identify не входят в этот статус.
Текст stderr и значения аргументов не публикуются. Категория stderr определяется только
по точному разрешённому образцу; `unclassified` означает неизвестную причину, а не
подтверждённую ошибку registry, Docker API или provider. Такой отчёт не разрешает повторять
неуспешный запуск без разбора причины и не меняет его результат на успешный.
При отказе bootstrap его первая закрытая диагностика сохраняется на самом исключении
до обязательного revoke. Успешный DELETE `204` не заменяет исходные stage, transport и
HTTP status. Если обычная ошибка revoke следует за первоначальной ошибкой, сохраняются
первоначальный объект и traceback; без первоначальной ошибки revoke по-прежнему завершает
проверку отказом. Revoke использует тот же deadline, прерывания не подавляются.
Этапы `bootstrap_key`, `bootstrap_identity`, `bootstrap_roles`, `bootstrap_fixed_read`
различают проверку ключа, identity, назначенных ролей и фиксированное чтение, включая
неверный ответ с HTTP `200`. Перехваченные локальные отрицательные проверки не становятся
общим «первым отказом». Только фиксированное bootstrap-чтение дополнительно отмечает
первую неуспешную проверку конечным этапом `bootstrap_read_*`, связанным с конкретным
исключением. Проверки и их порядок не меняются: `bootstrap_read_response` сохраняет
исходное совместное условие размера body и HTTP status, `bootstrap_read_number` проверяет
тип числа и конечность, `bootstrap_read_number_range` сохраняет совместную проверку
неотрицательности и целого значения, `bootstrap_read_count_nonzero` означает отказ
исходного требования `count == 0`. Остальные разрешённые этапы различают deadline, decode,
объект и envelope, scalar type, warning, results, query, columns и rows. Обычные request
и scalar-вызовы не включают эту диагностику; собственные исключения вычисления выражений
не превращаются в ошибки проверки. Эти этапы уточняют будущий отказ, но не устанавливают
причину ранее полученного native-отказа и не меняют его результат.
Фиксированное bootstrap-чтение использует builder filter
`span.serviceName = 'platform-fallback-control'`. В закреплённом SigNoz v0.146.0 это
[объявленное span-поле](https://github.com/SigNoz/signoz/blob/da556abac1fd41590811b8e0dcbcbdea242dd285/pkg/telemetryschema/tracestelemetryschema/const.go),
которое [storage сопоставляет с `resource_string_service$$name`](https://github.com/SigNoz/signoz/blob/da556abac1fd41590811b8e0dcbcbdea242dd285/pkg/telemetryschema/tracestelemetryschema/storage.go).
Так фиксированная resource service identity определяется и при пустом каталоге полей,
с прежними окном в минуту, одним запросом, viewer key и требованием `count == 0`.
Сам поиск metadata и его ошибки сохраняются; любые warnings остаются отказом.
Owned HTTP source model проверяет этот контракт, но не исполняет SigNoz и не устанавливает
класс warning ранее наблюдавшегося native-отказа. Результат замены требует нового native CI.
Вызовы MCP дополнительно сохраняют конечный этап первого отказа в том же исключении.
`mcp_wire_*` различают admission, отправку, headers/read, HTTP status, обычный body cap,
10-секундный deadline, decode и закрытие соединения. `mcp_inventory_size` обозначает
превышение отдельного предела каталога в фиксированном внутреннем вызове `tools/list`.
`mcp_rpc_*` различают объект,
версию JSON-RPC, id, error, result и isError; `mcp_initialize_version` сохраняет
проверку согласованной версии. `mcp_inventory_*` различают nextCursor, тип и
исходный предел1..128 tools, наличие обязательного query tool. Проверки,
порядок и bounds остаются прежними, pagination и дополнительные запросы не появляются.
Каждый wire-вызов сбрасывает прежний HTTP status; transport `mcp_http` и допустимый
status относятся к этому вызову, а не к предшествующему `query_v5`. До ответа status
равен0. Tag связан с authority и identity конкретного исключения, скопированный
или произвольный tag не подменяет контекст. Локальный отрицательный probe не становится
общим первым отказом. Обычный отказ закрытия соединения не заменяет уже активную
ошибку wire; без первоначальной ошибки закрытие по-прежнему может завершить вызов
отказом. Прерывания cleanup сохраняют прежнее распространение. Последующий revoke
не затирает первоначальный MCP stage/status/transport и traceback.

Новый этап уточняет следующий native-отказ, но не объясняет уже полученный
`mcp_inventory`/`ControlFailure`. В текущем результате66fc worker завершился
с exit1 за288.31056974 s; storage monitor и cleanup прошли. Сохранённый
`query_v5` HTTP200 мог относиться к более раннему bootstrap и не устанавливает
статус MCP inventory. Превышение body/deadline, форма каталога и JSON-RPC остаются
проверяемыми гипотезами до нового source-bound CI. Body, tool names, headers,
ключи и текст error не публикуются, формат остаётся из тех же пяти полей.
Предел тела для фиксированного внутреннего `tools/list` составляет262144 bytes.
Остальные вызовы сохраняют предел65536 bytes;3s disk helper,10s wire,55s readyz,
600+90 и30s owning protocol gate не расширяются.

Неизвестные значения обозначаются `unavailable`, HTTP status `0`
означает отсутствие сохранённого допустимого HTTP status. Текст ошибки, body, ключи,
идентификаторы и произвольные атрибуты исключения не входят в диагностику. Формат private
сообщения остаётся из пяти полей: `inside_failed`, `stage`, `category`, `http_status`,
`transport`. Collector отклоняет лишние или отсутствующие поля, неверный marker и HTTP
status; неизвестные stage, category и transport становятся `unavailable`.
Если основной блок worker уже завершился исключением, завершающий отказ storage monitor
не заменяет исходное исключение и его traceback. При успешном основном блоке отказ monitor
по-прежнему завершает запуск неуспешно. `storage_monitor` в публичном отчёте сохраняет только
первую закрытую пару stage/reason из `disk-last.json`, признак завершения monitor и этап
его завершения. Произвольные категории, текст ошибок, пути и значения private samples
не публикуются. Нераспознанные stage/reason становятся `unknown`, отсутствие корректного
наблюдения даёт `available: false`. Ожидаемая отмена остановленного monitor не считается
новым отказом. Для уже запущенного native вызова отмена признаётся только по собственному
процессу monitor и запросу остановки, сделанному строго до его monotonic deadline.
Поздняя отмена или совпадение со сроком не скрывают отказ по сроку. Время первого запроса
отмены сохраняется только в памяти до завершения этого процесса. Ошибка отмены или
незавершённый thread остаются видимыми отдельно от
исходного отказа worker. Сроки, частота наблюдений и правила успешного результата сохраняются.

Для первого отказа monitor поле `first_inner_command` дополнительно различает внутреннюю
команду, которая выбросила то же исключение: `context_show`, `context_inspect`, `daemon_info`,
`container_inspect`, `disk_exec` или `unknown`. Контекст сохраняется на исключении до reap,
поэтому поздний отказ основного блока или завершения не заменяет его последней командой.
Публикуются только фактически ограниченный `timeout_seconds`, `elapsed_seconds` по monotonic
clock, `native_exit` и `alive_before_reap`. Числа времени должны быть конечными и находиться
в диапазоне 0–690 секунд, timeout строго положителен. Это граница проверки диагностических
данных, она не увеличивает runtime или срок команды. Отсутствующий, некорректный или не связанный
с raw-вызовом контекст даёт `available: false`, без подстановки нулей. Аргументы, endpoint,
CID/PID, stdout/stderr и текст исключения не публикуются. Диагностика не добавляет native
вызовов и не устанавливает причину исторического отказа или нехватку ресурсов runner.

Для `disk_exec` новое необязательное поле `disk_helper_stage` показывает последнюю
подтверждённую отметку helper: `entered` после импорта `sys`, `imports_complete` после
исходных импортов `json`, `os`, `time`, `syscalls_complete` после обоих вызовов
`statvfs` и `stat`. Последняя отметка не доказывает завершение сериализации или доставки
stdout. Это фиксированные строки только для режима `disk`, в пределах прежних трёх секунд.
После существующего reap читаются только уже доступные остатки stderr, без ожидания или
новой команды. Принимается лишь полный упорядоченный префикс трёх отметок с EOF и общим
размером не более 128 байт. Неполный захват, неверный порядок, посторонние данные или
отсутствие отметок дают `unknown`. Даже EOF после остановки Docker CLI не доказывает,
что удалённый helper не начал выполнение. Старые записи без поля также не определяют
стадию. Сырые отметки и stderr не публикуются, а стадия сохраняется на исходном исключении
после reap. Сроки, ограничения ресурсов и условия успешного результата не меняются.

Семь исходных INDEX pins сохраняются. Для каждого в [OCI packet](../../infra/observability/signoz/oci/)
закреплены исходные байты index, child manifest и config: SHA256, точные размеры,
единственный linux/amd64 child, platform/config и volumes проверяются до acquisition.
Файлы не преобразуются formatter. Чтение локальное, ограниченное и один раз на engine,
без runtime HTTP к registry. Дубликаты JSON keys, подмена, отсутствующий файл или symlink означают отказ.

Pull с `--platform linux/amd64`, Compose, inspect и recovery используют один reference
`repository@childDigest`, выведенный из того же INDEX. `image inspect` не требует нового
[флага API 1.49+](https://docs.docker.com/reference/cli/docker/image/inspect/).
Native OS/architecture, RootFS и порядок diff IDs должны совпасть с проверенным config,
а RepoDigests должны содержать этот child в ожидаемом repository. Сохраняются проверки
Entrypoint/Cmd/User/WorkingDir и volumes. SHA256 всего config связывает и остальные поля;
новые требования к API-проекции Env/Labels/ArgsEscaped не добавляются.

Поддержаны две точные связи: native image ID равен config digest либо child digest.
Вторая требует корректных native image Descriptor и container ImageManifestDescriptor.
В первой только фактическое отсутствие поля допускается как недоступное native доказательство,
поскольку полная OCI-цепочка и native config ID/RootFS/platform доказывают другую строгую связь.
Любое присутствующее null, пустое, повреждённое или несовпадающее поле означает отказ.
В Descriptor проверяются digest, media type и точный размер исходного child manifest,
а при наличии platform также её значения. Отсутствующую platform подтверждают обязательные
index/config и native OS/architecture. Экспериментальная [семантика Moby](https://github.com/moby/moby/blob/5ed8b59a47094d686c9327999b451513a637a16d/api/types/image/image_inspect.go)
не используется для предположений о версии или storage mode фактического daemon.

Контейнер должен иметь `Config.Image`, точно равный child reference, и `Image`, равный
проверенному native image ID. CID/Created/nonce, лимиты, mounts и network остаются обязательными.
В отчёте различаются native descriptor, его наблюдаемое отсутствие и ещё не выполненная
проверка контейнера. Неполная связь контейнера не допускает успешного результата.
После успешной проверки всех одиннадцати контейнеров их связи с образами сохраняются
до запуска основной функциональной проверки. Позднейший отказ сохраняет это доказательство
допуска, но не подтверждает работоспособность, здоровое состояние ролей или общий успех.
Метаданные OCI не доказывают независимо соответствие compressed layers распакованным
слоям без их чтения: обработка слоёв и native наблюдения опираются на доверенный Docker daemon.
Отказы image admission публикуют только фиксированную причину из общего
`ImageAdmissionReason`, который используют сами проверки образа и collector.
Это различает отказ Descriptor, архитектуры, закреплённой конфигурации или volumes,
сохраняя неуспешный результат запуска. Неизвестная причина остаётся
`unclassified_failure`; текст исключения и произвольные суффиксы не публикуются.

Supervisor находится вне session worker. Native CLI создают собственные process groups
внутри этой session, чтобы recovery после `SIGKILL` worker мог завершить их все. При
обычном завершении Linux supervisor сохраняет zombie leader до проверки PID/start time
и очистки session. Поздняя recovery без доказуемой идентичности живой session отказывает
в таком завершении и оставляет результат очистки неуспешным, не затрагивая чужие процессы.
Повторная recovery не превращает первый неуспешный запуск или cleanup в успешный.

Tooling wrapper и workflow используют один `verify.mjs` с исходным сроком suite 30 секунд.
Workflow закрепляет Node через `.node-version` и pinned `setup-node`. Существующий внешний
`owned-process.py` владеет всем деревом тестов, включая отдельные sessions, при timeout,
SIGTERM и SIGKILL Node owner. Регрессионные проверки завершаются по фактическому отсутствию
всех зарегистрированных PID, сохраняя независимый foreign sentinel; вложенный fault fixture
пропускает только рекурсивный запуск самого wrapper test. Обычный suite выполняет эти тесты полностью.

## Закреплённые API и выпуск

[Lock](../../infra/observability/signoz/inputs.lock.json) сохраняет image index/amd64 manifests,
OCI metadata, конфигурацию и хеши первичных исходников API. Bootstrap основан на
[SigNoz v0.146.0](https://github.com/SigNoz/signoz/tree/da556abac1fd41590811b8e0dcbcbdea242dd285),
native transport на [SigNoz MCP v0.15.0](https://github.com/SigNoz/signoz-mcp-server/tree/d6a95cbb043ca7e0039cc4cbdfe9c68e5b988e9d).

Готовность native MCP проверяется через `/readyz`, который ждёт готовности индекса
документации. В закреплённой версии этот endpoint возвращает обычный текст: HTTP 503
означает, что индекс ещё не готов, HTTP 200 означает готовность. Только этот вызов
использует HTTP status без разбора JSON. Тело по-прежнему читается целиком в пределах
65536 bytes, сохраняются исходные ограничения 10 секунд на запрос, общего времени
и закрытие соединения. JSON-RPC `initialize`, `tools/list`, чтения MCP и ответы OTLP
по-прежнему требуют корректный JSON. Только фиксированный внутренний вызов `tools/list`
с пустыми params и id2 получает отдельный предел262144 bytes и читает не более262145 bytes.
Его право связано с внутренним объектом и конкретным исходным запросом к `/mcp`; строка
method, тело запроса, `FUNCTIONAL_STAGE`, CLI, конфигурация и данные агента не выбирают лимит.
Любой обычный `mcp_call`, включая `tools/list`, сохраняет предел65536 bytes и чтение65537 bytes.
HTTP status, JSON-RPC, отсутствие nextCursor, предел1..128 tools и обязательный query tool
проверяются в прежнем порядке, без pagination и дополнительных запросов. Полный публичный
каталог закреплённой версии содержит43 tools. Его локальная компактная модель занимает214194
UTF-8 bytes, модель с Go HTML escaping и завершающим переводом строки занимает214765 bytes.
Исходный форматированный fixture занимает434642 bytes вместе с метаданными и не является
native HTTP body. Тест воспроизводит обе модели через настоящий локальный HTTP и доходит до
намеренного OTLP503 только на пятом запросе. Это не устанавливает метод или полный размер
ранее наблюдавшегося native-отказа и не заменяет новый native-прогон.
Пустой HTTP 202 после `notifications/initialized` сохраняет прежнее поведение. Закреплённый MCP использует `JSONResponse: true`, поэтому
это изменение не добавляет разбор SSE и не заменяет готовность проверкой `/livez`.
Локальные HTTP-тесты проверяют эту границу протокола; завершение всего функционального
опыта и достаточность сервера подтверждаются отдельно фактическим native-прогоном.

Используются `/api/v1/register`, `/api/v2/sessions/email_password`, `/api/v1/roles`,
`/api/v1/service_accounts`, `/api/v1/service_account_roles`, создание/удаление keys,
`/api/v1/service_accounts/me` и `/api/v5/query_range`. При несовместимом API или недоступности
managed viewer запуск завершается ошибкой. Он не включает платную функцию и не покупает лицензию.

В проверенных исходниках базовые managed viewer/service account/key доступны в общей
Community/Enterprise реализации; custom roles имеют отдельные ограничения. Маркер
`ENTERPRISE` у официального образа сам по себе не доказывает необходимость покупки.
Этот сценарий не устанавливает юридическую допустимость конкретного образа для production.

## Ограничения результата и следующий этап

Даже зелёный `witness.json` подтверждает только функциональность этого fixture. Он не
доказывает совместимость полного приложения, стоимость запросов, p95, потери при сбоях,
свежесть данных или достаточность сервера. Первоначальный лимит native MCP базового профиля составляет
128 MiB; официальный README рекомендует не менее 512 MiB. Следующий явно выбранный опыт
512 MiB проверяет достаточность этого ограничения без отключения встроенного индекса или
изменения двух настроек обновления документации, которые остаются 0. Его достаточность ещё не
измерена. Предыдущие failed corpora сохраняют свои исходные профили и результаты. Наблюдение
MCP exit 137 / OOMKilled не устанавливает домен или порядок OOM; новый опыт не доказывает
причину старого отказа. Даже успешный функциональный результат относится только к указанному
профилю и окну, не выбирает production RAM и не подтверждает мощность полного workload.
OOM или неготовность остаются ошибкой, автоматического повышения лимитов или повторов нет.

Следующий независимый этап при необходимости: адаптер существующих 12 фаз полного
workload к этому lifecycle и фиксированным чтениям. Он должен сохранить те же источник,
corpus, все роли и квоты, SDK sampling, p95/CPU, freshness/lag, окна и общий срок 600 секунд,
проверки отказов, отсутствия потерь и cleanup. Только фактическое Linux сравнение OFF/ON
может обосновать выбор запасного решения и расчёт production мощности. Предыдущие Mac
запуски являются диагностикой; их нельзя использовать как доказательство такой мощности.

## Отдельная диагностика команды чтения диска

Дополнительная задача `disk_component` включается только точной строкой
`<!-- signoz-disk-component: run -->` в описании обычного pull request. Условие workflow
служит предварительным фильтром. Перед native-командами компонент сам проверяет точный
маркер с учётом регистра в ограниченном `GITHUB_EVENT_PATH`; неверный или отсутствующий
JSON, body и маркер запрещают запуск. Recovery уже зарегистрированного source/owner
не зависит от наличия маркера, чтобы удалённый маркер не мешал очистке. Задача использует
отдельный GitHub-hosted `ubuntu-24.04`, отдельный project и артефакт
`signoz-disk-component-<run>-<attempt>/component.json`. Основная функциональная проверка
выше сохраняет прежние команды, 11 ролей, пороги и сроки. Обе задачи проверяют полный
набор Python contracts через прежний wrapper с пределом 30 секунд.

[Компонент](../../scripts/observability-signoz/disk_component.py) создаёт только
`volume-init` и `disk` из прежнего плана: семь volumes и одна внутренняя сеть, те же
mounts, закреплённый native amd64 Python, `disk` 0.1 CPU/96 MiB, `volume-init` 0.025 CPU/32 MiB,
`MemorySwap` равен `Memory`, pids128. Сумма этих двух ролей составляет 0.125 CPU/128 MiB.
Для source/owner/recovery явно выбран `signoz-native-mcp512-4480m-under8g-v1`;
определения этих двух ролей совпадают с базовым профилем. Остальные девять ролей
не запускаются и не входят в фактическую сумму этого опыта. Параллельного storage monitor
здесь нет. Перед получением образа и между измерениями проверяется прежняя политика
свободного места на host, а состав ресурсов и фактические лимиты сверяются до и после.
Во время измерения полная инвентаризация выполняется ровно дважды: при входе и после
всех трёх команд. Итог сравнивается с сохранённым исходным снимком до записи
`component-inventory-after.json`. Между командами повторное обнаружение всех volumes
и сети не требуется; перед каждой конечной командой сохраняются исходные проверки
идентичности, квот и образа `disk`, а также preflight Engine. Это уменьшает число
повторных native-команд, но не обещает завершение за 60 секунд и не объясняет
прежний трёхсекундный отказ основного функционального опыта.

В фиксированном порядке выполняются по одной попытке: `/bin/true`, Python с импортами
`json`, `os`, `sys`, `time` и точным завершающим token, затем неизменённый настоящий
`lifecycle.vm_sample` через `Owned.exec`. Каждая конечная native-команда имеет прежний
предел 3 секунды. Проверки идентичности и `inspect` сохраняют собственные пределы
10 секунд. Поэтому три конечных окна по 3 секунды не означают 9 секунд всей проверки.
Если полного конечного окна уже нет, результат `not_run`; сокращённый timeout не
превращается в сравнимый отказ. Только последовательный конечный вызов raw получает собственное
полное окно 3 секунды без повторного ограничения оставшимся временем в `Engine.raw`. Предварительная
проверка остатка остаётся обязательной, общий предел измерения по-прежнему принадлежит
внешнему worker supervisor. Исходный конечный deadline восстанавливается в `finally`,
вызовы из других потоков запрещены. Неполная или прерванная фаза не позволяет
использовать даже быстрые записанные случаи как полное сравнение. Отсутствующий executable также не доказывает медленный daemon.

Подготовка контейнеров, измерение и очистка выполняются в отдельных workers под внешними
supervisors на 180, 60 и 90 секунд. Первичная проверка исходников проверяет чистый checkout
до регистрации setup worker, до Docker-команд и до создания native-ресурсов. Его время
вычитается из 180 секунд: если запас уже исчерпан, setup имеет `status: not_run`,
worker не запускается, а фактическое время, например 181 секунда, сохраняется целиком.
Сам Git/source bootstrap ограничен внешним шагом workflow на 8 минут и задачей на
12 минут. Это не жёсткий срок 180 секунд для bootstrap и не обещание общей длительности
180 + 60 + 90 секунд. Публичные поля отдельно называют `native_setup_limit_seconds`,
`native_setup_clock_includes_bootstrap`, `bootstrap_step_outer_limit_seconds`
и `workflow_job_outer_limit_seconds`. При прерывании или неполных source/owner receipts
recovery запрещает native-операции; отсутствие доказательства не становится успешной очисткой.
Каждый worker регистрируется по PID/start time до native-команд; cleanup worker имеет
отдельную запись, чтобы исходный recovery не завершал сам себя. При существующем owner
до любого сигнала проверяются source/request/owner, исходный план и его digest,
профиль/project/nonce и состав существующей registry. Допустимая частичная registry
и её отсутствие сохраняют обычный путь очистки. До появления owner проверенные
source/request разрешают только остановку своих зарегистрированных worker и cleaner.
Неверный контекст запрещает сигналы и native-команды. Фактическое время включает
завершение процессов и не обрезается до лимита: превышение запрещает полноту диагностики.
`outer_elapsed_seconds` относится ко всему вызову случая, включая preflight и reap;
это не внутренняя native-метка. Только доступный `first_inner_command` при отказе
сохраняет прежние exception-bound cap/elapsed/exit/alive observations.

Collector сверяет source, профиль, исходный план, image/config identities, лимиты,
неизменность native ID и времени создания до/после, frozen CLI/Compose/daemon identities,
конечные окна и очистку ровно 2 containers/7 volumes/1 network. Смена идентичности,
неполные случаи, неверные или неизвестные поля, несоответствие профиля и неудачная
очистка запрещают `diagnostic_complete`. Raw stdout/stderr, аргументы, пути fixture, nonce,
CID, DSN и переменные окружения в этот артефакт не копируются.

`diagnostic_complete` говорит о полноте отдельного опыта, включая правильно наблюдаемый
отказ команды. Все признаки `functional_acceptance`, `full_workload_acceptance`,
`resource_acceptance`, `capacity_acceptance`, `production_acceptance` всегда ложны;
артефакт не передаётся функциональному collector. Три быстрые команды означают только,
что проблема здесь не воспроизвелась. Быстрый `/bin/true` и медленные Python-команды
указывают на различие путей, но не доказывают причину. Другой runner, фиксированный
порядок, кеши и отсутствие девяти ролей не позволяют установить причину прошлого отказа
или мощность рабочего сервера.


## Отдельный опыт с импортами в cgroup disk

Опциональная задача `import_control` использует тот же проверенный PR marker
`<!-- signoz-disk-component: run -->`, отдельный [модуль](../../scripts/observability-signoz-import-control/control.py),
собственные тесты и артефакт `signoz-import-control`. Она не заменяет исходные три
последовательных случая disk component и не передаёт результат функциональному collector.

После прежней подготовки двух ролей выполняется ровно один настоящий `vm_sample`
без дополнительной нагрузки и один с параллельным конечным импортом `inside` и
`functional_witness` в том же disk cgroup. Их функции не вызываются, backend, HTTP,
bootstrap, ключи и ingestion не используются. Сохраняются disk 0.1 CPU/96 MiB,
семь volumes, одна сеть, прежние проверки исходников, образа, владельца и свободного
места, а также внешние пределы фаз 180/60/90 секунд и конечный замер 3 секунды.

Только внутри этого опыта ограниченный CPython profiler читает существующие локальные
переменные выбранного `Engine.raw` при выходе. Он не меняет исходный helper или Engine
и восстанавливает прежний profiler; ошибки наблюдения дают неизвестный результат.
Полное окно 3 секунды и остаток внешнего времени проверяются после фактического
preflight. Короткое или неполное окно означает `not_run`, не сравнимый отказ.

Пересечение интервала импортов с полным окном native Docker exec подтверждается
только при совпадении проверенных clock basis и неизменной генерации контейнера.
Это не доказательство одновременного исполнения Python bytecode. Host PID импортера
не подтверждается; его собственная идентичность проверяется только внутри actor.
Идентификаторы, пути, PID, аргументы, body и ошибки не копируются в публичный результат.
Если импорты закончились раньше, данные отсутствуют или проверка не прошла, результат
неизвестен. Повтор пары, искусственное удержание импортера и увеличение лимитов запрещены.

Остановка своего CLI и join потока не доказывают остановку удалённого actor.
Окончательная проверенная очистка ровно двух контейнеров, семи volumes и одной сети
обязательна. Все признаки functional/resource/capacity/production acceptance ложны.
Локальный Darwin/arm64 отклоняется прежней native-проверкой; реальный парный опыт
выполняется только на проверенном Linux amd64 после ревью исходников.
