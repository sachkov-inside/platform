# Необязательная аналитика браузера

Реализация #1566 находится в `apps/web/src/features/storage-notice`. Она заменяет существующее
уведомление единым выбором cookies и аналитики только после разрешённой активации. Вход и покупка
не запрашивают второй выбор. Отказ не меняет доступ к продукту. Техническая Web telemetry
ошибок и vitals имеет собственный действующий путь и этим выключателем не управляется.

## Выключенное состояние и будущая активация

По умолчанию приём выключен. Для включения одновременно нужны:

- `INSIDE_ANALYTICS_ENABLED=true`;
- `INSIDE_ANALYTICS_LEGAL_REVISION`, совпадающий с текущей опубликованной редакцией cookies
  в `@inside/legal`, не ниже редакции 3;
- `INSIDE_UMAMI_ENDPOINT=http://umami-ingest:3000/api/send`, никакой иной адрес не принимается;
- `INSIDE_UMAMI_WEBSITE_ID`, UUID настоящего сайта в собственном Umami;
- `INSIDE_ANALYTICS_PSEUDONYM_SECRET`, серверный секрет длиной 32–256 символов.

Действующая редакция cookies сейчас 2. Переменные окружения сами по себе её не заменяют и
не разрешают включение. [Проект дополнений](../legal/observability-analytics_DRAFT.md) не опубликован.
Перед активацией владелец принимает полные legal-редакции, пользовательский путь и визуальный вид,
а отдельный production rollout проходит действующие разрешения и проверки. Preview не включает сбор
на действующем сайте. Секрет нельзя помещать в `NEXT_PUBLIC_*`, логи или issue.

Смена секрета разрывает сопоставимость псевдонимов Account. Обновление
секрета требует отдельного операционного решения, а не незаметного действия при подготовке.

## Что отправляется и как это читается

`AnalyticsObservation` стоит в настоящих представлениях Product, доступного Material, ограничения
доступа и страницы покупки. Он наблюдает видимое состояние после рендера в браузере. RSC и prefetch
ничего не отправляют. Повторная доставка доменных событий, оплаты и права не выводятся из этих
наблюдений. Источники подтверждённых действий остаются у владельцев домена.

Браузер передаёт только закрытый вид события, UUID Product/Material из presentation-модели и
проверенные коды источника/кампании. При неизвестном ID представление пропускает наблюдение,
а не подставляет slug. Сервер проверяет schema, Origin, JSON и предел 1 KiB через общий
`handleOptionalMutationOperation`, затем получает текущий Account из доверенной сессии.

Сервер читает свежую bounded reference по одному UUID у Content Library. Владелец использует
ProductDirectory для reader visibility и PublishedMaterialSelection + ContentAccess для Material.
Непубликовавшийся, неизвестный или скрытый объект не экспортируется; недоступное тело нельзя
сообщить как `material_view`. Проекция ограничения остаётся наблюдением браузера, а не фактом
выдачи доступа. Узкие HTTP reads `library/products/by-id/<UUID>/reference` и
`library/materials/by-id/<UUID>/reference` возвращают только kind, UUID и availability, без тела.

В native Umami поступает один PageView. Вместо slug адрес содержит подтверждённый публичный
UUID Product или Material. Две сущности дают разные адреса; показ ограничения и переход
к покупке имеют свои виды пути. Эти business IDs позволяют сопоставить статистику с названиями
через существующий каталог владельца. Названия в Umami не отправляются. Account использует
серверный HMAC; исходный Account ID в native хранилище не передаётся.

Сервер заново составляет только native `utm_source` (код кампании) и `utm_medium` (код источника
перехода). Допускаются `direct`, `inside`, `telegram`, `newsletter`, `unknown`. Все исходные
query/hash, рекламные click IDs, title, slug и свободные URL/referrer удаляются до отправки.
Это синтетические параметры из закрытого списка, а не копия исходной строки запроса.
Существующий bounded read `/api/websites/<website>/events` показывает `urlPath` и `urlQuery`:
агент различает сущности и читает эти коды без нового endpoint или расширения query-прав.
Native PageViews не удваиваются вторым custom event. Поля и PageView-модель сверены с
[pinned Umami 3.4.0 native events query](https://github.com/umami-software/umami/blob/ec0ff50388c264ed8ce46f00967e92f7e71476ae/src/queries/sql/events/getWebsiteEvents.ts).

Текущий trusted ingress resolver общий с rate limit. Native detector временно получает его IP-ключ
и ограниченный User-Agent только по private сети. IPv6 укрупняется до /64; native геолокация
для такого ключа неизвестна. Прямой доступ к Web в обход доверенного ingress не является
поддерживаемой production-топологией. Исходные заголовки не попадают в application logs или ответы.

## Выбор, отказ и неполнота

localStorage `inside.analytics-choice.v1` содержит только редакцию и `necessary`/`allowed`.
Нового browser visitor ID, cookie или Umami cache token нет. Настройки доступны в подвале без
входа. Изменение действует в текущей и других открытых вкладках. При отзыве новые отправки
останавливаются, текущие browser requests отменяются. Уже принятый сервером запрос невозможно
отозвать через AbortSignal. При ошибке сохранения действует запрет в памяти, старый выбор
удаляется по возможности; аналитика в текущем документе остаётся выключенной.

Одновременно выполняются не более четырёх optional reports, browser budget составляет 2 секунды,
native export budget 1 секунду. Очереди и повторных отправок нет. Отказ, блокировщики, исчерпание
лимита и потеря доставки делают статистику неполной. Эти данные не служат доказательством оплаты,
доступа или полного числа действий.

## Проверка до production

Focused module, Chromium и Storybook сценарии проверяют выключенное состояние, равные кнопки,
сохранение выбора, отзыв между вкладками, недоступное хранилище, смену Account, ограничения тела
и приватность payload. Storybook proof требует принятия владельцем; временная семантическая
реализация помечена #1566 и сама по себе принятой визуальной работой не объявляется.

Workflow `observability-browser-analytics.yml` запускает отдельный synthetic native proof на Linux.
Он использует существующий внешний Umami supervisor, его приватный query service и отдельный
синтетический сайт той же reader team. Chromium проходит реальный выбор и общий Web handler;
каталог и сессии представлены явно синтетическими портами, а native transport теста направлен через owned query service к настоящему pinned Umami.
Сессия и принятая редакция в этом synthetic корпусе подменены явно, production gate не обходится.
Существующий read-only gateway должен вернуть по одному PageView двух Product и двух Material
с разными проверенными UUID в адресах и закрытыми native UTM-кодами, без sentinel URL/PII. Затем
два синтетических Account и выход должны дать разные native session IDs без raw Account ID. Отзыв
проверяется до следующего browser наблюдения. Старый native MCP/count corpus использует другой
сайт, поэтому его ожидаемое количество не меняется.

Этот proof не создаёт отдельные Docker resources или ingest ports: все контейнеры принадлежат
внешнему pilot lifecycle. Приватные входы и Vitest log остаются внутри private directory;
публикуется только `browser-analytics-proof.json` вместе с source/cleanup evidence. Поле
`last_completed` содержит только последний завершённый этап из закрытого перечня: запуск теста,
готовность listener, видимый выбор, отправку наблюдений, проверку native событий, смену сессии
и отзыв. Если тест не начался или файл этапов непригоден, это указано отдельно. Тексты ошибок,
стек, private body и ключ reader в это поле не попадают. Успех CI
не заменяет проверку production ingress, визуальное принятие, legal-публикацию, ресурсную
приёмку, очистку и production rollout. Pending native CI нельзя описывать как выполненный proof.
