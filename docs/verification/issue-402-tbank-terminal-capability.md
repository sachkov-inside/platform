# Терминалы Т-Банка и касса Inside: что подтверждено

Дата проверки: 11.09.2026.
Задача: [Platform #402](https://github.com/sachkov-inside/platform/issues/402).
Ответственный за доступ к кабинету и решения о терминале — владелец; за вызовы API и запись
результата — агент задачи.

Магазин: отдельный магазин Inside. Решение владельца от 11.09.2026. Магазин SachkovLearn не
используется: согласия покупателей и сохранённые привязки карт другого продукта не переносятся,
и namespace `CustomerKey` у Inside свой.

Обозначения: **да** — подтверждено проверкой; **нет** — выключено или непригодно; **?** —
неизвестно, нужен отдельный шаг. Ключи, пароли и полные идентификаторы терминалов сюда не
попадают. Проверка выполнялась на тестовом терминале; рабочий терминал не трогали.

## Что именно проверяли

Прямые вызовы платёжного API от имени тестового терминала и один полный карточный путь:
покупка с сохранением привязки, затем продление по этой привязке, затем полный возврат.
Оплату на форме банка проводил владелец тестовой картой банка.

Владелец 11.09.2026 разрешил вызовы к API тестового терминала и сам обратился в поддержку кассы.
Он же решил разместить корневой сертификат в репозитории сразу, а после проверки — ограничить
доверие к нему одними вызовами банка. Поэтому задача сбора фактов несёт и эту правку среды.
Рабочий терминал, его настройки и реальные списания в проверку не входили. Приложение Inside в этой
проверке не участвовало — связка с ним относится к
[#413](https://github.com/sachkov-inside/platform/issues/413).

## Платёжное API

| Возможность | Статус | Чем подтверждено |
|---|---|---|
| Одностадийная оплата, `PayType=O` | да | запрос принят, выдана форма банка |
| Оплата картой до конца | да | статус `CONFIRMED`, источник `cards` |
| Сохранение привязки при `Recurrent=Y` | да | привязка активна, получен `RebillId` |
| Продление по привязке, `Charge` | да | статус `CONFIRMED` без участия покупателя |
| Полный возврат, `Cancel` | да | статус `REFUNDED`, остаток `0` |
| Чек в запросе, объект `Receipt` | да | принят с `usn_income`, `none`, `full_payment`, `service` |
| Разовая покупка без сохранения привязки | да | оплата и возврат прошли на платеже без `Recurrent` |
| Смена платёжного средства | частично | форма привязки выдаётся, завершение привязки не проверялось |
| `GetState` | да | вернул статус операции |
| `GetCardList` | да | вернул привязку, её состояние и `RebillId` |
| `AddCard` с `3DS`, `3DSHOLD`, `HOLD` | да | выдан `RequestKey` и форма привязки |
| `AddCard` с `CheckType=NO` | нет | запрос принимается, но `RebillId` по нему не приходит |
| Подпись запроса `Init` | да | банк отметил токен как верный |
| Признак родительской операции `OperationInitiatorType=1` | да | зафиксирован банком по оплаченному платежу |
| Автосписания на рабочем терминале | ? | тестовый контур ничего не доказывает о рабочем |
| СБП с привязкой счёта | не нужен сейчас | СБП выключен на магазине |

Приём запроса с `Recurrent=Y` сам по себе ничего не доказывает: возможность подтверждается только
выдачей `RebillId` по фактически оплаченному родительскому платежу. Здесь она подтверждена
именно так.

`RebillId` удалось получить методом `GetCardList`, а не только из уведомления банка. Это
существенно, потому что канал уведомлений на терминале сейчас выключен. Как запасной путь
восстановления привязки он проверен и работает; единственным путём его делать не следует.

## Онлайн-касса

| Что | Статус | Источник |
|---|---|---|
| Провайдер | CloudKassir | экран «Онлайн-касса» |
| Состояние | подключено | экран «Онлайн-касса» |
| Формат чека | ФФД 1.2 | экран «Онлайн-касса», карточка регистрации ККТ |
| Касса зарегистрирована | да | статус «Включена», есть отчёт о фискализации |
| Оператор фискальных данных | Платформа ОФД | карточка регистрации ККТ |
| Режим «расчёты только в интернете» | включён | карточка регистрации ККТ |
| Отдельная касса для Inside | не нужна | ответ поддержки кассы от 11.09.2026 |
| Место расчётов в регистрации ККТ | ? | указан домен SachkovLearn, не домен Inside |
| Система налогообложения | да | УСН «Доходы» 6%, совпадает с `usn_income` в запросе |
| Ставка НДС | да | «без НДС» согласуется с УСН «Доходы» и полем `none` |
| Признаки `full_payment` и `service` для подписки | ? | банк их принял, соответствие продукту не подтверждено |
| Признаки расчёта для разовой покупки руководства | ? | в кабинете подтверждена только позиция подписки |
| Состав продажи и ставка в кабинете | да | позиция «Подписка Материалы, 1 месяц», 1 000 ₽, без НДС |
| Формирование чека продажи | да | тест банка «Формирование чека» пройден |
| Формирование чека возврата | да | тест банка «Формирование чека возврата» пройден |

Приложение передаёт контакт покупателя в `Receipt.Email`. Оно отправляет `usn_income` и «без НДС»,
что совпадает с действующей системой налогообложения: УСН «Доходы» 6% с 21.07.2024. Если у ИП
появится обязанность по НДС, поле `receipt.tax` придётся менять вместе с ценами; сейчас такой
обязанности из проверенных источников не следует. Кабинет показывает именно эту позицию и ставку.
Банк засчитал собственные тесты формирования чека продажи и чека возврата на том составе
`Receipt`, который отправляет приложение.
Это проверка тестового контура: она подтверждает формат и приём чека, но не заменяет проверку
настроек кассы для реальных продаж.

### Место расчётов в регистрации ККТ

Касса зарегистрирована с местом расчётов на домене SachkovLearn, тогда как магазин Inside и его
терминал работают на собственном домене.

Поддержка кассы 11.09.2026 подтвердила, что при смене сайта, принимающего платежи, регистрировать
новую кассу не нужно и можно использовать существующую. Вопрос был именно о новой кассе, поэтому
остаётся уточнить отдельно: нужно ли обновлять место расчётов в карточке ККТ, чтобы чеки Inside
не уходили с адресом другого продукта. На тестовом контуре расхождение ничему не мешало, и
пройденные тесты формирования чека его не обнаруживают.

## Способы оплаты и ограничения суммы

Магазин Inside заявлен как информационно-консультационные услуги на собственном домене.

| Способ на платёжной форме | Состояние | Годится для автопродления |
|---|---|---|
| Банковская карта | в форме по умолчанию | да, проверено |
| T-Pay | в форме по умолчанию | по описанию банка — по карточной схеме, не проверено |
| Mir Pay, только Android | включён | по общему описанию COF допускается, не проверено |
| SberPay | включён | не подтверждено |
| Долями | включён | не подтверждено |
| Система быстрых платежей | **выключена** | отдельный процесс привязки счёта |

| Ограничение | Значение |
|---|---|
| Разовая операция | 300 000 ₽ |
| Операции по карте в сутки | 300 000 ₽ |
| Суточный оборот | 5 000 000 ₽ |
| Разовая операция «Долями» | от 4 до 200 000 ₽ |

Верхняя граница разовой операции задаёт `maximumKopecks`: 30 000 000 копеек. Отдельной нижней
границы суммы платежа кабинет не показывает — значения «мин.» в тарифе это минимальная комиссия,
а не минимальный платёж. Поэтому `minimumKopecks` остаётся решением Inside, а не ограничением
банка; его назначает задача, включающая оплату.

### Не каждый способ на форме даёт привязку для продления

Конфигурация приложения требует подтверждения `cardOnlyHostedConfirmed`: форма показывает только
те способы, которые дают сохранённую привязку. Сейчас это не так — на форме включены Долями,
SberPay и Mir Pay. Проверенный путь автопродления есть только у карты.

Риск конкретный: покупатель оформляет подписку способом без привязки, первый платёж проходит,
а списать продление нечем. До продаж подписки нужно либо оставить на форме только способы с
доказанной привязкой, либо доказать привязку для каждого включённого способа. На разовую покупку
руководства это не влияет: там привязка не нужна.

## Уведомления и возврат покупателя

| Что | Статус | Источник |
|---|---|---|
| Уведомления по HTTP на тестовом терминале | **выключены** | экран настройки терминала |
| Уведомления на почту на тестовом терминале | **выключены** | экран настройки терминала |
| Страницы успеха и ошибки | банковские по умолчанию | экран настройки терминала |
| Доставка обратного вызова до приложения | ? | нужен включённый канал и адрес по HTTPS |

Приложение передаёт свои `SuccessURL`, `FailURL` и `NotificationURL` в каждом запросе `Init`,
поэтому банковские страницы по умолчанию помехой не являются. Выключенный канал уведомлений —
риск другого рода: без него подтверждение оплаты остаётся только за сверкой через `GetState`
и `CheckOrder`, а привязка восстанавливается через `GetCardList`.

## Среда выполнения

Вызов банка не проходил проверку сертификата: цепочка Т-Банка заканчивается корнем УЦ Минцифры,
которого нет ни во встроенном хранилище Node, ни в образе backend. Проверено, что официальный
корень совпадает по отпечатку с тем, что предъявляет банк, и что с ним вызов проходит из обоих
образов backend. Корень подключается только к клиенту банка, поэтому остальные исходящие
соединения приложения его не получают.

Контракт и отпечаток описаны один раз в
[конфигурации среды](../runbooks/runtime-configuration.md).

## Как передать конфигурацию безопасно

Приложение читает настройки банка из двух переменных среды и ничего не хранит в репозитории:

- `TBANK_CONFIG_JSON` — окружение, ключ и пароль терминала, ключ шифрования привязок, границы
  суммы, адреса возврата и уведомления, параметры чека.
  Схема — `apps/backend/src/config/tbank-config.ts`.
- `TBANK_CA_FILE` — путь к корневому сертификату для соединений с банком; его контракт описан
  в [конфигурации среды](../runbooks/runtime-configuration.md).

Правила обращения с ними:

- ключи и пароли терминала хранятся и доставляются тем же порядком, что остальные секреты
  Platform: зашифрованный файл окружения по процедуре
  [подготовки секретов](../../infra/production/secrets/README.md), расшифровка только на хосте.
  Репозиторий, задачи, переписка и журналы их не содержат; приложение не пишет конфигурацию
  и привязки в лог;
- тестовое и рабочее окружения получают разные значения и никогда не делят одну базу данных:
  привязка карты, выданная на тестовом терминале, недействительна на рабочем и наоборот;
- `bindingEncryptionKey` — 32 случайных байта в base64, свой для каждого окружения. Он нужен и для
  восстановления сохранённых привязок, поэтому теряется вместе с возможностью продлевать подписки;
- адрес уведомления и адрес возврата — только HTTPS. Адрес возврата ведёт на страницу, которая
  спрашивает состояние покупки у сервера и не считает сам возврат покупателя доказательством оплаты;
- на локальном стенде адрес уведомления даёт временный HTTPS-туннель до
  `POST /billing/tbank/notification`; его адрес живёт только в среде стенда.

## План проверки на тестовом контуре

Что ещё нужно настроить до сквозного прогона
[#413](https://github.com/sachkov-inside/platform/issues/413):

1. включить канал уведомлений по HTTP на тестовом терминале и указать адрес туннеля;
2. решить состав способов на платёжной форме;
3. выдать стенду `TBANK_CONFIG_JSON` тестового терминала и `TBANK_CA_FILE`.

Сценарии, которые должен пройти сам прогон:

- покупка подписки каждого тарифа: оплата, выдача прав, доступ к материалам;
- разовая покупка руководства и доступ к нему;
- продление по сохранённой привязке и его отмена;
- смена платёжного средства;
- отказ банка, потерянный ответ и восстановление сверкой;
- возврат и снятие прав;
- повторная доставка уведомления и отсутствие двойной выдачи прав.

Тестовый контур не доказывает готовность рабочего терминала: она остаётся за
[#414](https://github.com/sachkov-inside/platform/issues/414).

## Что осталось снять

Пункты 1–3 закрывает владелец: они требуют кабинета кассы, банка или коммерческого решения.
Пункт 4 закрывает агент задачи вместе с настройкой стенда, пункт 5 — отдельная задача.

1. Место расчётов в регистрации ККТ: подтвердить у кассы, нужно ли обновлять адрес в карточке.
2. Состав способов на платёжной форме: оставить только способы с доказанной привязкой либо
   доказать привязку для включённых.
3. Канал уведомлений по HTTP: включить на тестовом терминале и проверить доставку до приложения.
4. Автосписания и касса рабочего терминала. Готовность к реальным продажам из тестового контура
   не выводится и остаётся за [#414](https://github.com/sachkov-inside/platform/issues/414).

## Границы

Проверка выполнена только на тестовом терминале и только по карточному пути. Рабочий терминал,
его настройки и реальные списания не затрагивались. Сквозной сценарий в самом приложении,
включая выдачу прав доступа после оплаты, сюда не входит и остаётся за
[#413](https://github.com/sachkov-inside/platform/issues/413).
