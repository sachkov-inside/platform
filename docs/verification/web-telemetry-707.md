## Storage and query procedure

`pnpm telemetry:measure` fills 600,000 metrics and 150,000 errors. Each error message contains
500 four-byte Unicode code points, 2,000 UTF-8 bytes, generated by xorshift seed 707 from
U+1F300–U+1FAFF. The 1,024-message corpus varies characters within each message. PostgreSQL does
not deduplicate messages across rows. This is the diverse corpus accepted by the coordinator,
not a proof over every possible combination of message, digest and name.

The fixture uses the longest current route template, distinct 32-character digests, `Error` names,
three p75 metric kinds and both device classes. Subsequent days call the actual `record_vital`
and `record_error` routines, including quota and coverage updates. Each cycle inserts one day's
quota and deletes samples older than 30 days. Thirty-two cycles replace the entire original set.

Size sums tables, their indexes/TOAST, materialized relations and the route identity sequence.
Each cycle records size before cleanup, after cleanup and after ordinary VACUUM. No VACUUM FULL,
REINDEX, LZ4, byte cap or global PostgreSQL setting change occurs. Ordinary checkpoints model a
real day's WAL maintenance. The schema measurement does not include WAL, database-wide catalogs
or backup copies. Files retain ordinary index/table bloat and reusable pages; vacuum may truncate
empty tail pages, as in normal operation.

Before timing, the query adapter runs against an empty date window. It does not read the corpus.
Eight initial summaries and one after each maintenance cycle measure the actual summary p75 SQL.
The maximum is the largest of these 40 measurements. Full summary timings include separate error
and coverage queries; the 200 ms criterion applies to the p75 query.

## API memory and collection latency

API RSS compares compiled `origin/main` (`bc94bf20`) with the merged feature (`e96cc8ed`). Each of
three paired runs uses separate fresh migrated databases and processes. Both processes warm the
same public catalogue endpoint 100 times, then receive 1,000 alternating vital/error reports.
The old API returns 404; the new API stores them. Both perform GC before RSS sampling. The medians
are 388,169,728 and 396,394,496 bytes. Warming a database-backed endpoint initializes the same
existing Prisma query engine in both versions; a health-only baseline would omit that cost.

Collection timings compare handlers against `05959055`, using 100 preparation calls and 500
measured calls. The Next `after` callback is captured and transport is excluded from response
latency. This measures the synchronous collection increment; it is not a browser/network percentile.
Browser collection code is unchanged. Separate forwarding tests verify response-before-persistence
and preservation of the original log when transport fails. Full-stack verification exercises the
real web/API transport.

## Delivery boundary

The migration changes exact schema identity. The release contract requires repair forward after
migration; it does not allow the previous application release as rollback. Production Compose
smoke verifies fresh/prefix upgrades, frozen N-1 queries and runtime readiness.

The orchestrator owns merge and release. After deployment, production acceptance still checks
available server memory of at least 1 GiB, ingestion, retention completion and the read-only MCP
summary. The full monitoring stack remains #1289.
