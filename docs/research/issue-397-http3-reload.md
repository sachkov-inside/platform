# Почему зависал HTTP/3 на странице авторизации

Дата проверки: 2026-09-08. Задача: [#397](https://github.com/sachkov-inside/platform/issues/397).
Предшествующее восстановление доступности: [#387](https://github.com/sachkov-inside/platform/issues/387).

Это отчёт об исследовании до обновления production. Последующее исправление и возврат
HTTP/3 выполнены в [#399](issue-399-caddy-upgrade.md); там записаны итоговые проверки
и приёмка владельца. Текущая конфигурация и порядок обновления принадлежат
[production runbook](../runbooks/production-foundation.md#обновление-пакета-caddy-на-работающем-сервере).

## Вывод

Установленная Caddy из Ubuntu (`2.6.2-14`) теряет первый HTTP/3-запрос после reload
конфигурации. Это воспроизведено на том же сервере через loopback, с синтетическим
сертификатом и статическим ответом: без внешней сети, VPN, Logto и Telegram.
HTTP/2 в той же последовательности продолжает отвечать.

Причина локализована в сочетании старой Caddy и обновлённой библиотеки quic-go в
дистрибутивном пакете. Наиболее точно механизм объясняет отсутствующая доработка
закрытия QUIC listener из upstream Caddy #7177: после reload старый обработчик
остаётся ждать соединение и может забрать запрос, который уже не обслужит.
Это вывод из воспроизведения, сравнения сборок и исходников; отдельную сборку
Ubuntu с единственным перенесённым исправлением в этом исследовании не собирали.

Отключение HTTP/3 в #387 обходит неисправный путь и является обоснованной мерой
восстановления доступности. Оно не исправляет дефект установленной сборки.
Для устранения причины было рекомендовано отдельно обновить Caddy на проверенную
актуальную официальную сборку, сохранив HTTP/3 выключенным до проверки после деплоя.

## Наблюдения и контрольные опыты

Рабочая Caddy на момент исследования: `/usr/bin/caddy`, пакет Ubuntu `2.6.2-14`, Go `1.25.0`, amd64.
Версия приложения из `caddy version` — `2.6.2`; она не отражает перенесённые
изменения зависимостей дистрибутива. Точная версия встроенной quic-go отсутствует
в доступном build-info, поэтому по одному номеру Caddy её не утверждаем.

Изолированные процессы слушали только `127.0.0.1:19443` (TCP/UDP) и
`127.0.0.1:19419` (admin). Каждый использовал отдельные config/data и сертификат
для `probe.test` / `other.test`. Запросы проверяли этот сертификат, обходили proxy
и DNS через `RESOLVE`; публичные сертификаты и ключи не использовались.

Клиент: Python 3.14, `curl_cffi==0.16.3`. Принудительный `v3only` исключает скрытый
переход на HTTP/2. Успех требовал HTTP 200, фактический `V3` и актуальное тело
`reloadN HTTP/3.0`. Контрольный `v2` требовал `V2_0` и соответствующее тело.

| Сборка | До reload | После двух reload | Изоляция клиента |
|---|---|---|---|
| Ubuntu `2.6.2-14`, первоначальный опыт | H2/H3: 200 | Первый H3 после каждого reload: timeout, 0 bytes; следующий: 200 | Новый requests session |
| Ubuntu `2.6.2-14`, повтор | H2/H3: 200 | 2/8 H3 timeout: первый после каждого reload; все H2: 200 | Новый Python-процесс на каждый запрос |
| Ubuntu `2.6.2-14`, повтор с диагностикой | H2/H3: 200 | Те же 2/8 H3 timeout; все H2: 200 | Новый Python-процесс |
| Официальная `2.6.2` | H2/H3: 200 | Все 4 H3 и 4 H2: 200 | Новый requests session |
| Официальная `2.10.0` | H2/H3: 200 | Все 8 H3 и 8 H2: 200 | Новый Python-процесс |
| Официальная `2.10.1` | H2/H3: 200 | Все 8 H3 и 8 H2: 200 | Новый Python-процесс |
| Официальная `2.11.4` | H2/H3: 200 | Все 8 H3 и 8 H2: 200 | Новый Python-процесс |

Каждый timeout ограничен клиентом тремя секундами: это порог теста, а не измерение
максимальной длительности зависания. В первоначальном опыте успешные H3-запросы
занимали единицы миллисекунд. В опытах с новым процессом время включает запуск Python.

Первоначально успешный второй запрос шёл на другое имя. Повтор с одним `probe.test`
показал, что определяющим является первый запрос после reload, а не имя домена.
Старые browser cookies, TLS sessions и кеш клиента для воспроизведения не нужны.

## Механизм и первичные источники

В [исходном пакете Ubuntu `2.6.2-14`](https://archive.ubuntu.com/ubuntu/pool/universe/c/caddy/caddy_2.6.2-14.debian.tar.xz):

- `debian/control` требует `golang-github-quic-go-quic-go-dev (>= 0.53)`;
- patches `0007-quic-go-0.50.0.patch` и `0009-quic-go-0.53.0.patch` адаптируют старый
  код к новым интерфейсам библиотеки;
- остановка HTTP/3 по-прежнему опирается на `server.h3server.Close()` без отдельного
  закрытия возвращённого Caddy QUIC listener; соответствующего переноса #7177 нет.

Начиная с [quic-go 0.52](https://github.com/quic-go/quic-go/releases/tag/v0.52.0),
HTTP/3 server больше не закрывает listener, переданный приложением через
`ServeListener`: этим должно заниматься само приложение. Изменение внесено в
[quic-go #5129](https://github.com/quic-go/quic-go/pull/5129).

Разработчики Caddy описали оставшееся старое предположение в
[Caddy #7172](https://github.com/caddyserver/caddy/issues/7172) и исправили его в
[#7177](https://github.com/caddyserver/caddy/pull/7177), commit
`7590c9ca1ba6096408574a7dd3b9dc42d12cb948`: Caddy сохраняет QUIC listeners и явно
закрывает при остановке сначала приём соединений, затем underlying packet connections.
Исправление включено в [релиз 2.10.1](https://github.com/caddyserver/caddy/releases/tag/v2.10.1).

При reload старый HTTP server останавливается, а listener переиспользуется новым.
В [Caddy 2.6.2 `fakeCloseQuicListener.Accept`](https://github.com/caddyserver/caddy/blob/v2.6.2/listeners.go#L571)
переданный контекст игнорируется: ожидание использует собственный контекст listener,
отменяемый только его `Close()`. В
[quic-go 0.53 `serveListener`](https://github.com/quic-go/quic-go/blob/v0.53.0/http3/server.go#L289)
после `Accept` проверяется уже отменённый контекст старого HTTP server: функция
возвращается до запуска обработчика принятого соединения. Вместе эти два участка
объясняют потерю первого запроса после reload и успех последующих.
Без согласованного завершения старого приёма получается соединение с успешным QUIC/TLS,
но без HTTP-ответа. Это согласуется с прежним внешним наблюдением на auth: handshake
проходит, GET отправлен, ответ не приходит. Отличие Ubuntu от официальной 2.6.2
показывает, почему объяснения только возрастом Caddy недостаточно.

Другая известная ошибка — устаревшая TLS-конфигурация после reload,
[#5517](https://github.com/caddyserver/caddy/pull/5517). Она не объясняет полученный
дифференциальный результат сама по себе: официальная 2.6.2 без этого исправления
проходит наш сценарий, а Ubuntu-сборка нет. Смена сертификата в тест не входила.

## Воспроизведение

Сценарий на каждом бинарном файле одинаков:

1. Запустить отдельную Caddy с одним HTTPS server на loopback, протоколами `h1/h2/h3`,
   явно загруженным синтетическим сертификатом, выключенным automatic HTTPS и
   `static_response` с телом `probe {http.request.proto}`.
2. Дважды запросить H2 и H3, проверив статус, протокол и тело.
3. Изменить только тело на `reload0 {http.request.proto}` и отправить конфигурацию
   в admin `POST /load` с `Content-Type: application/json`.
4. Четырежды последовательно запросить H2, затем H3. Каждый запрос запускается в новом
   Python-процессе; `timeout=3`, `NOPROXY=*`, `RESOLVE=probe.test:19443:127.0.0.1`.
5. Повторить пункты 3–4 с `reload1`, затем завершить только тестовый процесс.

Команда, давшая воспроизведение на Ubuntu:

```sh
PYTHONPATH=/var/lib/inside/verification/http3-397/python \
  python3 /var/lib/inside/verification/http3-397/fresh-client-probe.py \
  /usr/bin/caddy ubuntu-fresh-client
```

Сигнал ошибки из сохранённого результата:

```text
reload-0-attempt-0 v2     200 V2_0 reload0 HTTP/2.0
reload-0-attempt-0 v3only curl (28): timeout after 3002 ms, 0 bytes received
reload-0-attempt-1 v3only 200 V3 reload0 HTTP/3.0
reload-1-attempt-0 v3only curl (28): timeout after 3002 ms, 0 bytes received
```

Полные scripts, JSONL результатов, синтетические диагностические стеки и патчи
пакета сохранены в локальном архиве артефактов `inside/platform/issue-397-20260908`.
Рабочий каталог опыта на сервере после проверки удалён. Для повторения нужно
восстановить scripts, изолированно установить указанный клиент и создать новый
синтетический сертификат. Это исследовательский сценарий, не команда деплоя.

Официальные архивы загружены из GitHub Releases и сверены с опубликованными SHA-512.
Для 2.11.4 дополнительно проверен SHA-256 из GitHub asset metadata:
`527fbf917c39189a1e3b31d34fa955601680b2d5c8055d2a87b8b9588dec7bb9`.

## Что это означает для эксплуатации

На момент завершения исследования HTTP/3 оставался выключенным на публичном `:443`; рабочая Caddy во время исследования
не заменялась и не перезапускалась. PID `6356`, время запуска `2026-09-05 08:52:13 UTC`
сохранены. Контроль: foundation health успешен, auth возвращает ожидаемый redirect,
Inside — HTTP 200. SHA-256 рабочего Caddyfile после опытов:
`75ee8952a0691a15694d21b5c649632eed7c7e2d8dc50419a5d45b91202a3506`.

По результатам исследования был рекомендован отдельный шаг: подготовить обновление Caddy с закреплённой версией и
процедурой отката; проверить текущий конфиг и модули, запуск, повторные reload,
авторизацию и здоровье сервисов. Затем отдельно решать возврат HTTP/3 по результатам
внешних запросов и реального мобильного браузера с VPN и без него.

Loopback доказывает серверный дефект, независимый от блокировок в России. Он не
доказывает отсутствие дополнительных ограничений UDP/QUIC у конкретного оператора.
Разницу поведения с VPN можно объяснить другим выбором протокола, маршрутом или
повторной попыткой; точную причину для устройства владельца без его сетевой трассы
это исследование не устанавливает. Полный вход через Telegram в этих опытах не выполнялся.
