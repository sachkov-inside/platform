Актуальное продолжение от 21.10.2026: [вариант хранения и план решения](issue-1599-storage-decision-2026-10-21.md)

## Решение, которое требуется принять

Рабочая площадка уже находится в Амстердаме. Это не только внешний вход: там работают
приложения, Logto, PostgreSQL, RabbitMQ и обработчики Telegram. Новые данные записываются туда.
Доказанного исключения, позволяющего всю эту регистрацию и обработку при сборе данных граждан РФ
вести в зарубежных базах, исследование не установило. Добавление согласия или российского backup
после иностранной записи эту проблему не устраняет. Основание: статья 18(5), сопоставленная со
статьёй 6(1), и фактические маршруты ниже [L1]. Это вывод о применимости нормы к известным фактам,
а не судебная квалификация всех операций Inside.

Уточнение владельца 20.10.2026: перенос пользовательских приложений обратно в РФ не подходит
из-за доступности из VPN. Сохранение зарубежной пользовательской площадки является обязательным
условием выбора. Прежняя рекомендация варианта B не принята владельцем; ниже он оставлен
для сравнения, а не как согласованный план.

Основной кандидат для дальнейшей проверки: зарубежная пользовательская площадка и полноценный
российский контур сбора/обновления с ограниченной последующей обработкой в AMS (вариант C).
Доступ пользователя идёт к AMS; необходимые обращения к РФ выполняет наша серверная система.
Это требует нового прикладного разделения, проверки статьи 12, правовой оценки границы сбора
и технического доказательства последовательности. Нельзя обещать выполнение всех требований
только на основании схемы «сначала RU commit, затем AMS»: допустимость последующих конкретных
операций проверяется отдельно, включая логи, сессии, webhooks и уточнение данных.
Один российский прокси либо перенос только PostgreSQL при сохранении иностранных первых записей
не являются доказательством выполнения требований.

Важно исправить прежнее категоричное объяснение: статья 18(5) не требует сама по себе размещать
в РФ каждый HTTP endpoint, TLS termination или исполняемый процесс. Она ограничивает конкретные
операции при сборе с использованием зарубежных баз. Поэтому AMS frontend/backend с записью в
российский контур является предметом проектирования, а не автоматически запрещённой схемой.
На первом этапе C целесообразно проверять без полноценной зарубежной реплики персональных данных:
публичный runtime в AMS, авторитетные записи/обновления и необходимые хранилища в РФ. Удалённый
доступ к российской БД, отдельный российский сервис записи и расположение конкретных Logto/queue
компонентов сравниваются по операциям и задержкам. Память, кэши, swap, crash dumps, журналы и
retry buffers нельзя автоматически исключать из проверки словом «stateless».

             ↓

             ├→ файлы/аватары → Yandex Object Storage, ru-central1

             ├→ эквайринг → Т-Банк → касса/ОФД
             └→ Kinescope API

Браузер → Kinescope iframe/CDN (отдельный маршрут)
Обращения → Gmail оператора (отдельный маршрут)
MCP ответы → выбранный пользователем агент → возможный поставщик модели

Российские object storage и backup не меняют того, что новые записи аккаунтов, событий и
очередей сначала происходят в AMS. IP/VPN пользователя не используются как доказательство
гражданства. Для проекта проще сначала проектировать единый контролируемый маршрут всех
пользователей; возможное разделение по категориям субъектов потребует отдельного решения.

| Учебные сдачи | Пользователь или его агент → report JSON/text, note, repository URL/branch/commit в PG AMS | Проверка заданий по договору; автор/авторизованный клиент агента | Свободный текст может содержать лишние сведения; запрет чувствительных данных и минимизация; сроки и процесс удаления не подтверждены |

| Видео | Браузер → Kinescope iframe/CDN; сервер → API | Просмотр материалов; устройство/IP/время/источник у провайдера | По реальному договорному контуру и настройкам viewer analytics, не по домену `.io` |
| Ошибки и производительность | Браузер/сервер → Web stdout AMS до backend normalization; затем PG AMS | Работоспособность/безопасность; route, error name/message/digest, mobile, metrics | PG telemetry 30 дней; stdout отдельная копия. Нужны очистка свободного message и календарь журналов |

Для каждой строки рабочие PG/очереди/журналы в AMS могут создавать дополнительные копии в WAL,
backup, временных файлах, логах ошибок и административных экспортных файлах. Они входят в тот же
учёт. Хеш/fingerprint/opaque ID и шифрование не равны доказанному обезличиванию.

### Что проверено по защите и очистке на рабочем сервере

- PostgreSQL `ssl=off`; соединения с ним идут по внутренним сетям одного Docker host.
  Это не публично открытый PostgreSQL и не доказательство TLS между разными будущими площадками.
- `log_statement=none`, `log_min_duration_statement=-1`, `log_min_error_statement=error`,
  `log_parameter_max_length_on_error=0`. Полного журналирования запросов не включено; текст
  ошибочного SQL всё равно может попадать в stderr. Состав фактических журналов без чтения записей
  этим не установлен.
- Guest root disk имеет ext4, `lsblk` не показал LUKS/crypt mapper. Шифрование дисков на стороне
  провайдера и раздельное хранение ключей неизвестны. Из этого нельзя делать вывод «никакого
  шифрования у Timeweb нет». Отдельно проверить требования Telegram [P7].
- Host daemon default: `json-file`, 20m × 5. У существующих Platform/Logto/PG контейнеров
  `HostConfig.LogConfig.Config={}`; у Telegram явно 10m × 3. Поэтому нельзя выдавать настройку
  default за доказанную действующую ротацию каждого существующего контейнера. Активные журналы
  проверенных контейнеров пока меньше порога, наблюдаемой ротацией вопрос не разрешён.
- UFW активен: разрешены SSH, HTTP, HTTPS TCP/UDP. Некоторые host services слушают другие
  адреса/порты, но listener не равен публичной доступности через firewall. Внешняя повторная
  проверка всех административных портов в этой работе не выполнялась.
- В live Logto user sign-in включены email code и inside-telegram; email signup с verification.
  `privacy_policy_url` задан, `agree_to_terms_policy=Automatic`. Отдельное согласие нельзя
  доказать этим флагом: надо проверять конкретные экраны и журнал принятия.
- В checked-in custom access-token hook есть `inside_receipt_email` без явной audience-проверки.
  Но live `jwt.accessToken` config не содержит этой строки. Значит выдача этого claim в текущем
  MCP не доказана. Нужна синтетическая проверка hook/audience без вывода реальных токенов.
- Не подтверждён единый проверенный путь удаления аккаунта, связанных данных в двух приложениях,
  журналов и повторного применения удалений после восстановления. Отдельные cleanup существуют.
  Ручная процедура возможна; её исполнение нужно показать на синтетическом наборе.
- Read-only S3 metadata API для namespaces `public`, `protected`, `quarantine`: versioning
  не включено; `GetBucketLifecycleConfiguration` вернул `NoSuchLifecycleConfiguration` (404);
  `GetBucketEncryption` вернул `ServerSideEncryptionConfigurationNotFoundError` (404).
  Это отсутствие отдельных настроек, а не доказательство отсутствия заявленного провайдером
  шифрования физических носителей [P4]. `GetBucketLocation` вернул пустое значение; нельзя
  трактовать S3-compatible ответ по правилам AWS как доказательство размещения в США.
  Регион `ru-central1` установлен по live конфигурации и географии услуги Yandex.
  Удаление/orphan cleanup должны исполняться приложением; lifecycle не является запасной очисткой.
- Бакет PostgreSQL backup проверен тем же read-only API: versioning не включено,
  lifecycle отсутствует, отдельная bucket encryption configuration отсутствует. Полученный ACL
  не содержит group grants; это не полная проверка IAM/bucket policy и не доказательство всей
  модели доступа. Retention здесь обеспечивает pgBackRest, а не правило S3 lifecycle.

В [#856](https://github.com/sachkov-inside/platform/issues/856) есть сообщение владельца о подаче

сообщил, что отдельное трансграничное уведомление не подавалось. Эти два факта не смешиваются.

Подготовить следующие изменения после выбора фактической схемы:

До ожидания документов или нового переноса определить правовую квалификацию текущих операций
и временный режим. Если неправомерная обработка установлена, применяются сроки ст.21(3), а не
свободно выбранный владельцем срок реализации. Рассмотреть остановку соответствующих новых
регистраций/изменений либо законный маршрут их приёма, сохранив обязательные доказательства и
возможность безопасного перехода. Не выдавать будущее уведомление за разрешение продолжать
выявленную неправомерную операцию.

1. **Сведения оператора по ст.22.** Проверить октябрьскую подачу и её статус, затем дополнить
   фактические цели, наборы, основания, места баз/обработки, статус ИП, реквизиты и меры.
   При октябрьских изменениях срок по ч.7 ориентировочно 15.11.2026. Не подавать второе первое
   уведомление вместо изменения и не заявлять несуществующую российскую рабочую базу.
2. **Отдельное уведомление по ст.12.** Для реально установленных иностранных передач определить
   получателей/страны, собрать сведения ч.5, проверить ограничения и применимый порядок начала.
   Подготовить честные фактические даты. Поздняя подача не превращается в своевременную и не
   устраняет возможные прежние нарушения. Решение о продолжении конкретного потока до закрытия
   условий должно быть принято отдельно; не подменять его обещанием «потом уведомим».
3. **Новая редакция политики.** Существующую v4 не переписывать задним числом. Подготовить следующую
   редакцию с реальной инфраструктурой, получателями, странами, сроками/удалением, каналами связи
   и новыми доменами. Объём публичных технических деталей выбирать по необходимости, без секретов.
4. **Контакты и формы.** Если выбран российский ящик поддержки, сначала настроить маршрут,
   затем обновить контакты/формы, проверить отсутствие скрытой Gmail-пересылки и решить старую историю.
5. **Договоры.** Проверить Timeweb, Yandex, Kinescope и остальных по их фактическим ролям.
   Подготовить недостающие условия поручения, доступ/подрядчиков, удаление, инциденты и подтверждения.
6. **Экраны и доказательства.** Для операций на согласии проверить отдельное действие и его журнал.
   Для договора не добавлять ненужный общий чекбокс. Основание новой редакции и необходимость
   информирования/нового согласия определить по содержанию изменений, а не автоматически.
7. **Внутренние процедуры.** Установить лиц с доступом, сроки, обработку обращений, удаление и
   восстановление, инциденты. Ручной процесс допустим как кандидат, если он реально проверен.

Это перечень подготовительных действий. Готовая к отправке форма с неизвестными странами,
непроверенными адресами/основаниями или ложными сроками не подготовлена и не должна подаваться.

Сопоставимое прочитанное мотивированное постановление о российском малом операторе с нашей

Публичные подборки не дают числа всех операторов и проверок, поэтому нельзя честно вычислить
процент вероятности или сказать «маленьких не проверяют».

Прямой текст ст.13.11 КоАП в СПС, редакция 04.08.2026: ч.8 для юрлиц 1–6 млн рублей,
ч.9 повторно 6–18 млн; по примечанию 1 для этих частей ИП отвечает как юрлицо [L4].
Это источник текста закона на неофициальном хосте, граница первичной проверки отмечена.
Ч.10 про уведомление о намерении обработки предусматривает 100–300 тыс. для юрлиц, но
её нельзя автоматически назначать каждому отсутствующему трансграничному уведомлению без
разбора состава. Штрафы разных составов не складываются в прогноз наказания Inside.

Практическая оценка: игнорирование сохраняет известные несоответствия фактов документам и
необоснованную иностранную первую запись. Реальные пути обнаружения включают обращение
пользователя, проверку опубликованных форм/политики, запрос к оператору и хостеру. Это не
утверждение, что какой-либо из этих процессов уже начался. Защищаемая позиция строится на
реальных ограничениях обработки и доказательствах, а не на малой заметности.

Существующие HAProxy профили являются основой эксперимента B, но не готовой настройкой:

согласовать допустимые время открытия сайта/входа, долю успешных попыток, перечень сетей РФ/VPN,
восстановление и месячный бюджет. Сначала проверить правовые границы C, затем измерить его
на синтетическом стенде с теми же TLS/SNI и маршрутами. Если C не проходит правовую или сетевую
проверку, сравнить D и другие конкретные границы, не возвращаясь автоматически к отклонённому B.
Числа задержек и смета без
измерений/тарифов здесь не выдумываются. Прежние 37/38 сетевых проверок текущей AMS не являются

### Испытания выбранной схемы

Использовать изолированные стенды, точные image/source и синтетические данные; внешние
почту/Telegram/банк/S3 заменить управляемыми тестовыми получателями. Не проводить отказные
эксперименты с реальными людьми на production. Записывать operation ID, destination, commit/ack,
наличие marker и outcome, без токенов и настоящих данных.

| Сценарий | Проверка и критерий |
| --- | --- |
| Email signup/sign-in/refresh | Учесть Logto verification/user/audit до Platform Account; отдельно SMTP и BFF/session. В C доказать RU commit/ack до разрешённой зарубежной записи |
| Telegram без аккаунта | `/start`, обычное сообщение, callback, linking; webhook inbox/contact не обходят границу, payload очищается в определённый срок |
| Checkout/contact/recurring/refund | Fake bank и webhook, повтор/утрата ответа; правильные contact snapshots, inbox и отсутствие непредусмотренных копий |
| MCP grant/refresh/submission | Audience, TTL, набор имён claims, получатель; только свои сдачи; email claim проверять синтетически без вывода JWT |
| Avatar/assets | Metadata/object order, частичный отказ, orphan cleanup, версии объектов и удаление |
| Telemetry/tracking | Гость/пользователь/error/path markers; раздельно проверить web stdout, PG и Telegram tracking. Backend normalization не должна оставлять сырой marker в stdout |
| Outbox/broker/inbox/quarantine | Stop consumer, потеря confirm, replay/invalid message; учесть PG и RabbitMQ copies, ограничение quarantine и очистку |
| Отказ RU | В C все операции, требующие RU-first, отказывают до AMS записи/отправки. Нельзя сохранять в AMS «пока Россия недоступна» |
| Обход маршрута | Прямой AMS IP с верным SNI, auth, Telegram/банк webhook, MCP, внутренние URL; правило не зависит от DNS/GeoIP/VPN |
| Удаление + restore + replay | Удалить marker, восстановить backup до удаления, replay событий. До traffic применены удаления/ограничения; marker не возвращается в выдачу, файл и рассылку |
| Сети и recovery | Матрица нужных РФ/VPN, мобильных/домашних сетей и отказ каждой площадки; измерены TLS/login/операции и восстановление относительно принятых критериев |

Для C одних timestamp недостаточно: нужны причинно связанные commit acknowledgement и
разрешение дальнейшей отправки. Этот тест доказывает технический порядок, но не заменяет
правовую оценку допустимости конкретной последующей операции.

### Переход без потери данных

Сначала подготовить инфраструктуру выбранного варианта и доказать её на синтетике.
Перед переносом остановить новые входящие изменения и всех текущих writers, включая workers,
Logto, webhook consumers и WAL archiver. Сделать актуальную согласованную копию PG и RabbitMQ,
перенести на новые изолированные volumes, сверить данные и только затем запустить один комплект
writers. Переключить DNS/webhook/deploy target и резервирование по отдельному плану.
Не включать старую RU-базу: она не содержит новых AMS записей. Rollback должен сохранять данные,
принятые после переключения, а не только возвращать старый DNS [текущий runbook].
Старые снимки удалить после принятого окна восстановления с учётом договоров и удаления провайдера.
