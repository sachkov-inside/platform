# Где архитектура Platform помогает агенту и где требует догадок

Дата: 16.11.2026. Срез: `0421558663e3f889f38ae2d6ba508d298427d523`, текущий `main`, сверенный через HTTPS fetch и GitHub GraphQL. Это исследование, предложения ниже ещё не приняты. Продуктовый код и действующие правила не меняются.

Задание 3.1 требует карту web/backend, проверяемые примеры ошибок, предложения по пользе и отдельные решения владельца. Критерии готовности: охватить эффекты, таймеры, подмены своих модулей, четыре набора данных, временный интерфейс, комментарии, виджеты и платежи/доступ; для каждого предложения назвать объём, риск и вопрос. Проверка работающего приложения не нужна: меняется только исследование. Новую проверку пятнадцати страниц этот аудит не проводил.

## Карта за десять минут

**Module** скрывает implementation за interface. Interface включает порядок вызовов, ошибки и условия использования. **Seam** обозначает место смены adapter. **Depth** означает, сколько поведения получит вызывающий через небольшой interface. Выигрыш для вызывающих называем **leverage**, сосредоточенность знания и изменений у владельца называем **locality**. Это словарь [codebase-design](../../.agents/skills/codebase-design/SKILL.md). Доменные имена берём из [GLOSSARY](../../GLOSSARY.md), владельцев фактов сверяем с [картой контекстов](../product/domain-context-map.md).

### Web

`app` соединяет маршруты с `_pages`; страницы собирают `widgets`, `features`, `entities`, `shared`. Сервер читает backend через сгенерированный transport; браузер хранит состояние запросов в TanStack Query. Интерактивная запись проходит именованную operation и same-origin Route Handler. Это закреплено в [ADR 0011](../adr/0011-client-owned-library-catalog.md), [0012](../adr/0012-browser-owned-interactive-mutations.md), [0027](../adr/0027-web-navigation-and-caching.md), [0038](../adr/0038-one-definition-per-browser-mutation.md).

| Область | Владелец и путь | Что получает извне |
| --- | --- | --- |
| Поиск и чтение | `_pages/library-discovery`, `_pages/material-reader`, срезы каталога и Material | Публичную проекцию, разрешение читать, контент и медиа |
| Продукт и обучение | Страницы продукта, программы, словаря и заданий; `entities/product-page`, `entities/product-access`, `entities/product-task` | Product Reader State, программу, прогресс, сдачи |
| Личные действия | Закладки, чтение, профиль, кабинет; соответствующие `features` | Сессию, личные факты и результаты записей |
| Продажа | `features/billing-checkout`, `features/owner-payments`, страницы checkout и кабинета | Цену, Purchase и Product Access; браузер не выдаёт право |
| Авторская работа | `_pages/material-authoring`, `_pages/content-collections`, авторские списки; `widgets/material-authoring` | Авторские права, схемы и операции backend |
| Общий runtime | `shared/api`, `shared/lib`, `shared/ui`, shell widgets | Transport, session, query infrastructure, browser primitives |

Точные имена срезов и оставшиеся пробелы приведены в дополнении ниже. [check-web-architecture](../../apps/web/scripts/check-web-architecture.mjs) проверяет слои, межсрезовые импорты, server/browser/storybook, чтение и запись, cache и operation-маршруты. Он не доказывает правильность времени фокуса, отсутствие потери события, полноту сценария или допустимость подмены собственного модуля. Проверка синтаксиса `fetch` имеет известные обходы через переменную init и `globalThis.fetch`, описанные в ADR 0038. Это предмет ревью, а не обнаруженный здесь обход в продукте.

### Backend

В `src/modules` находятся 30 каталогов. HTTP, MCP и workers собираются в `src/entrypoints`; Nest wiring находится выше владельцев. Внутри Module вертикальные `features` держат операцию и transport рядом, `facets` собирают несколько связанных операций. `domain`, `ports`, `infrastructure`, `shared` служат нескольким срезам. `index.ts` является внешним interface. [ADR 0004](../adr/0004-feature-first-backend-modules.md) запрещает превращать каждую функцию в отдельный DI seam; [ADR 0005](../adr/0005-prisma-in-use-cases.md) оставляет Prisma непосредственно у владельца операции.

## Где агент легко ошибается

1. **Жизненный цикл браузера распределён между вызывающими.** Подписка должна очиститься, callback не должен устареть, focus должен дождаться появления элемента. Копируя прямой effect, агент копирует и эти обязательства. Точные примеры и счётчики в дополнении. Один универсальный `useEffectOnce` скроет зависимости, но не даст depth.
2. **Тест может проверять выдуманный interface.** Когда тест подменяет `@/shared`, он исключает из проверки реальные transport, operation и query semantics. Seam для web-теста проходит по backend, времени или случайности. Простое удаление mock без восстановления поведения теста недостаточно.
3. **Один сюжет имеет четыре ручных представления.** Story fixtures, seed, navigation fake backend и e2e interception не выводятся друг из друга. Seed действительно состоит из 1 270 строк в трёх файлах `src/development/seed-local-{development,offer-catalog,stand-accounts}.ts`. Один общий JSON ответа не подходит seed: реальные записи должны пройти interfaces владельцев, а HTTP-ответ остаётся проекцией.
4. **Большой платежный implementation требует знания порядка операций.** [BillingPayments](../../apps/backend/src/modules/billing/facets/billing-payments/billing-payments.ts) имеет 2 509 строк. Это сигнал для чтения, не доказательство shallow Module. Его interface скрывает транзакции и согласование с банком. Комментарий у повторного чтения fulfillment после admission объясняет реальную гонку. Разносить файл на функции без общей проверки последовательности значит потерять locality.
5. **Доступ имеет три результата.** В [ContentAccess interface](../../apps/backend/src/modules/content-access/facets/content-access/content-access.interface.ts) `unavailable` отличается от отказа, allow несёт `checkedContentVersion`, а только часть разрешений имеет `validUntil`. `authorizeAccounts` необязателен. Агент, который сведёт ответ к boolean или перенесёт значение между запросами, потеряет условия доступа. Нужны проверки через настоящий interface; общий boolean helper ухудшит depth.
6. **Комментарий одновременно бывает правилом и объяснением.** Лексический поиск строк `^\s*//` в TS/TSX/JS/MJS под src даёт web 1 026, backend 784, telegram 562, включая generated и stories. Это другой охват, чем прежние 715/780/502. Число не доказывает вред комментариев. JSDoc исключён. В `payment-attempt.ts` enum уже выражает допустимые состояния, но запрет отправки retired Purchase в банк требует поведенческого теста, а не ещё одного типа.
7. **Виджет уже генерируется из исходника.** Оба `*-widget-html.generated.ts` запрещают ручную правку, [widget-build](../../apps/telegram/scripts/widget-build.ts) строит HTML. `test/unit/{trainer,ai-models}-widget-build.test.ts` проверяют равенство свежей сборки, размеры, запрещённые конструкции и уникальность классов без учёта регистра. Ошибка в источнике всё равно проходит в HTML. Такие проверки уже существуют в `test/widget/ai-models-widget.test.ts` и `trainer-widget-screens.test.ts`: вкладки, возврат, повтор, длинные объяснения и минимум 11 px. По коду новый пробел не доказан; правильное действие сейчас сохранять существующий путь и не править generated HTML вручную.
8. **Исторический статус выглядит действующим решением.** `DESIGN.md` содержит `owner visual GO is not yet recorded` рядом с production-owned интерфейсами. Нельзя автоматически превратить отсутствие записи в согласие. Прежние пять маркеров не воспроизвелись: найдены четыре места `Temporary semantic UI` ссылаются на закрытые функциональные задачи #1196, #1553, #1741, #1546; связанные визуальные задачи #1278, #1554, #1744, #1547 сверены через `gh issue view`: #1278 CLOSED, #1554/#1744/#1547 OPEN. Прежние четыре открытые integration issue не воспроизвелись, подтверждены три связанные открытые задачи. Пятый маркер и четвёртую задачу нельзя объявить долгом без их адресов.

### Что удалось повторить из прежних измерений

GitHub `gh pr list --state merged --limit 150 --json number,title,changedFiles,files,mergedAt,url` дал окно 31.10–16.11.2026: 150 PR, 25 с 25+ файлами, 16 с изменением generated widget HTML. В этих 16 есть последовательные исправления #2009, #2012, #2018, #2020, #2021, #2054, #2082. Название `fix` само по себе не доказывает регрессию после merge; прежние «5 нуждались в исправлении» и причинный вывод про деньги/миграции не воспроизведены. Для политики внимания основание остаётся [отдельное исследование](issue-2186-delivery-baseline-and-review-experiment.md), его выборка имеет другой размер.

Прежние 7 пустых страниц из 15 принимаем только как входной сигнал. Новый запуск не выполнен, актуальную долю пустых страниц не утверждаем. Из seed и сюжетов нужно составить матрицу и проверить наполненные состояния отдельно от намеренных empty/error.

### Сценарные данные и наполненный seed

Первый набор должен включать: библиотеку с продолжением и фильтрами; Product с главами, платным/бесплатным уроком, дополнительным материалом и артефактом; ученика с Product Access и начатым/завершённым уроком; закладки; задание с текущей версией, сдачей и Author Feedback; словарь; авторские списки платежей, людей и ожидания с данными. Seed уже создаёт демонстрационные материалы, продуктовую программу и цены. Поиск в трёх seed-файлах не показывает построения полного личного пути, сдач с обратной связью, списка платежей и ожидания. Именно эти наполненные состояния нужно добавить; это вывод из исходников, не наблюдение пустого экрана.

Сюжет хранит факты и ожидаемую роль, а adapter seed вызывает реальные interfaces и создаёт данные только в изолированной тестовой базе. Empty, denied, unavailable и устаревшая версия остаются отдельными сценариями. Реальные банк, рассылка и production в seed не входят. Нельзя генерировать тестовое ожидание тем же mapper, который тестируется. Backend-only интеграционные fixtures не нужно все переводить на web-проекции.

### Первые свойства для платежей и доступа

Для BillingPayments проверять перестановки повторов callback/poll, временный сбой банка, потерянный ответ Init, повтор команды и последующую сверку. Свойства: одно подтверждение не выдаёт два Product Access; повтор команды не создаёт новую Purchase; неуспешный/неизвестный платёж сам по себе не даёт право; снятая до отправки покупка не вызывает Init. Отзыв/возврат проверять по действующей продуктовой модели, не придумывать правило «любой refund автоматически отзывает право». Использовать настоящую БД и внешний bank adapter, как в `test/integration/payment-access-matrix.test.ts` и `billing-payments.test.ts`, с короткими последовательностями.

Для `assembleContentAccess` генерировать Subject, publication, Products, права, действие, версию и отказ dependency. Свойства: неизвестность никогда не превращается в allow; результат batch совпадает со scalar при одинаковом снимке; перестановка независимых элементов не меняет решения; повтор ресурса сохраняет отдельный itemId; чтение/скачивание/видео/Task не обходят политику владельца. Границы времени и смену версии проверять отдельно на реальных adapters. Существующие `test/access-scenarios` и `test/unit/content-access.test.ts` сохраняются; grep `fast-check|fc\.` в backend test на срезе не нашёл реализации property-based tests.

### Порядок запретов

№3 не означает заменить каждый effect общей обёрткой. Сначала удалить синхронизацию derived state и запросы из effects, затем спрятать повторяющиеся browser lifecycle obligations. После переноса добавить запрет прямых `useEffect`/`useLayoutEffect` в продуктовых срезах с разрешением только в названных adapter-файлах. Отдельно решить исключения для редактора и сторонних primitives, оставив точный путь и тест. Таймеры запрещать по доказанным видам обходов, не запрещать debounce, уведомления и реальное ожидание пользователя. Это сохраняет depth вместо косметического переименования.
