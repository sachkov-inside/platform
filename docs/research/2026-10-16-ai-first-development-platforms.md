# Платформы AI-first разработки и ориентиры программы Inside

**Дата проверки:** 16.10.2026. **Статус:** исследование для обсуждения программы, без утверждения новых глав или продуктовых требований.

## Вопрос и основной вывод

Какие возможности стоит реализовать в учебной платформе, чтобы разобрать AI-first разработку команды на содержательном проекте?

Проверенные продукты объединяют задачи, знания проекта, инструменты, изолированное выполнение, проверки и контроль человека.
Компании строят вокруг агентов собственную инфраструктуру, которая выдаёт доступы, сохраняет ход работы и проверяет результат.
Поэтому платформу Inside можно развивать как общее место работы сотрудников и агентов над проектами.
Это вывод исследования, а не подтверждённый спрос на курс или обязательство реализовать весь обзор.

## Охват и ограничения

Проверены официальные документы GitHub, Cursor, Devin и Port, а также инженерные публикации Spotify, Ramp, Stripe и Uber.
Документация подтверждает описанные возможности, но исследование не включает запуск продуктов или проверку аккаунтов.
У перечисленных страниц документации дата публикации не показана; дата проверки не означает дату выпуска функции.
Корпоративные публикации описывают конкретные внедрения и содержат самоотчёты компаний.
Их показатели нельзя переносить на Inside или считать доказательством общего роста производительности.
Функции могут зависеть от тарифа, настроек администратора и текущего этапа выпуска.

## Возможности готовых платформ

| Платформа | Что подтверждают официальные документы | Что полезно для учебного проекта |
|---|---|---|
| GitHub Copilot cloud agent | Агент получает задачу из issue, комментария или интерфейса. Он работает в отдельной временной среде GitHub Actions, запускает тесты и создаёт PR. [Описание](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent) | Связать задачу, запуск агента, отдельную ветку, результат проверок и PR. |
| GitHub Copilot | Интерфейс показывает журналы и активные сессии; человек может уточнять задачу во время работы. [Управление](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/agent-management). Агент не может одобрить или слить свой PR. Запуск workflow требует одобрения по умолчанию; настройка допускает автоматический запуск. [Ограничения](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) | Показывать состояние выполнения и сохранять отдельную проверку человеком перед принятием изменения. |
| GitHub Copilot | MCP подключает инструменты внешних систем. Сейчас cloud agent поддерживает MCP tools, но не resources/prompts и не удалённые OAuth-серверы. Инструменты вызываются без промежуточного запроса одобрения. [MCP](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/mcp-and-cloud-agent) | Проверять совместимость клиента, способ авторизации и разрешения каждого инструмента. |
| Cursor Cloud Agents | Агенты работают в отдельных виртуальных машинах. Запуск доступен из приложения, web, Slack, Linear, GitHub и API. Среда содержит репозитории, зависимости и команды запуска. [Описание](https://cursor.com/docs/cloud-agent) | Передавать работу из привычного интерфейса в облачную среду с готовыми средствами проверки. |
| Cursor Cloud Agents | Есть отдельные типы секретов для среды, выполнения и сборки. Секреты выполнения скрываются из ответов инструментов, но доступны через терминал среды. Сеть можно ограничивать списком разрешённых адресов. [Secrets & Network](https://cursor.com/docs/cloud-agent/security-network) | Разобрать выдачу секретов, сетевые ограничения и различие между скрытием значения и запретом доступа. |
| Devin | Linear позволяет назначать задачи агенту, запускать сценарии через метки и получать ход работы с PR. Jira Cloud поддерживает назначение и упоминание агента. [Linear](https://docs.devin.ai/integrations/linear), [Jira](https://docs.devin.ai/integrations/jira) | Интеграция с существующим трекером уже даёт содержательную задачу для AI-инженерии. |
| Devin | Security Profiles ограничивают сеть, MCP, git и GitHub CLI. Профили применяются к организации, автоматизации или сессии. [Профили](https://docs.devin.ai/product-guides/security-profiles). Секреты имеют персональную, общую и более узкие области. [Секреты](https://docs.devin.ai/product-guides/secrets) | Разделить пользователя, агента, проект и разрешённые действия. Выдавать доступ на сервере, а не только через инструкцию модели. |
| Devin | Session Insights показывает расход ACU, сообщения, размер сессии и проблемы выполнения. ACU измеряет вычислительные затраты продукта. [Анализ сессий](https://docs.devin.ai/product-guides/session-insights). Старый Knowledge объявлен устаревшим; новые инструкции предлагают оформлять как Skills in Plugins. [Knowledge](https://docs.devin.ai/onboard-devin/knowledge-onboarding) | Анализировать причины повторных попыток и отделять документы проекта от процедур и памяти агента. |
| Port | Каталог связывает сервисы, владельцев, агентов и инструменты. Port MCP открывает данные и действия внешним агентам. [Управление агентами](https://docs.port.io/agent-management/overview/) | Пример управляющей платформы поверх разных агентов, близкий общей идее Inside. |
| Port | Ассистент отвечает по каталогу и запускает действия. Доступные инструменты ограничиваются правами пользователя. Подтверждение, автоматическое выполнение и отключение инструмента настраиваются отдельно. [Tools and approvals](https://docs.port.io/port-ai/tools-and-approvals/), [Ассистент](https://docs.port.io/port-ai/port-ai-assistant/) | Встроенный помощник может искать владельца, объяснять доступы и выполнять разрешённые операции платформы. |

Эти страницы описывают существующие механизмы продуктов, однако не подтверждают универсальную доступность каждому клиенту.
Например, GitHub прямо помечает сторонних coding agents как public preview.
[Статус сторонних агентов](https://docs.github.com/en/copilot/concepts/agents/about-third-party-coding-agents).

## Как компании организуют разработку

### Spotify, Honk

Spotify описала ограничения раннего агента 24.11.2025.
Выбор файлов вручную и простой цикл вызовов мешали изменениям в нескольких файлах и расходовали контекст.
[Context Engineering](https://www.engineering.atspotify.com/2025/11/context-engineering-background-coding-agents-part-2).

В публикации 09.12.2025 независимые проверки выбирают сборку, тесты и форматирование по содержимому репозитория.
Агент получает короткие сообщения об ошибках; PR появляется после успешных проверок.
Отдельная модель сравнивает запрос и diff, но авторы тогда ещё не построили структурированную оценку этой модели.
[Strong Feedback Loops](https://www.engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3).

Обновление 03.06.2026 описывает Claude Agent SDK в Kubernetes pods, запуск из Slack и учёт PR через существующую платформу.
Для курса достаточно одного удалённого исполнителя и списка запусков; повторять масштаб Spotify необязательно.
[Обновление Honk](https://www.engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint).

### Ramp, Inspect

Ramp 12.01.2026 описала отдельную sandbox VM для каждой сессии, снимки подготовленных сред и сохранение сессии между подключениями.
Интерфейс позволяет продолжать работу с разных клиентов, проверять приложение и видеть предварительный результат.
Компания сообщила, что Inspect написал около 30% слитых frontend/backend PR на момент публикации.
Доля PR не измеряет причинный рост производительности.
[Why we built our background agent](https://engineering.ramp.com/post/why-we-built-our-background-agent).

### Stripe, Minions

Stripe 19.02.2026 описала изолированные среды без production-данных пользователей и произвольного сетевого доступа.
Сценарий сочетает фиксированные шаги проверки с шагами агента; после ограниченного числа попыток работа возвращается человеку.
Общий MCP-каталог содержит множество инструментов, но конкретный агент получает небольшую подходящую подборку.
Компания сообщила о 1300 слитых PR в неделю с человеческим ревью; это не автономный merge и не оценка ускорения.
[Minions, Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2).

### Uber, Software Factory и MCP Gateway

Uber 27.08.2026 описала агентов для ревью, исправления CI, подготовки PR и разбора инцидентов.
Компания оценивает конкретные сценарии по качеству, стоимости, задержке и завершённым результатам.
Например, проверку ревью строят на задачах с известными ошибками.
Политика расходов использует уведомления и повышение лимита через руководителя; жёсткий автоматический запрет не был её целью.
[Software Factory](https://www.uber.com/us/en/blog/efficient-software-factory/).

Uber 01.10.2026 описала MCP Gateway с реестром, проверкой инструментов владельцами, авторизацией и журналом вызовов.
Клиент постепенно запрашивает серверы, инструменты и схемы вместо загрузки полного каталога сразу.
Сервер применяет права, скрывает чувствительные данные и ограничивает частоту вызовов.
[Designing MCP Gateway](https://www.uber.com/pr/en/blog/designing-mcp-gateway/).

## Инженерные принципы для отдельных экспериментов

Anthropic 08.04.2026 описала разделение журнала сессии, управляющей программы агента и изолированной среды.
Журнал позволяет восстановить работу после сбоя управляющей программы; секреты могут оставаться вне среды выполнения.
[Managed Agents](https://www.anthropic.com/engineering/managed-agents).

Материал Anthropic 29.09.2025 различает текущий контекст, долговременные заметки и поиск нужной информации по запросу.
Он рассматривает сочетание предварительно загруженных данных с поиском во время задачи.
[Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents).

Материал 09.01.2026 предлагает оценивать задачу, попытку, журнал действий и конечное состояние системы отдельно.
Сообщение агента об успехе не заменяет проверку результата кодом, моделью или человеком.
[Evals for agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

## Предложения для обсуждения программы

Следующие направления выводятся из исследования. Они не меняют текущую программу автоматически.
Каждое направление можно оформить самостоятельной небольшой главой с видимым результатом.

| Направление | Минимальный результат платформы | Инженерные темы |
|---|---|---|
| Знания команды | Помощник находит ответ по документации, показывает источник и соблюдает доступы. | RAG (Retrieval-Augmented Generation), подготовка ответа с поиском по документам; поиск по словам и смыслу, разбиение документов, обновление индекса, проверка качества поиска. |
| Инструменты агентов | Личный агент разработчика вызывает разрешённые функции платформы. | MCP, авторизация, выбор инструментов, ограничение ответов, управление контекстом. |
| Помощник внутри платформы | Агент объясняет проекты и доступы, помогает пройти онбординг, выполняет разрешённое действие. | Цикл агента, состояние диалога, память, подтверждение действий, проверка полномочий. |
| Задачи команды | Платформа передаёт задачу агенту и связывает запуск с трекером и репозиторием. | Интеграции, события, повторная доставка, защита от двойного запуска, критерии завершения. |
| Облачное выполнение | Один исполнитель принимает задачу, работает отдельно и сохраняет результат. | Подготовка среды, очередь, секреты, ограничения сети, отмена, восстановление и ограниченные повторы. |
| Проверка изменений | Агент создаёт PR с результатами тестов; человек видит, что осталось проверить. | CI, независимые проверки, ревью, проверка границ задачи, передача работы человеку. |
| Качество и расходы | Платформа показывает ход работы, ошибки и стоимость завершённой задачи. | Журнал действий, токены, задержка, бюджет, набор проверочных задач, сравнение моделей и конфигураций. |

Для сквозного примера подходит путь сотрудника от подключения к проекту до проверки PR облачного агента.
Документы и доступы дают контекст, инструменты выполняют действия, трекер задаёт работу, а проверки подтверждают результат.
Облачный исполнитель может использовать готовую среду выполнения агента; собственную модель или замену Cursor создавать необязательно.

Для первого варианта разумно интегрировать один существующий трекер, например GitHub Issues.
Собственный полноценный трекер увеличит продуктовую работу, но сам по себе не добавит обязательную тему AI-инженерии.
Это рекомендация исследования, а окончательный выбор принадлежит владельцу.

Исследование не доказывает, что каждой команде нужны vector database, долговременная память или несколько агентов.
RAG стоит сравнить с прямым чтением документов, а многоагентный сценарий с одним исполнителем на одинаковых задачах.
Обещание курса лучше связывать с результатами и темами; конкретные поставщики могут меняться.
