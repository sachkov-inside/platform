# pgBackRest: проект перехода и пакет недостающих сведений

Дата: 21.10.2026. Задача: [#1627](https://github.com/sachkov-inside/platform/issues/1627).
Основа проекта: `acc31f103a1aa67c06b20da1e9bee79c45194aae`.
Это подготовленный проект для отдельного принятия, не действующий operational runbook.
Production не читался и не менялся. Все будущие операции ниже ещё не выполнены.
Оценка исторического шифрования остаётся в [исследовании](2026-10-21-pgbackrest-historical-encryption.md).

## Принятое направление и фактический статус

Владелец в этой сессии согласовал три предложения: сохранить все имеющиеся копии до определения
сроков восстановления; подготовить конкретный переход с отдельным согласованием исполнения;
оставить RNG непройденным без исключения. Ответ: «со всем согласен, реализуй всё».
Согласованное направление не является принятием ещё не подготовленной HIGH production-операции.

| Предмет | Статус |
| --- | --- |
| Binary upgrade и full `20261021-051241F` | Выполнены в [#1579](https://github.com/sachkov-inside/platform/issues/1579#issuecomment-6308646285), не повторять |
| Качество исторических подключей | Не установлено; восстановимость не доказывает случайность ключей |
| Сохранение всех имеющихся копий | Направление принято, техническая защита от истечения ещё не применена |
| Новый repository/stanza | Предложены ниже, не созданы |
| RNG | `rngFailureVerified=false`, без исключения; STOP сохраняется |

В [pgbackrest.conf](../../infra/production/database/pgbackrest.conf) задано
`repo1-retention-full=4`, тип `count`. [database-backup](../../infra/production/database/database-backup)
не отключает auto-expire. Поэтому обычное расписание может удалять старые цепочки.
Отсутствие ручного удаления не гарантирует сохранение истории. Effective production overrides,
провайдерский lifecycle и отдельные expire jobs пока неизвестны.

## Предлагаемая схема

Сохранить старый repository как repo1, его stanza `production`, ключи и все зависимости истории.
Для новых копий предложен **отдельный bucket у текущего backup provider**, если измеренные
стоимость, регион, доступность и изоляция доступа приемлемы. Bucket не создавать до принятия
бюджета. Если это не проходит критерии ниже, выбор места вынести владельцу с измерениями.

Новый repository подключить как repo2 с собственными access credentials и passphrase, с
`aes-256-cbc` и TLS verification. В нём создать новую stanza с тем же именем `production`.
Идентичность stanza здесь определяется парой repository + имя. Старые `archive.info`,
`backup.info` и manifests в новый repository не копировать: это перенесло бы старые подключи.
Создатель новой stanza должен быть закреплённым исправленным binary 2.59.3, а не moving tag.

Предлагается штатный multi-repository путь: в период перекрытия WAL поступает в оба repository,
а backup каждого выбирается явно. Имя `production` сохраняет совместимость существующих
entrypoints, но repo selector нельзя оставлять неявным. Не предлагать две shell-команды
архивации как замену штатному multi-repository механизму.

Основания: [multiple repositories](https://pgbackrest.org/user-guide.html#multi-repo),
[stanza-create](https://pgbackrest.org/command.html#command-stanza-create).
Страницы upstream на дату чтения показывают 2.60.0. Для применения на 2.59.3 точные параметры,
поведение асинхронного spool и выбор repository должны пройти отдельную синтетическую репетицию
на закреплённом image. Смена версии binary в этот переход не входит.

## Пакет недостающих несекретных сведений

Это спецификация следующего ограниченного чтения, а не уже собранный inventory. Перед чтением
зафиксировать точные команды и фильтры в reviewed пакете. Никаких общих environment/config dumps,
`docker inspect` целиком, plaintext info/manifests, secret files или пользовательских записей.
Обычный `info --output=json` отличается от извлечения файлов `backup.info` через `repo-get`;
сохранять разрешённые поля, а не сырой JSON или сообщения об ошибках.

| Сведения | Разрешённый источник и поля | Когда достаточно |
| --- | --- | --- |
| Связь repo1 и production | Выборочные несекретные настройки: stanza, repo index/type/path, provider/region, cipher type, версии и digest. Bucket обозначать внутренним псевдонимом | Есть датированное соответствие конфигурации, live image и repository; секретные значения не читались |
| История stanza | Сохранившийся журнал создания/переноса: timestamp, binary/OpenSSL version, source receipt | При отсутствии журнала дата и происхождение остаются неизвестными; backup label их не заменяет |
| Полный retained inventory | Структурированный `info` по конкретному repo: label, type, timestamps, prior/reference, backup/WAL bounds, sizes, status | Все записи и зависимости перечислены; ошибки/неполнота названы, пагинация исчерпана где применима |
| Архив WAL | Список имён архивных объектов и sizes, timelines, start/stop, без чтения payload | Есть проверка непрерывности для выбранных recovery intervals. Min/max сами по себе не доказывают отсутствие дыр |
| Кто может удалять | Разрешённые поля retention/expire-auto overrides, имена и расписания backup/expire jobs, bucket lifecycle/versioning/expiration rules | Перечислены все известные пути удаления, в том числе провайдерские; неизвестный путь блокирует гарантию сохранения |
| Размер и рост | Полный object listing только старого backup namespace, sizes/counts, счётчики объёма за доступный период, свободное место/quota | Учтены metadata, bundles, WAL, версии объектов и источник/период каждой величины; недостающие измерения обозначены |
| Цена | Датированная официальная тарифная страница текущего provider/region/class или действующий billing contract | Есть единицы, валюта, налоги/скидки, storage, запросы, egress и лимит расходов; без этого суммы не выдумывать |
| Recovery доступ | Подтверждение наличия host и offline recovery material по действующей процедуре, без содержимого | Восстановление сможет получить доступ независимо от потерянного VPS; секреты не попадают в отчёт |

Каждое наблюдение связывать с временем UTC и source revision. Не смешивать результаты разных
repository. Пока jobs и lifecycle продолжают менять данные, inventory является наблюдением,
а не согласованным снимком. Повторная сверка нужна после защиты от истечения и после перехода.
Состояние на момент согласия владельца задним числом восстановить по старым receipts нельзя.

## Сохранение истории до перехода

Первой HIGH операцией предложено исключить автоматическое истечение, сохранив backup и WAL.
Её принять отдельно до применения. После принятия взять существующие deployment locks,
приостановить только запуск собственных backup/expire jobs, дождаться завершения активных
операций, не прерывая живой backup. Проверить провайдерские правила удаления.
Архивацию WAL и приложения на этой фазе не останавливать.

В reviewed effective backup configuration задать `expire-auto=n`, проверить отсутствие
переопределяющих env/CLI и отдельного expire. Провайдерский lifecycle, если он может удалить
нужную историю, требует отдельного принятого изменения. Вернуть расписание только после
проверки effective настройки всех entrypoints. Не удалять retention settings как способ
«заморозки». [Expire auto](https://pgbackrest.org/configuration.html#section-backup/option-expire-auto)
отключает автоматический expire, но не другие механизмы удаления.

Зафиксировать T0 после подтверждённой защиты: все retained sets на T0, их full/diff/incr
зависимости, metadata и WAL для всех доступных на T0 интервалов входят в сохраняемую историю.
Предложен дополнительный полный encrypted snapshot старого namespace в отдельное защищённое
место, без преобразования ключей. Его согласованность, полноту объектов и restore проверить;
параллельное копирование меняющегося namespace само по себе не является согласованным snapshot.
Не считать Object Lock обязательной настройкой без проверки совместимости.

Если защиту от истечения подтвердить нельзя, сохранение не объявлять выполненным и переход
не начинать. До отдельного решения срок хранения всех сохранённых цепочек не сокращать.
При нехватке места не возобновлять expire молча: остановить переход и согласовать ёмкость.

## Ёмкость, стоимость и окно

Обозначения для расчёта: H = bytes сохраняемой истории; F = измеренный размер новой full;
D = bytes diff/incr и WAL в сутки; N = согласованный период расчёта в днях; U = распакованный
размер кластера; E = downloads/egress для выбранной матрицы восстановления. Пока значения неизвестны.

Предлагаемый резерв object storage: H для дополнительного старого snapshot плюс F + D × N
для нового repository, сверх уже занятого repo1. Учесть noncurrent versions отдельно и добавить
30% запаса. Это оценка бюджета, не доказательство достаточности: уточнить по измеренному росту,
overlap WAL в repo1 и repo2 и временным uploads. Для restore host отдельно нужны staged ciphertext,
U, WAL replay, logs и 30% запаса; проверки запускать последовательно, чтобы не умножать U.

Стоимость = GB-month по каждому месту/классу + requests + E × egress rate + временный restore host.
Перевести bytes в единицы тарифа. N задаёт бюджетный горизонт, не разрешает удаление на N-й день.
Переход допускается только если quota/free space покрывают рассчитанный пик, прогноз не исчерпает
место до следующей проверки и сумма укладывается в явно принятый владельцем бюджет.
При превышении подготовить альтернативу с фактическими ценами, без покупки и ротации старых credentials.

Из-за [Compose env_file](../../infra/production/database/compose.yaml) новые секреты должны быть
доступны и backup-контейнеру, и postgres, выполняющему archive-push. Изменение env требует
проверенного способа применения, потенциально recreate postgres. Планировать maintenance window,
длительность определить репетицией и объявить владельцу до применения. Перерыв 90,6 s из #1579
не является оценкой этого перехода. Общий local Compose stand не использовать и не останавливать.

## Последовательность будущего исполнения и отката

1. **До изменений.** Собрать reviewed inventory, заполнить расчёт, принять HIGH пакет сохранения
   истории и выполнить его с доказательством T0. Получить свежую old backup/isolated restore
   по существующей защищённой процедуре. Сохранить public config preimages и закрытые recovery
   материалы по [secrets contract](../../infra/production/secrets/README.md), без выгрузки секретов.
2. **Подготовить новый namespace.** Принять bucket/budget/access scope, доставить новые секреты
   защищённо. Проверить пустоту нового namespace. В отдельной staged configuration, не в live
   bind mount, создать новую stanza только в новом repository на закреплённом 2.59.3.
   Конфигурация этого шага должна содержать только новый repository. Старый не инициализировать.
3. **Принять и применить переключение.** До окна проверить итоговый diff и репетицию, принять
   конкретный HIGH commit и команды. Под locks временно остановить расписание, дождаться jobs,
   применить multi-repository config/secrets согласованным способом, сохранить тот же live volume.
   Не запускать restore на live volume и не делать database rollback. Проверить WAL в обоих repos,
   spool/errors, свободное место и приложения. Не менять finite archive queue limit так, чтобы
   потеря WAL принималась за успешную архивацию.
4. **Новая цепочка.** Явно выбрать repo2 для full backup, проверить нужный WAL и isolated restore.
   До результата сохранять old backup path. Только после успешной матрицы переключить расписание
   full/diff/incr на явный repo2. Old backup jobs вывести из расписания отдельным принятым diff;
   old WAL продолжать в период перекрытия. Не сохранять неявный default repo1 в helper.
5. **Завершение.** Зафиксировать последнюю защищённую старую точку, первую новую и доказанный
   интервал перекрытия. Прекращение old WAL допускается только после подтверждения покрытия всех
   требуемых точек старой историей и новой цепочкой, со специальным принятием этой границы.
   Старый repository, его ключи и snapshot сохранить, ничего не удалять.

Если ошибка возникла до переключения, live path остаётся старым, новые частичные объекты
не удалять автоматически. Если после переключения, вернуть принятую old routing/configuration
и old расписание **с отключённым expire**, проверить catch-up WAL и свежий old backup/restore.
Сохранить новые записи в live БД, тот же volume и оба repository. Не возвращать старый data volume
или backup поверх текущих записей. Откат не должен вернуть auto-expire вместе с preimage.
Если old archive не догоняет WAL или нужные segments недоступны, возврат не объявлять успешным;
дальнейшие изменения остановить, зафиксировать recovery gap и получить отдельное решение.

## Матрица доказательств и готовность

| Проверка будущего исполнения | Критерий успеха |
| --- | --- |
| Синтетическая репетиция на 2.59.3 | Новый repo независим; old metadata не перезаписаны; WAL в оба repo, явный backup selector, old routing возврат и cleanup подтверждены |
| История T0 | Каждый retained backup label восстановлен, все три БД доступны; полные зависимости сохранены. Для каждого непрерывного доступного интервала отдельно проверены начальная/конечная PITR точки и граница перехода; пробелы названы |
| Новая full и WAL | Из repo2 восстановлены inside, logto, inside_telegram. Схемы и данные сравнены закрытой сверкой; для изменявшихся таблиц ограничения названы, несовпадения не скрыты |
| PITR | Достигнута выбранная точка и timeline, replay завершён на target; для синтетики доказаны изменения до/после точки. Live marker writes этим планом не разрешаются |
| Изоляция | Закреплённый image, fresh owned volumes, staged ciphertext read-only, без published ports, приложений и consumers; секреты только в закрытом окружении |
| Cleanup | Собственные процессы, контейнеры, volumes и временные secrets удалены с проверкой; история и recovery материалы сохранены |

[isolated-database-restore.py](../../scripts/isolated-database-restore.py) уже использует
stanza `production`, POSIX staging и immediate restore. Он не доказывает PITR или полное
сравнение данных. Прежде чем использовать его для этой матрицы, подготовить и независимо
проверить недостающее покрытие. Непроверенные labels/интервалы остаются непроверенными.

Пакет для разрешения исполнения должен содержать заполненный inventory и бюджет, actual
config/script diff, rehearsal receipts, immutable head, Standards/Spec/Security review и CI,
план окна и recovery/rollback commands. Этот документ задаёт его состав, но пока не является
готовым executable пакетом. Для исполнения нужны отдельное принятие HIGH результата и границы
production-операции по [change-risk policy](../agents/change-risk.md).

`rngFailureVerified=false` остаётся без исключения. Остановленный эксперимент не исследуется,
не проектируется и не заменяется другим механизмом. #1627 остаётся открытой; security acceptance
не GREEN. Новых уведомлений, платежей, provider callbacks или действий поддержки план не включает.
