# Полная переделка админки: библиотеки и основание интерфейса

Уточнение владельца после просмотра прототипа: новая админка сохраняет цветовую стилистику платформы.
Все варианты наследуют токены `apps/web/app/globals.css`. Возможность изменить палитру,
обсуждавшаяся ниже в исследовании, этим уточнением отменена.

Дата исследования: 20.10.2026. Статус: предложение для выбора и проверки направления, не принятое архитектурное решение.

Источники проверены по доступным официальным страницам и репозиториям. Страницы `main`, документация и каталоги изменяются; дата исследования не означает зафиксированный снимок каждого npm-пакета. Версии в проекте проверены по локальным файлам, совместимость новых пакетов сборкой пока не проверялась. Маркетинговые заявления об accessibility не считаются доказательством доступности нашего будущего интерфейса. Число компонентов и GitHub stars не используются как критерий качества.

## Результат сравнения библиотек

**Рекомендация исследователя: полностью перепроектировать админку на shadcn/ui, используя новые композиции экранов и выбранные блоки blocks.so. Серьёзная альтернатива для сравнения на одном реальном экране: Mantine.** Это рекомендация по исходным данным, которую следует подтвердить прототипом. Сохранение технических примитивов не требует сохранять нынешние цвета, шрифты, размеры, карточки, меню или распределение функций по страницам.

Основание: проект уже содержит React 19, Next.js 16, Tailwind 4, `radix-ui`, shadcn CLI и локальные UI-компоненты. `apps/web/components.json` задаёт `radix-nova`. Поэтому shadcn позволяет заменить всю композицию и визуальный язык без обязательной замены API каждого поля и диалога. Mantine даёт более цельный комплект готовых подсистем, но потребует перехода на его компоненты, стили и контекст. Это оценка стоимости интеграции, а не измеренная оценка часов. Локальные источники: [package.json](../../apps/web/package.json), [components.json](../../apps/web/components.json).

## shadcn/ui и Mantine: что действительно различается

### shadcn/ui

Официальный changelog от июля 2026 переключил новые проекты и открываемые страницы документации на Base UI. Он прямо сохраняет поддержку Radix и не требует миграции действующих приложений. Поэтому новый default не является причиной автоматически переделывать все наши примитивы. Примеры необходимо брать из правильного варианта: API `asChild` у Radix и `render` у Base UI различаются. [Изменение default](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default), [различия API](https://github.com/shadcn-ui/ui/blob/main/skills/shadcn/rules/base-vs-radix.md).

Data Table у shadcn является руководством по сборке таблицы с нужным поведением, а не универсальным готовым продуктом для любых данных. Актуальный пример использует TanStack Table v9. Нельзя механически смешивать его с примерами старых версий или брать локальную фильтрацию всего массива вместо серверной обработки больших выборок. Формы также требуют выбора управления состоянием и согласования ошибок API. [Data Table](https://ui.shadcn.com/docs/components/base/data-table), [React Hook Form](https://ui.shadcn.com/docs/forms/react-hook-form).

Вывод: выигрыш shadcn для нас состоит в свободе композиции и близости к текущему стеку. Это не аргумент оставить нынешнюю структуру страниц. Полная переделка остаётся полной, даже если проверенные Dialog, Button и Input продолжают выполнять базовую работу.

### Mantine

AppShell имеет отдельное состояние сворачивания для телефона и компьютера, ширины по breakpoints и секции header/navbar/aside/main. `useForm` документирует вложенные значения, списки, ошибки и uncontrolled-режим. `Table.ScrollContainer` решает локальную прокрутку широкой таблицы. Это конкретные готовые механизмы, полезные админке. [AppShell](https://mantine.dev/core/app-shell/), [useForm](https://mantine.dev/form/use-form/), [Table](https://mantine.dev/core/table/).

При этом core Table не обещает единый готовый data grid со всей логикой сервера. Не следует приписывать Mantine core возможности сторонних Mantine React Table или Mantine DataTable. Также компоненты Mantine требуют контекст и относятся к client components, хотя могут предварительно рендериться на сервере. Для Next.js есть официальный порядок настройки. [Next.js guide](https://mantine.dev/guides/next/).

Вывод: Mantine стоит предпочесть, если на одинаковом экране он заметно сокращает дополнительную работу над датами, формами, уведомлениями и оболочкой и при этом даёт нужный визуальный результат. Если такого выигрыша нет, массовая замена API ради нового вида добавляет миграцию без пользовательского преимущества.

## Дополнительные инструменты из списка

**tweakcn**: визуальный редактор тем shadcn/Tailwind, исходный код под Apache-2.0. Подходит для сравнения цветов, шрифтов, радиусов и теней. Переносим выбранные токены, не используем редактор тем как замену проектированию сценариев. [Проект](https://tweakcn.com/), [исходники](https://github.com/jnsahaj/tweakcn), [лицензия](https://github.com/jnsahaj/tweakcn/blob/main/LICENSE).

**Sileo**: MIT, React toast с morphing-анимацией, action и promise-состояниями. Это узкий механизм уведомлений. До добавления проверить screen reader announcements, возможность дочитать сообщение, уменьшение движения и наложение на мобильные действия. Открытая начальная документация не доказывает выполнения этих требований. Выбирать после решения, какие действия нуждаются в кратком уведомлении, а какие в постоянном результате рядом с формой. [Сайт](https://sileo.aaryan.design/), [документация](https://sileo.aaryan.design/docs).

## Как выбрать по результату, а не по впечатлению от каталога

Для решающего сравнения достаточно одного согласованного дизайна на двух основаниях, shadcn и Mantine, с одинаковыми данными и состояниями. Экран должен содержать реальную таблицу, фильтр дат, редактирование, ошибку сохранения и мобильную навигацию. Дополнительные кандидаты подключать, если первые два не закрывают конкретную задачу.

Критерии: понятность назначения экрана без инструкции; видимость главного действия; успешное выполнение задания с телефона; доступная клавиатурная навигация; читаемые ошибки; объём собственного кода для одинакового поведения; поведение на реальных объёмах данных. Если библиотека выигрывает только шрифтом и цветом демонстрации, это выбор оформления, а не основание для миграции.

Ни одна из проверенных библиотек сама не решает группировку разделов, избыток поясняющего текста, смешение аналитики и операционной работы или выбор главного действия. Эти изменения должны быть отдельной частью полной переделки интерфейса.

## Предлагаемая структура админки

Это предложение для прототипа, не принятое изменение продуктового контракта.
Названия разделов ниже человеческие. Они не переименовывают доменные сущности и API.

| Область | Содержимое | Принцип |
| --- | --- | --- |
| Контент | Материалы, темы, продукты | Общий вход в авторскую работу. В продукте своя навигация по программе, оформлению и настройкам. |
| Ученики | Сдачи и существующие операции доступа | Переход от списка к конкретной задаче или человеку. Полная карточка ученика потребует отдельной проверки доступных данных. |
| Продажи | Предложения, оплаты, платёжные ссылки, наборы | Операционные задачи отделены от отчётов. Между продажей продукта и настройкой его предложения есть понятный переход. |
| Коммуникации | Существующие сценарии и рассылки | Отдельная область, чтобы термин «воронка» не смешивал сценарий сообщений с аналитическим отчётом. |
| Аналитика | Воронка продаж, ожидание набора, анкета | Один контекст продукта и периода. Разные единицы измерения и области действия фильтров обозначены явно. |

На компьютере: спокойная боковая навигация с этими группами, рабочая область с единым заголовком,
контекст продукта в нужных разделах. Короткое действие может открываться в диалоге или боковой панели.
Длинный редактор получает полноценную страницу и сохраняемый адрес.

На телефоне: три наиболее частых направления и «Ещё» либо компактное меню всех разделов.
Выбор зависит от приоритетных задач владельца. Страница содержит один основной рабочий столбец.
Детали из боковой панели становятся отдельным экраном с возвратом к прежнему списку и фильтрам.
Задачи не исчезают из-за ширины окна. Поиск команд может ускорять работу с клавиатурой,
но обычная навигация должна работать без знания сочетаний клавиш.

Предлагаемое визуальное направление: светлая нейтральная рабочая область, спокойная навигация,
один акцент для значимых действий, тонкие разделители, умеренные радиусы и минимум теней.
Основной рабочий текст ориентировочно 15–16 px, вторичные подписи 13–14 px при достаточном контрасте.
Это исходные параметры для сравнения, не окончательные токены. Продукты и материалы читаются
как упорядоченные списки; крупные карточки остаются там, где действительно группируют отдельную задачу.
На компьютере можно предусмотреть обычную и компактную плотность, если это подтвердит работа с длинными списками.
Шрифт выбирается с полноценной кириллицей и проверяется на реальных названиях продукта и главы.

Новая обзорная страница нужна только при наличии полезных ответов: что требует проверки,
где продолжить работу и что изменилось. Набор декоративных счётчиков не решает текущую проблему.

## Как переделать экран со скриншота

1. В верхней строке показать «Аналитика», выбранный продукт, главу и понятный период.
   На телефоне вторичные фильтры раскрываются кнопкой; применённые значения остаются видны.
2. Основным содержимым сделать этапы воронки и их значения. На компьютере они могут идти горизонтально,
   на телефоне вертикально. У каждого этапа остаётся единица измерения.
3. Под ними разместить сравнение источников. Пользователь может открыть источник и увидеть его этапы,
   не прокручивая широкую таблицу на телефоне.
4. Ожидание набора и анкету отделить вторичными представлениями внутри аналитики. Выбор главы не должен
   создавать впечатление, что ожидание относится к главе. Его собственный набор показан явно.
5. «Как считаются числа» открыть по ссылке рядом с отчётом. Время обновления оставить видимым.
   Невозможность рассчитать показатель объяснять рядом с ним с доступным следующим действием.

Критическое ограничение: контакты бота, аккаунты, текущий размер списка ожидания и изменения за период
не взаимозаменяемы. Нельзя рисовать убывающую воронку и проценты между этапами, пока не подтверждены
общий знаменатель и правила сопоставления. В примере из скриншота 0 контактов и 2 аккаунта не означают
конверсию 200%. Нельзя превращать отсутствие данных в ноль или добавлять тренд выручки без временного ряда.
Основание: [модель отчёта](../../apps/web/src/_pages/sales-funnel-report/model/sales-funnel-report.ts),
[методика в текущем представлении](../../apps/web/src/_pages/sales-funnel-report/ui/sales-funnel-report-view.tsx),
[ожидание набора](../../apps/web/src/_pages/sales-funnel-report/ui/waitlist-demand-view.tsx).

## Состав рекомендуемой основы

- shadcn/ui на существующей линии Radix для базовых элементов. Сначала получить единое поведение Button,
  Field, Select/Combobox, Tabs, Dialog, Menu, Sheet и статусов сохранения.
- Готовые композиции из официальных shadcn blocks и blocks.so как исходные заготовки с последующей адаптацией.
  Не смешивать разные реализации одного примитива только ради внешнего вида.
- Для сложных таблиц рассмотреть TanStack Table. [Официальное руководство shadcn Data Table](https://ui.shadcn.com/docs/components/radix/data-table)
  показывает именно сборку своей таблицы. Это не готовый универсальный admin grid. Для простого отчёта
  обычная семантическая таблица может быть достаточна.
- Для графиков использовать [shadcn Chart](https://ui.shadcn.com/docs/components/radix/chart) как вариант
  поверх Recharts после проверки реальных рядов данных. График не должен быть обязательным украшением.
- Сохранить существующее управление данными, авторизацию и команды приложения. Разработать новые
  представления через принятые в проекте интерфейсы отображения и адаптеры.
- Использовать существующие Lucide и Storybook. Выбор шрифта, темы, радиусов и плотности включить
  в новый визуальный прототип. Рекомендация библиотеки не фиксирует нынешнюю палитру.

У shadcn часть поведения и сопровождения остаётся нашей ответственностью. Если главная цель владельца
состоит в минимуме собственного кода компонентов, Mantine заслуживает отдельного сравнения на тех же экранах.
Нельзя обещать одновременно полную свободу внешнего вида и отсутствие сопровождения локальных компонентов.

## Что проверить перед выбором и переносом

Предлагаемый следующий результат: исполнимый Storybook-прототип оболочки и трёх связанных задач.
Для первого набора подходят список продуктов с переходом в редактор, поиск оплаты с деталями
и аналитический отчёт со скриншота. Приоритет задач уточняется у владельца.

Показать две композиции на одной рекомендуемой основе: рабочее пространство с группами разделов
и более выраженную навигацию вокруг выбранного продукта. Это проверяет устройство админки,
а не только две цветовые темы. Mantine имеет смысл добавлять отдельным техническим сравнением,
если после исследования остаётся существенное сомнение именно в библиотеке.

| Проверка | Критерий принятия прототипа |
| --- | --- |
| Полнота навигации | Все текущие административные возможности достижимы на телефоне и компьютере. Выход на публичный сайт не дублирует имя административного раздела. |
| Рабочая задача | Можно найти нужную запись, открыть детали, выполнить демонстрационное действие и вернуться с сохранённым контекстом. Новые API для этого не выдумываются. |
| Малый экран | Проверены 320, 390 и 768 CSS px, длинные русские подписи, экранная клавиатура и фиксированные панели. Основная работа не требует горизонтальной прокрутки всей страницы. |
| Компьютер | Проверены 1280 и 1440 CSS px. Заголовки, поиск, фильтры, основное действие и детали имеют устойчивое положение. |
| Доступность | Видимый focus, работа с клавиатурой, управление закрытием overlays, ошибки у нужных полей, состояние сохранения объявляется программно, reduced motion. |
| Размер нажатия | Цель для основных сенсорных действий, 44 × 44 CSS px. Это проектная цель удобства. [WCAG 2.2 AA 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) устанавливает 24 × 24 CSS px с исключениями, а не обязательные 44. |
| Масштабирование | Проверены 200% увеличения текста и [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), без потери действий и значений. Для сложной таблицы допустим отдельный прокручиваемый регион, но не единственный способ выполнить основную задачу. |
| Состояния | Обычные данные, длинные значения, пустой результат, загрузка, ошибка с повтором, отсутствие доступа, несохранённые изменения и конфликт, где применимо. |
| Прозрачность | Демо-данные отмечены. Нет выдуманных процентов, выручки, графиков и неработающих элементов, выдаваемых за интегрированные. |

После выбора композиции требуется визуальная приёмка по
[frontend delivery](../agents/frontend-delivery.md), затем перенос производственных модулей
с сохранением доменного поведения. Редизайн можно выпускать последовательно: новая оболочка,
контент, продажи и доступ, затем коммуникации и аналитика. Каждая область должна получать
законченную рабочую задачу и состояния, чтобы переделка не осталась смесью разных интерфейсов.

интерактивный прототип не создавался, production UI и продуктовые контракты не изменены.
Совместимость внешних библиотек с закреплёнными версиями проекта должна подтверждаться
