# Историческое шифрование pgBackRest: оценка доказательств и план сохранения восстановления

Дата: 21.10.2026. Задача: [#1627](https://github.com/sachkov-inside/platform/issues/1627).
Это исследование и проект решения, без доступа к production и без изменения repository,
stanza, cipher, retention, credentials или backup sets. Секреты и пользовательские записи
не извлекались. Исполнимые команды remediation здесь намеренно не задаются.

## Вывод

Имеющиеся сведения подтверждают работоспособность выбранных backup/restore, но **не доказывают
качество исторических подключей и солей**. Подключ означает внутренний ключ pgBackRest,
отдельный от пользовательской passphrase repository. Свидетельств слабого ключа или утечки
также не получено. Статус исторического шифрования: **качество не установлено**.

Обновление production и новая full copy завершены отдельно в #1579. Его закрытие и перенос
остатка в #1627 не являются security acceptance. `rngFailureVerified=false` сохраняется.
Действует STOP владельца: остановленный эксперимент не повторять, не исследовать и не
проектировать его выполнение или альтернативные механизмы. Успешные backup/restore, upstream CI
и ссылки его не заменяют. Дальнейшее решение о приёмке этого незакрытого пункта требует
отдельного решения владельца, без предложения обойти STOP.

## Что сообщает официальный advisory

[Weak Encryption Subkeys and Salts, 04.10.2026](https://pgbackrest.org/news.html#weak-encryption-subkeys-and-salts)
описывает версии до 2.59.3: ошибка получения случайных данных могла остаться незамеченной
и привести к слабым подключам и солям. Затронуто шифрование repository.

Подключи `archive.info` и `backup.info` возникают при `stanza-create` и живут всю жизнь stanza.
Upgrade их не заменяет. Первый защищает WAL; второй защищает manifests, содержащие подключи
данных backup, в том числе новых. Full backup получает собственный подключ данных, который
наследуют его differential/incremental копии. Поэтому новая full copy не заменяет подключи stanza.

Слабая соль сама не раскрывает подключ, но может раскрывать совпадение данных и до восьми
байтов прежнего содержимого памяти. Старые соли и подключи данных уходят с истечением
соответствующих backup/WAL. Advisory рекомендует версию ≥2.59.3, новую full copy и, при слабом
подключе stanza, новую stanza в новом repository с сохранением нужной старой истории.

Описанный upstream признак слабости, ≥6 нулевых байтов подключа, не является доказательством
случайности при отсутствии признака. Для возможных сборок до 2.53 с OpenSSL 1.0 advisory отдельно
указывает недетектируемый этим способом случай. В этой работе подключи не проверялись,
команды их извлечения не запускались и не воспроизводятся.

Время в labels описывает backup chain, а не дату создания stanza. Дата появления Dockerfile или
runbook в Git тоже не доказывает время исполнения `stanza-create`. Самый ранний приведённый
здесь backup label не объявляется первым backup за жизнь stanza.

## Что остаётся неизвестным

1. Точная дата и происхождение действующей stanza, её переносы/пересоздания и идентичность
   repository на всём историческом интервале.
2. Binary/image и OpenSSL, фактически создававшие её подключи, а также полная цепочка прежних
   окружений. Нынешняя версия библиотеки не доказывает историческую.
3. Качество подключей stanza, подключей каждого retained full set и солей его файлов/WAL.
   Backup, который можно расшифровать, может быть зашифрован слабым ключом.
4. Полный текущий список retained full/diff/incr sets, их зависимости, границы WAL/PITR,
   условия автоматического истечения и требуемый владельцем срок сохранения истории.
   PITR означает восстановление на выбранный момент с применением WAL.
5. Наличие независимых копий старого ciphertext и прежних выгрузок. Будущая замена ключей
   не устраняет риск уже существующих копий.

Датированные restore receipts не заменяют текущий inventory. По ним нельзя объявлять старую
историю удалённой, все retained sets проверенными или все периоды восстановления покрытыми.

## Проект решения с сохранением истории

Следующие этапы **не разрешены к исполнению этим документом**. Это отдельная будущая работа.
Рекомендуемый путь при сохраняющейся неопределённости: новая stanza в отдельном repository
для будущих копий, нужную прежнюю историю сохранить отдельно до явного решения о её судьбе.
Это рекомендация по ограничению риска, а не утверждение о найденном слабом подключе.

### Gate 1. Владелец определяет нужную историю и границу риска

Зафиксировать самые ранние необходимые точки восстановления, срок хранения и допустимый
период риска неизвестного исторического шифрования. Отдельно принять конкретный HIGH результат
и объём будущей операции. Запуск этой исследовательской сессии такого принятия не даёт.
Не менять retention и не запускать истечение ради упрощения перехода.

Подготовить только разрешённый несекретный inventory: идентификаторы repository/stanza без
credentials, labels, типы и даты backup, parent dependencies, доступные интервалы WAL, версии
создателей из сохранившихся журналов, ссылки на receipts. Дату stanza подтверждать отдельным
журналом, а при его отсутствии оставить неизвестной. Содержимое info/manifests, ключи,
passphrases, dumps и пользовательские записи не публиковать и не извлекать для анализа ключей.
Получение новых сведений с production требует отдельной согласованной границы чтения.

### Gate 2. Принять конкретный план перехода, отката и обращения с секретами

Для нового repository заранее определить отдельное место хранения, бюджет, доступы,
шифрование, сохранность recovery credentials и владельца операции. Новые credentials и
production configuration требуют отдельного разрешения. Старые ключи сохранить по действующей
защищённой процедуре для восстановления, не публикуя их и не вращая их в рамках исследования.

Проект перехода должен исключать перезапись старой stanza, разрыв текущей архивации WAL и
неявное удаление старой истории. До переключения нужны проверенный старый recovery path,
план возврата архивации и резерв ёмкости. Конкретные изменения timers, archive routing,
retention и возможный перерыв вынести на принятие владельцу до выполнения.

[Официальное руководство](https://pgbackrest.org/user-guide.html) описывает зависимости backup,
WAL и retention, а также несколько repositories. Эти возможности сами по себе не доказывают
безопасность конкретного перехода. Изменение шифрования существующей stanza не подменяет
создание новой. Копирование прежнего ciphertext в новое место не создаёт новые подключи.

### Gate 3. Проверить восстановление до признания перехода успешным

После отдельно разрешённого создания нового repository/stanza на исправленном binary
получить новую full copy и доказать поступление нужного WAL. Затем восстановить её в
изолированном окружении, без published ports, приложений и consumers. Проверить все три БД,
схему и сохранность данных штатной закрытой сверкой; наружу сохранить только агрегаты,
labels, версии, digest, exit codes и ограничения. Проверить выбранную точку PITR, а не только
старт PostgreSQL. Ресурсы и временные секретные файлы убрать с отдельной квитанцией очистки.

Для необходимой старой истории сохранить полные зависимости full/diff/incr, metadata и WAL,
достаточные для выбранных точек. [Руководство pgBackRest](https://pgbackrest.org/user-guide.html)
поясняет, что incremental зависит от предшествующей цепочки, а restore требует WAL.
Проверить восстановление старой истории по принятому покрытию, включая границу перехода.
Пропуски отметить как непроверенные. Новая full copy не содержит состояния БД на прошлые даты
и не заменяет этот этап. Публичный отчёт не должен содержать пользовательские данные.

Успех operational restore подтверждает восстановимость, но не ретроспективную случайность
ключей. При провале новой копии, WAL или restore переход не принимать, старую историю
сохранять, возврат проводить только по согласованному плану.

### Gate 4. Отдельно решить судьбу старого repository и остаток приёмки

Утвердить дату и основание окончания хранения каждой нужной цепочки только после доказанного
нового recovery path и покрытия требуемых старых точек. До этого старый repository сохраняется
как необходимая история с явно записанным неизвестным качеством шифрования. Любое дальнейшее
ограничение записи, изменение retention или удаление требует отдельного разрешения.
Удаление backups не считать доказательством качества их прежнего шифрования.

В #1627 раздельно сохранять: выполненный binary upgrade, выполненные обычные restore,
неустановленное историческое шифрование, разрешение/исполнение будущего перехода и
`rngFailureVerified=false`. Решение владельца о дальнейшем статусе RNG-пункта запросить
отдельно, не предлагая выполнения запрещённого эксперимента. До разрешения незакрытых
критериев security acceptance не объявляется GREEN.
