# Свидетельства задачи #670: переходы между страницами

Замеры сняты набором `pnpm --filter @inside/web test:navigation` на production-сборке web с
подставным backend (`apps/web/test/navigation`). Backend намеренно замедлен на 700 мс, чтобы было
видно, что человек видит, пока страница идёт; в снимках задержка 1,5 секунды. Общий кеш сервера
сброшен перед каждой проверкой, а каждый переход начинается с устоявшейся страницы: её личная часть
уже пришла. Переход, начатый раньше, ждёт эту часть (ADR 0026, «Цена решения») — этот случай в
замеры не входит.

«До» — тот же набор на коде без изменений: каталог `apps/web/test/navigation` и
`playwright.navigation.config.ts` скопированы во временный worktree на `main` (`0e0676d2`), где
скрипта `test:navigation` ещё нет, поэтому набор запущен из `apps/web` напрямую:

```bash
NAVIGATION_EVIDENCE_STAGE=before UPDATE_EVIDENCE=issue-670 \
  pnpm exec playwright test --config playwright.navigation.config.ts
```

Каталог `before/` затем перенесён сюда. Утверждения там падают, а замеры, записанные до них,
остаются. Двух замеров для «до» нет: предзагрузка по намерению записывается после своего
утверждения, а Core Web Vitals ждут отметку `inside:web-vital:CLS`, которую ставит только код
ветки. «После» — ветка задачи.

Что изменилось:

- вместо одной серой плашки с подвалом под ней переход сразу показывает рамку своей страницы, а
  шапка урока и состав программы настоящие с первого кадра;
- повторный переход в окне 60 секунд, «назад», «вперёд» и возврат на уже открытую Главную не
  делают ни одного запроса и готовы за 14–77 мс; раньше возврат на Главную занимал 30–753 мс;
- наведение или касание ссылки приносит общую часть урока до нажатия: переход готов за 87–146 мс
  при backend в 700 мс;
- время «до готовности» на первом переходе по-прежнему ограничено ответом backend: закрытое тело и
  личная часть не кешируются, а общая часть при сброшенном кеше читается заново. Разброс строк
  «первый раз» складывается из этих чтений и задержки React до 300 мс между скелетом и содержимым
  (`FALLBACK_THROTTLE_MS`).

Столбцы: какой скелет побывал на экране, сколько запросов RSC сделал переход, сколько прошло до
готовой страницы. «До первого кадра» — отметка `inside:navigation`: от нажатия до отрисовки нового
адреса. Core Web Vitals сняты за цикл «программа ↔ урок» с «назад» и «вперёд».

Снимки лежат рядом: `before/` и `after/`, для компьютера и телефона — скелет перехода в урок, готовый
урок, возврат в программу и готовая программа. Готовые страницы на обеих стадиях выглядят одинаково:
менялся путь к ним, а не они сами. Истории «LoadsInPlace» в Storybook проверяют, что скелет, общая
часть и готовая страница не двигают друг друга.
