# #609: очередь React при повторном открытии меню

Предупреждение возникает из-за вложенного синхронного `act` в тестовой обвязке.
Компонент редактора не приостанавливается на Promise. История теперь ждёт завершения
активации меню и возвращения фокуса после вставки блока. Production-код не меняется.

## Доказательство причины

Минимальный воспроизводящий сценарий: открыть меню, вставить «Совет», сменить вид на
«Важно», вставить название, повторно открыть меню. В [логе](reentrant-act.log) сообщение
приходится на второе открытие. В этот момент `queue.length=2`, `didUsePromise=false`,
`isFlushing=true`.

Цепочка вызовов:

```text
MaterialDocumentEditorView: useEffect для menuOpen
  searchInput.current?.focus()
    user-event: patchedFocus → dispatchDOMEvent
      Storybook: eventWrapper → синхронный React.act
        flushActQueue: повторный вход, isFlushing=true
        очередь остаётся непустой → сообщение о suspended component
```

Источники на зависимостях из `pnpm-lock.yaml`:

- `react@19.3.0/cjs/react.development.js`: `flushActQueue` не выполняет очередь при
  `isFlushing=true`; синхронная ветка `act` проверяет `queue.length`, не признак Suspense.
- `@storybook/react@10.6.1/dist/_browser-chunks/chunk-7HUHAOMV.js`: `eventWrapper`
  возвращает результат события и не ждёт thenable, который вернул `act`.
- `widgets/material-authoring/ui/material-document-editor.client.tsx`: эффект `menuOpen`
  фокусирует поиск. Кнопка открытия через `onPointerDown.preventDefault()` сохраняет
  прежний фокус; её `onClick` меняет только `menuOpen` и `menuSearch`.

## Изменение и проверка возврата

История активирует настоящую кнопку через `.click()` внутри ожидаемого асинхронного `act`.
Callback возвращает `Promise.resolve()`, чтобы React использовал асинхронную ветку и
дождался своей очереди. Для этого собственного `act` история временно включает
`IS_REACT_ACT_ENVIRONMENT=true`, как обвязка Storybook, затем восстанавливает прежнее
значение. Это включает проверки React.

После вставки «Совета», «Итогов» и «Ресурса» история ждёт фактического фокуса редактора.
Tiptap возвращает его через `requestAnimationFrame`; наличие узла в документе ещё не
означает, что фокус уже вернулся. Открытое меню проверяет фокус поля «Найти блок».

Spy на `console.error` вызывает настоящую консоль. В конце `play` история проверяет
отсутствие ошибок; `finally` восстанавливает консоль и при падении. Возврат исходного
`openMenu` при сохранённых ожиданиях фокуса даёт красную проверку на исходном сообщении.
Проверка в cleanup `beforeEach` была нечувствительной к этой мутации и удалена.

```bash
pnpm --filter @inside/web test:storybook \
  src/_pages/material-authoring/ui/material-authoring-page.stories.tsx \
  -t 'Редактор · блоки урока'
```

## Метод измерения CI

[timings.json](timings.json) сохраняет длительности из нативного JSON reporter Vitest:
`assertionResults.duration` измеряет всю задачу, включая hooks и проверки доступности.
Это не самодельный замер только `play`. Значения успешных задач сохраняются без порога.

Каждый полный прогон содержит 73 файла и 585 историй, включая неизменённые соседние
истории редактора. Исходные прогоны 37483174033 и 37483163930 принадлежат одному
временному окну. Их нельзя считать независимыми наблюдениями.

Парные задания `before` и `after` используют одни зависимости и один набор файлов.
Для `before` восстановлен только исходный файл истории с `eb5656c5`.
`after` проверяет исправленную историю. Во втором парном эксперименте каждый раннер
выполняет полный набор сначала с обычным параллелизмом, затем с `--no-file-parallelism`.
В первом окне режим без параллелизма идёт вторым; это сравнение не исключает влияние порядка.
Дополнительный эксперимент после 15:50 UTC меняет порядок на serial → parallel.

Число перекрывающихся файлов получено из их `startTime` и `endTime` в отчёте Vitest.
Это число одновременно измеряемых файлов, а не догадка о внутренних воркерах браузера.
Список соседей охватывает интервал всего файла редактора, а не только историю блоков.

Временный reporter и задания измерения сняты до merge. Обязательные гейты,
таймауты и число повторов тестов не меняются.

## Результаты

В обычном полном прогоне до исправления получены 1283,8–2288,1 мс: пять измерений
в двух временных окнах 14:58–15:25 и 15:50–15:57 UTC. После исправления получены
1354,7–1878 мс: три измерения в тех же двух окнах. Уменьшение хвоста этими измерениями не подтверждено. Это диапазон
наблюдённых значений, а не оценка всего распределения.

В первом окне последний парный прогон выполняет оба режима в порядке parallel → serial:

| История | До, параллельно | До, последовательно | После, параллельно | После, последовательно |
| --- | ---: | ---: | ---: | ---: |
| Редактор · блоки урока | 1399,1 мс | 954,0 мс | 1878,0 мс | 1092,1 мс |
| Редактирование и автосохранение | 2201,9 мс | 1742,9 мс | 3398,3 мс | 2080,5 мс |
| Вложенное изображение · форма вложения | 891,4 мс | 567,5 мс | 1066,5 мс | 919,5 мс |

Оба раннера предоставили четыре CPU. Число перекрывающихся файлов изменилось с трёх
до одного. История блоков в последовательном режиме короче на 445,1 мс до исправления
и на 785,9 мс после. Неизменённые соседние истории также различаются между раннерами
и режимами. Поэтому предупреждение не объясняет весь разброс: он остаётся без предупреждения
и зависит от условий полного прогона. Это сравнение само по себе не отделяет параллелизм от порядка запуска.

Кандидат из #602 уже устранён на исходном `eb5656c5`: редактор читает `useEditorState`,
а `useMaterialBlockControls` планирует замеры по изменению положения, а не на каждую
транзакцию. Эта задача не возвращает полную перерисовку и не меняет production-редактор.

Конкретные падения старого дерева по 15000 мс не воспроизведены. Исходные зависимости, сам редактор
и состав набора изменились после наблюдений 12.09.2026: сейчас 73 файла вместо 111.
Эти замеры не оценивают частоту редких пересечений старого порога.

Источники CI:

- [Исходный PR-прогон](https://github.com/sachkov-inside/platform/actions/runs/37483174033)
  и [исходный ручной прогон](https://github.com/sachkov-inside/platform/actions/runs/37483163930):
  UI прошёл; временная выгрузка замеров нарушила контракт workflow, поэтому весь CI красный.
- [Первый парный эксперимент](https://github.com/sachkov-inside/platform/actions/runs/37485549965):
  обе измерительные задачи прошли.
- [Парный эксперимент с последовательным режимом](https://github.com/sachkov-inside/platform/actions/runs/37486433751):

- [Контроль другого окна и CPU](https://github.com/sachkov-inside/platform/actions/runs/37489433034):
  четыре полных прогона по 585 историй и четыре контрольных по 27 историй прошли.

Их присутствие временно нарушило контракт выпуска, требующий перечислить все jobs CI в gate.
До merge исходный workflow восстановлен полностью; контракт выпуска не ослаблен.

## Контроль CPU в отдельном окне

[Диагностический скрипт](https://github.com/sachkov-inside/platform/blob/56450e24ad4f5dd28499e9bdd80f6908fad842d5/scripts/storybook-609-experiment.sh)
возвращает в копии истории три исходных посимвольных ввода из `c2d67be0^`.
Каждый ввод повторяется 12 раз через `userEvent.clear` и `userEvent.type` с `delay:null`.
Итоговые значения и проверки сохраняются. Это 564 набранных знака вместо исходных 47;
утяжеление состоит из реальных транзакций редактора, без фиксированных пауз.
Production-код, включая исправление #602, остаётся прежним.

Node и его Chromium получают одно доступное ядро через `taskset` в обоих случаях.
В случае `loaded` два отдельных процесса непрерывно вычисляют на том же ядре.
В случае `idle` этих процессов нет; это отсутствие добавленной нагрузки, а не гарантия
отсутствия внешней нагрузки виртуального раннера. Скрипт завершает оба процесса после прогона.
`before` выполняет loaded → idle, `after` выполняет idle → loaded.

Каждый контрольный прогон проверяет все 27 историй файла. Нативный reporter измеряет всю
задачу и неизменённые соседние истории. Диагностический `--testTimeout=120000` не обрезает
значения по историческим 15000 мс. Этот параметр действует только во временном задании;
финальная конфигурация тестов не меняется.

### Контроль порядка полного набора

В окне 15:50–15:57 UTC полный набор идёт в обратном порядке serial → parallel:

| История | До, последовательно | До, параллельно | После, последовательно | После, параллельно |
| --- | ---: | ---: | ---: | ---: |
| Редактор · блоки урока | 1210,9 мс | 2288,1 мс | 800,7 мс | 1354,7 мс |
| Редактирование и автосохранение | 1780,4 мс | 2446,6 мс | 1637,4 мс | 2074,2 мс |
| Вложенное изображение · форма вложения | 669,5 мс | 1758,5 мс | 588,6 мс | 1364,3 мс |

В обоих порядках параллельный полный набор медленнее последовательного для всех трёх
историй. Порядок сам по себе не объясняет эту разницу. Перекрытие файлов меняется
с одного до трёх; состав соседей сохранён в JSON. Здесь число файлов выступает
наблюдаемым контекстом, а следующий эксперимент непосредственно меняет доступ к CPU.

### Контроль конкуренции за одно ядро

| История | До, idle | До, loaded | После, idle | После, loaded |
| --- | ---: | ---: | ---: | ---: |
| Редактор · блоки урока, 12 вводов | 8629,5 мс | 51363,0 мс | 7502,3 мс | 37036,1 мс |
| Редактирование и автосохранение | 2594,5 мс | 6316,2 мс | 2309,3 мс | 5231,4 мс |
| Вложенное изображение · форма вложения | 781,0 мс | 3562,7 мс | 769,2 мс | 2608,7 мс |

Конкуренция за CPU увеличила длительность утяжелённой истории в 5,95 раза до исправления
и в 4,94 раза после. Оба loaded-прогона пересекли 15000 мс; оба idle-прогона остались
ниже. Все проверки прошли. После исправления предупреждения нет, включая loaded-прогон
на 37036,1 мс. В исходной истории предупреждение осталось в обоих режимах.

Следовательно, конкуренция за CPU является установленным механизмом долгого хвоста
реальных действий редактора: одинаковая работа без неё укладывается в порог, а с ней
пересекает его даже без предупреждения. Это не доказательство, что именно два процесса
нагружали конкретный раннер сентября. Состояние того раннера не сохранено.
Обычный полный набор в двух порядках показывает тот же знак замедления при совместном
выполнении файлов; контроль CPU проверяет механизм отдельно от порядка.

Устранение предупреждения не устраняет чувствительность к доступному CPU. Числа до/после
получены на разных раннерах, поэтому разницу 51363 → 37036 мс нельзя целиком приписать
исправлению `act`. Неизменённые соседние истории тоже быстрее на after-раннере.
Два временных окна и управляемая нагрузка не оценивают p95 или частоту редких падений.
