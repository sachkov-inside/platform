# #609: очередь React при повторном открытии меню

Предупреждение возникает из-за вложенного синхронного `act` в тестовой обвязке.
Компонент редактора не приостанавливается на Promise. История теперь ждёт завершения
активации меню и возвращения фокуса после вставки блока. Production-код не меняется.

## Доказательство причины

Минимальный воспроизводящий сценарий: открыть меню, вставить «Совет», сменить вид на
«Важно», вставить название, повторно открыть меню. В [логе](reentrant-act.log) сообщение
приходится на второе открытие. В этот момент `queue.length=2`, `didUsePromise=false`,
`isFlushing=true`.

Цепочка вызовов:

```text
MaterialDocumentEditorView: useEffect для menuOpen
  searchInput.current?.focus()
    user-event: patchedFocus → dispatchDOMEvent
      Storybook: eventWrapper → синхронный React.act
        flushActQueue: повторный вход, isFlushing=true
        очередь остаётся непустой → сообщение о suspended component
```

Источники на зависимостях из `pnpm-lock.yaml`:

- `react@19.3.0/cjs/react.development.js`: `flushActQueue` не выполняет очередь при
  `isFlushing=true`; синхронная ветка `act` проверяет `queue.length`, не признак Suspense.
- `@storybook/react@10.6.1/dist/_browser-chunks/chunk-7HUHAOMV.js`: `eventWrapper`
  возвращает результат события и не ждёт thenable, который вернул `act`.
- `widgets/material-authoring/ui/material-document-editor.client.tsx`: эффект `menuOpen`
  фокусирует поиск. Кнопка открытия через `onPointerDown.preventDefault()` сохраняет
  прежний фокус; её `onClick` меняет только `menuOpen` и `menuSearch`.

## Изменение и проверка возврата

История активирует настоящую кнопку через `.click()` внутри ожидаемого асинхронного `act`.
Callback возвращает `Promise.resolve()`, чтобы React использовал асинхронную ветку и
дождался своей очереди. Для этого собственного `act` история временно включает
`IS_REACT_ACT_ENVIRONMENT=true`, как обвязка Storybook, затем восстанавливает прежнее
значение. Это включает проверки React.

После вставки «Совета», «Итогов» и «Ресурса» история ждёт фактического фокуса редактора.
Tiptap возвращает его через `requestAnimationFrame`; наличие узла в документе ещё не
означает, что фокус уже вернулся. Открытое меню проверяет фокус поля «Найти блок».

Spy на `console.error` вызывает настоящую консоль. В конце `play` история проверяет
отсутствие ошибок; `finally` восстанавливает консоль и при падении. Возврат исходного
`openMenu` при сохранённых ожиданиях фокуса даёт красную проверку на исходном сообщении.
Проверка в cleanup `beforeEach` была нечувствительной к этой мутации и удалена.

```bash
pnpm --filter @inside/web test:storybook \
  src/_pages/material-authoring/ui/material-authoring-page.stories.tsx \
  -t 'Редактор · блоки урока'
```

## Метод измерения CI

[timings.json](timings.json) сохраняет длительности из нативного JSON reporter Vitest:
`assertionResults.duration` измеряет всю задачу, включая hooks и проверки доступности.
Это не самодельный замер только `play`. Значения успешных задач сохраняются без порога.

Каждый полный прогон содержит 73 файла и 585 историй, включая неизменённые соседние
истории редактора. Исходные прогоны 37483174033 и 37483163930 принадлежат одному
временному окну. Их нельзя считать независимыми наблюдениями.

Парные задания `before` и `after` используют одни зависимости и один набор файлов.
Для `before` восстановлен только исходный файл истории с `eb5656c5`.
`after` проверяет исправленную историю. Во втором парном эксперименте каждый раннер
выполняет полный набор сначала с обычным параллелизмом, затем с `--no-file-parallelism`.
Режим без параллелизма всегда идёт вторым; сравнение не исключает влияние порядка запуска.

Число перекрывающихся файлов получено из их `startTime` и `endTime` в отчёте Vitest.
Это число одновременно измеряемых файлов, а не догадка о внутренних воркерах браузера.
Список соседей охватывает интервал всего файла редактора, а не только историю блоков.

Временный reporter и задания измерения сняты до merge. Обязательные гейты,
таймауты и число повторов тестов не меняются.

## Результаты

В обычном полном прогоне до исправления получены 1283,8–1857 мс: четыре измерения
в трёх временных срезах. После исправления получены 1802,5–1878 мс: два измерения
в двух срезах. Уменьшение хвоста этими измерениями не подтверждено. Это диапазон
наблюдённых значений, а не оценка всего распределения.

В последнем парном прогоне каждый раннер выполняет оба режима:

| История | До, параллельно | До, последовательно | После, параллельно | После, последовательно |
| --- | ---: | ---: | ---: | ---: |
| Редактор · блоки урока | 1399,1 мс | 954,0 мс | 1878,0 мс | 1092,1 мс |
| Редактирование и автосохранение | 2201,9 мс | 1742,9 мс | 3398,3 мс | 2080,5 мс |
| Вложенное изображение · форма вложения | 891,4 мс | 567,5 мс | 1066,5 мс | 919,5 мс |

Оба раннера предоставили четыре CPU. Число перекрывающихся файлов изменилось с трёх
до одного. История блоков в последовательном режиме короче на 445,1 мс до исправления
и на 785,9 мс после. Неизменённые соседние истории также различаются между раннерами
и режимами. Поэтому предупреждение не объясняет весь разброс: он остаётся без предупреждения
и зависит от условий полного прогона. Сравнение не отделяет параллелизм от порядка запуска.

Кандидат из #602 уже устранён на исходном `eb5656c5`: редактор читает `useEditorState`,
а `useMaterialBlockControls` планирует замеры по изменению положения, а не на каждую
транзакцию. Эта задача не возвращает полную перерисовку и не меняет production-редактор.

Падения старого дерева по 15000 мс не воспроизведены. Исходные зависимости, сам редактор
и состав набора изменились после наблюдений 12.09.2026: сейчас 73 файла вместо 111.
Эти замеры не оценивают частоту редких пересечений старого порога.

Дополнительные измерительные задачи последних двух экспериментов не входили в `CI Gate`.
Их присутствие временно нарушило контракт выпуска, требующий перечислить все jobs CI в gate.
До merge исходный workflow восстановлен полностью; контракт выпуска не ослаблен.
