# Telegram-коммуникации Inside v1

Статус: продуктовая модель согласована владельцем 2026-09-06 в
[решении #120](https://github.com/sachkov-inside/workspace/issues/120), авторский путь уточнён
в [#125](https://github.com/sachkov-inside/workspace/issues/125) и
[#129](https://github.com/sachkov-inside/workspace/issues/129).
[Specification #119](https://github.com/sachkov-inside/workspace/issues/119) ведёт delivery;
[цель #118](https://github.com/sachkov-inside/workspace/issues/118) остаётся в Human Backlog.
Это контракт первой версии, не свидетельство реализации, готовности авторского контента или запуска.

## Результат и граница

Один существующий бот Inside знакомит зрителя с продуктом и направляет на конкретные опубликованные
материалы и серии Platform. Обычная ссылка запускает стандартную воронку, тематические ссылки —
свои сценарии. Владелец и его агент управляют сообщениями, расписанием, обновлениями и разовыми
рассылками. Новые шаги доходят и до тех, кто раньше завершил воронку.

Platform остаётся единственной authority контента и доступа. Бесплатный материал доступен без
обязательной регистрации; marketing entry не создаёт Account, browser session или Membership.
Слово «мастерская» здесь означает нынешний Inside, а не отдельную Workshop surface, которую отменило [ADR 0033](../adr/0033-product-tariff-payment-model.md).
Актуальные Material/Series и порядок чтения описаны в
[контексте серий](../product/series-planning-handoff.md).

В v1 нет AI-диалогов, графового конструктора, условных ветвлений, A/B движка, нового billing,
платных отдельных серий, альбомов, опросов или сегментации по статусу Membership. Сообщения
одинаковы для оплативших и неоплативших. Авторский контент готовится отдельно; разработка использует
явные тестовые примеры. Оплата, чтение и удержание не выводятся из кликов.

## Владельцы состояния и доступ

- **Telegram application:** заготовки, определения и опубликованные ревизии коммуникаций,
  ссылки источников, участие, предпочтение marketing on/off, расписание, delivery history,
  разовые рассылки, события входа и статистика отправок. Один сохраняемый runtime, не in-memory timers.
- **Platform:** Account и разрешения; серверный owner facade, UI, MCP, контентные адреса и
  приём переходов. Данные Telegram читаются через versioned authenticated API, не через shared DB
  или source imports. Platform не хранит вторую изменяемую копию сценариев и не запускает scheduler.
- **Workspace:** этот cross-repository контракт. Детальные application interfaces, схемы,
  миграции, тесты и runbooks принадлежат приложениям. Контрактные fixtures vendored в каждом repo;
  сборка не зависит от соседнего checkout или доступности Workspace.

В Platform вводится отдельное разрешение `communications:manage`, проверяемое тем же Accounts
механизмом, что остальные permissions. `materials:manage` не даёт его автоматически. HTTP UI и
MCP вызывают одни application operations от authenticated Account. Агент имеет полный набор
операций владельца, включая publish, launch, pause, resume, skip и explicit retry; дополнительный
ручной UI gate для агента не вводится. API сохраняет actor, operation ID и ревизию операции.

Telegram author intake доступен только Telegram identity, доказанно связанной с Account с актуальным
`communications:manage`. Нужен узкий service-authenticated вызов Platform для такой проверки;
username, forward origin и знание ID заготовки не подтверждают право. Service-to-service запросы
используют существующий authentication механизм приложений и bounded actor context; конфигурацию
секретов не переносить в tracker. Неизвестный/неподтверждённый автор не может записывать заготовки.
Функция делегирования агенту не разрешает любому BotContact вызывать admin API.

При реализации этих границ нужны passing/negative contract fixtures: поддельный actor, отсутствующее
разрешение, отозванный доступ, чужой template ID, stale revision и повтор operation ID. Это ближайшие
fitness checks seam; физический transport/schema уточняется первым enabling ticket без новых
продуктовых решений.

## Сохранённые посты и создание воронок

Основное место подготовки исходного текста и медиа — Telegram. Владелец явно открывает авторское
меню, присылает поддерживаемое сообщение, настраивает URL-кнопки и сохраняет пост. Бот, веб-админка
и delegated agent используют одну библиотеку постов и одни операции. Пост — та же versioned
заготовка (`templateId`), а не новый независимый тип содержимого. Его можно использовать в общем
знакомстве, непосредственном ответе воронки, её отложенных шагах и разовой рассылке.

1. В обычной переписке сообщение не становится постом или рассылкой. Авторский режим и каждое
   действие требуют подтверждённую Telegram identity и текущее `communications:manage`.
   Повтор Telegram update не создаёт вторую запись или отправку.
2. Форматы: text, photo, video, video_note, voice, document. Сохраняются поддерживаемые Telegram
   entities, подпись, URL-кнопки и их расположение по строкам. Кружок с пояснением — один логический
   шаг из ordered parts, например video_note и text. Неподдерживаемый контент отклоняется с понятной
   ошибкой, без усечения сообщения и без потери форматирования.
3. Пост хранит снимок текста/entities и Telegram `file_id` в контексте bot identity. Edit/delete
   исходного сообщения не меняет сохранённый пост; замена выполняется явно в авторском меню.
   Собственная копия media bytes, общий media manager и upload через Platform не требуются.
   Недействительный file reference виден как ошибка. Секретный Telegram download URL не попадает в UI.
4. Веб-админка показывает сохранённые посты и позволяет выбрать или явно заменить часть. В ней нет
   основного текстового редактора, который переписывает импортированный пост или сбрасывает entities.
   API/MCP сохраняют возможности прямой авторской подготовки через те же проверяемые операции.
5. Выбор поста копирует его текущий snapshot в часть черновика. Последующие изменения поста не
   меняют даже уже выбранную часть автоматически. При явной замене содержимого сохраняется ID
   существующей части; добавление создаёт новый ID. После publish фиксируется новая revision.
6. Образец себе — отдельное явно запрошенное действие, адресованное только подтверждённому автору.
   Web preview, выбор поста и сборка черновика ничего не отправляют. Образец готовится тем же
   механизмом содержимого и кнопок, что будущая доставка; неизвестный результат не повторяется
   автоматически. Полноценный Telegram-вид медиа проверяется этим образцом, а не имитацией в браузере.

В боте владелец открывает «Воронки», создаёт стандартный или тематический сценарий, выбирает
непосредственный ответ из постов, добавляет отложенные шаги и их части, задаёт задержки в понятных
единицах времени. Меню показывает текущую цепочку, позволяет переставить или удалить шаг/часть,
сменить пост, настроить источники, посмотреть изменения и охват, опубликовать или изменить lifecycle.
Общий intro настраивается отдельно с явным предупреждением: его Save меняет знакомство для новых
получателей, а прежним оно не повторяется.

Веб-админка удобна для обзора длинной последовательности: содержимое частей, порядок, время,
источники, состояние публикации и история доставки с explicit retry/skip. Агент помогает собрать
цепочку из сохранённых постов и вызывает те же операции. Новый scheduler, второй набор definitions,
графовый редактор и дополнительные ручные gates после действий агента не вводятся.

Публикация из бота проверяет обещанные бесплатные Materials и публичные страницы Product в Platform
по [контракту публичных целей](../integrations/communications-v1.md#funnel-management-ui). Telegram
передаёт выбранный snapshot через узкий service-authenticated boundary; Platform проверяет текущего
автора и доступность targets своим существующим механизмом. Эта проверка не читает определения
воронки обратно из Telegram во время удержания их транзакционных блокировок. Недоступный validator
или target запрещает публикацию; preview показывает причину. Ревизия защищает проверенное
содержимое от одновременной подмены. Вызов bot-local publish не становится обходом ContentAccess.

### Авторская админка рассылок

Уточнение владельца от 2026-09-06 ([Workspace #125](https://github.com/sachkov-inside/workspace/issues/125)):
полный процесс разовой рассылки доступен через `/admin` в Telegram, веб-админку и существующий
делегированный MCP. Это помощь автору, а не AI-диалог бота с подписчиками.

В боте доступны создание и явная замена сообщения, список постов, добавление/удаление URL-кнопок,
название, HTTPS-адрес и ряд кнопки. Кнопки одного ряда идут рядом, внутри ряда — в порядке добавления;
до 20 кнопок суммарно и до 8 в одном ряду. Отсутствующий ряд в старых данных сохраняет прежнюю
вертикальную раскладку. Произвольные callback-действия в содержимом поста не входят в поставку.

Автор собирает рассылку из сохранённых частей, меняет порядок и явно заменяет выбранную часть,
задаёт все контакты или объединение воронок, время и запускает рассылку. Бот явно подписывает
часовой пояс расписания (Москва, UTC+3). Пауза, продолжение, отмена и результаты используют тот же
механизм рассылок, что Platform. Перед запуском бот показывает выбранную версию и время.

Образец — отдельная явная отправка только в подтверждённый Telegram самого автора. Адресата
невозможно передать в API/MCP. Право и связь аккаунта проверяются при постановке и перед отправкой;
образцы доступны при включённой служебной доставке независимо от выключателя маркетинга.
Повтор одной команды/API operation не отправляет второй образец. Потерянный результат сохраняется
как unknown без автоматической повторной отправки. Web preview сам не отправляет сообщений.

Рассылка хранит собственный снимок выбранных частей. Правка поста, его исходного сообщения или
кнопок не меняет ни черновик, ни запланированную рассылку без явной замены части. После начала
рассылки существующие правила неизменности и suppression остаются в силе.

## Входы и общее знакомство

У каждой воронки стабильный ID; несколько source links, например для десяти роликов, могут
ссылаться на один сценарий. У source link свой стабильный код и имя источника. Ровно одна
доступная опубликованная воронка назначена стандартной до включения маркетинга.

- `/start` без аргумента запускает стандартную воронку.
- Известный marketing source запускает соответствующую воронку, сохраняя остальные участия.
- Auth/link/sign-in payload имеют отдельное пространство значений и обработчики. Они не запускают
  воронки, не сбрасывают stop и не включают маркетинг. Повреждённый служебный token остаётся
  служебной ошибкой. Согласовать адаптер с актуальным состоянием
  [sign-in #116](https://github.com/sachkov-inside/workspace/issues/116), а не старым checkout.
- Неизвестный, архивный или временно выключенный marketing source даёт понятный ответ и кнопку
  общего знакомства. Это не скрытая подписка на другой сценарий; нажатие запускает обычный вход.

При первом marketing entry отправляется общий блок знакомства, затем сразу тематическая ссылка
или начальный ответ стандартной воронки. Тематический вход сам по себе не зачисляет в полную
стандартную воронку. Общий блок — одно общее сообщение/набор частей со стабильным ID, доставляемый
один раз на контакт. Его edit не повторяет отправку. Параллельные входы сериализуют его доставку.

Непосредственный ответ на осознанный повтор source link возвращает материал, не сбрасывая
расписание и не повторяя знакомство. Повтор одного update вообще не повторяет ответ. Если маркетинг
выключен пользователем, запрошенная навигационная ссылка доступна, но общие/отложенные сообщения
не включаются. Повторный source entry может сохранить участие с выключенной доставкой.

## Ревизии и сроки

Воронка имеет draft, published revision и отдельный lifecycle published/paused/archived.
Не перезаписывать published snapshot при autosave. Publish сравнивает expected revision,
валидирует содержание/доступность обещанных free targets и показывает diff, ожидаемый охват и
досылку. Это информационный preview, а не обязательное ручное подтверждение после агента.
Один publish operation ID приводит к одному результату, даже при повторе запроса.

Шаг имеет неизменный `stepId`, порядок, неотрицательную задержку и список частей. История отправки
использует contact + funnel + step ID, а не текст/hash, позицию или revision. Каждая часть имеет
стабильный ID в снимке отправки; частично отправленный шаг нельзя повторить целиком.

В одной воронке одновременно исполняется не более одного шага. Следующий выбирается по текущему
опубликованному порядку среди ещё не завершённых/не подавленных шагов. Для шага без активной попытки:

`dueAt = max(enrolledAt, step.firstPublishedAt, previousCompletionAt) + delay`

Для первого шага `previousCompletionAt` отсутствует. Для следующих это фактическое завершение
предыдущего исполнявшегося шага данного участия, даже если после reorder их позиции поменялись.
Initial entry response имеет нулевую задержку; запланированные шаги идут после его завершения.

Завершение multipart шага — подтверждённая отправка всех его частей, явный skip оператором либо
terminal partial/cancelled после отмены оставшихся частей. Для skip/cancel сохраняется отдельный
результат, не sent. `previousCompletionAt` — момент фиксации terminal результата; от него начинается
задержка следующего шага. Partial/cancelled становится terminal только когда нет in-flight/unknown
частей. Cancel request запрещает новые части, но ждёт результата уже начатых или явного решения
unknown. Обычный content edit сохраняет snapshot уже начатого шага; отмена частей требует явного
delete/cancel. Unknown/failed часть без такого разрешения блокирует следующие части и шаги этой
воронки, не всю систему.

Общего дневного предела и тихих часов нет. Разные воронки и разовая рассылка могут отправляться
рядом. Транспорт всё равно соблюдает Telegram per-chat/global limits и `retry_after`; задержки от
фактической отправки не компенсируются ускорением следующих шагов. Между частями одного логического
шага действует только техническая очередь Telegram.

## Изменения для прежней аудитории

- **Добавление ID:** новый шаг получают все участники воронки, включая завершивших, кроме
  остановивших маркетинг и технически недоступных. Новый шаг с задержкой день, добавленный после
  месячного перерыва, идёт через день от публикации. Следующий новый шаг — от предыдущего завершения.
- **Правка ID:** уже доставленное не пересылается; ещё не начавшийся шаг использует актуальный
  published snapshot. Правка задержки не меняет `firstPublishedAt`. Нужна новая рассылка исправления —
  создать новый шаг, а не сбрасывать sent marker.
- **Reorder:** изменяет порядок только ещё не начатых шагов; не требует повторить доставленное.
- **Delete:** отменяет не начатые шаги; история остаётся. Удалённый step ID нельзя переиспользовать
  для другого сообщения. Статус cancellation отличим от sent.
- **Pause/archive:** новые внешние отправки не стартуют. При pause/resume непросроченные сроки
  сохраняются, первый overdue шаг готов сразу, дальнейшие — от его реальной отправки. У archive
  старые ссылки дают fallback; восстановление только явной операцией с теми же ID/историей.
- **Rollback:** новая published revision на основе старого содержания. Уже доставленное не
  повторяется, возвращённые недоставленные старые шаги сохраняют ID/firstPublishedAt. Suppressed
  при пользовательском stop шаги не оживают. Изменения audience видны до publish.

Перед внешним dispatch атомарно проверяются current publication, lifecycle, marketing preference
и contactability. Уже начатый внешний запрос нельзя отменить задним числом. Он заканчивается с
сохранённым snapshot; явный delete/cancel может отменить ещё не начатые части. Доставленные части и
неотправленные отменённые части дают явный partial/cancelled исход, а не фиктивный полный sent.

## Общий stop и возобновление

Одна команда/кнопка выключает весь маркетинг: воронки, их новые элементы и разовые рассылки.
Служебные sign-in/link ответы сохраняются. Пользователь включает маркетинг отдельным явным
действием; `/start`, auth и Telegram unblock не являются таким действием для ранее отказавшегося.
Выбора отдельных тем/категорий нет. Факт stop проверяется повторно перед внешней отправкой.

При возобновлении пропущенное не догоняется. Чтобы отличить пропущенное от будущего при относительных
задержках, scheduler сохраняет/вычисляет **виртуальное расписание на время stop**: от последнего
реального завершения последовательно вычисляет dueAt, считая очередной dueAt виртуальным завершением
предыдущего шага. Добавления начинаются не раньше firstPublishedAt. Шаги с виртуальным dueAt не позже
resumeAt получают suppressed marker; первый будущий срок сохраняется, затем отсчёт снова идёт от
реальных отправок. Изменения опубликованного порядка до resume пересчитывают только неотправленное
по тем же правилам. История sent не изменяется. Повторный start не сбрасывает suppression.

Техническая блокировка бота отдельно означает недоступность транспорта. При возврате доступности
устаревшие маркетинговые шаги также не отправляются пачкой: применить тот же механизм suppression
для периода недоступности; явный stop при этом остаётся выключенным. Operator pause не равен
отказу пользователя и следует правилам pause выше.

## Разовые рассылки

Владелец собирает draft из сохранённых Telegram-постов; агент использует те же snapshots и
проверяемые операции подготовки содержимого. Автор задаёт аудиторию и отправку сразу либо в
будущую дату UTC (UI показывает понятное локальное время). Аудитория: все BotContacts либо объединение
участников выбранных воронок. Участник получает рассылку максимум один раз независимо от числа тем.
Статус Membership не участвует. «Все» включает и прежние BotContacts, но это не зачисляет их в воронки.

Снимок кандидатов строится при фактическом запуске, в том числе для scheduled broadcast. Один launch
operation ID имеет один audience snapshot. Контакты, пришедшие после запуска, старую рассылку не
получают. Opted-out/blocked исключены, и eligibility перепроверяется перед dispatch.
Stop/block сохраняет необратимый suppressed outcome для всех ещё не начатых частей получателя
уже запущенных рассылок, включая delayed retry; поздний resume/unblock их не восстанавливает.
Для in-flight/unknown применяется cancel-request и сохранение результата без новых автоматических
попыток. Будущая рассылка, ещё не запущенная на момент resume, собирает новый snapshot по текущей
eligibility. Contact,
отказавшийся после snapshot, не получает сообщение после начала действия stop. Резюмирование
рассылки не добавляет новых получателей; отменённая/завершённая рассылка не запускается повторно
под тем же ID. Для повтора создаётся новая рассылка с новым ID.

До запуска можно редактировать draft; запущенные content/audience неизменны. Pause/resume/cancel
действуют только на не начатые внешние отправки. Нет общего frequency cap с воронками. Можно видеть
snapshot size, progress и причины skipped/failed/unknown; технический rate limiting общий.

## Надёжность и наблюдаемость

Durable update inbox, publish/launch records, enrollments и delivery intents живут в PostgreSQL.
Atomic claim, уникальные keys и crash-safe transitions защищают от двойной обработки конкурирующими
workers. Точный transaction/outbox механизм выбирается внутри приложения с доказательством через
real-DB concurrency/crash tests. Не считать короткую lease гарантией отсутствия повторного эффекта.

Bot API send не предоставляет документированного client idempotency key. Если ответ потерялся
после возможной отправки, сохраняется unknown; автоматический retry не повторяет этот эффект.
Владелец/агент выбирает skip или explicit retry с видимым риском дубля; исходное evidence не
переписывается. При подтверждённом отказе Telegram применяются классифицированные bounded retries,
`retry_after`, terminal error и видимая причина. Известный sent не пересылается после DB ack fault.
Общий выключатель маркетинга не отключает служебные auth/link сообщения. Очереди имеют служебный
приоритет и не дают массовой рассылке блокировать подтверждение входа.

Хранить enrollment, step/part delivery markers, опубликованные revisions, suppression и аудит
операций, пока существует соответствующая история контакта. Автоматическое удаление этой истории
не входит в v1; повтор deployment не обнуляет её. Raw Telegram payloads, credentials и debug traces
не становятся бессрочным аналитическим хранилищем: применять текущие redaction/retention приложения.
Права на контактные данные ограничены `communications:manage`. Удаление персональных данных и
production retention/privacy review следуют отдельному operational процессу, не обходятся этим scope.

## Аналитика

UI/API/MCP показывают общее число BotContacts; reachable/blocked/marketing-off; уникальных участников
каждой воронки; first и latest source entry и историю осознанных повторных входов; доставки,
suppression/failure/unknown; разовые рассылки и зарегистрированные переходы на Platform. Владелец
видит контакт и источник его входа. Дедупликация webhook не увеличивает показатели.

Для ссылки в доставленном сообщении Telegram создаёт opaque tracking token, который Platform
разрешает через authenticated API до настроенного безопасного адреса. Raw Telegram ID, auth/link
secrets и свободный redirect URL не передаются в query. Redirect не выдаёт доступ к контенту;
недоступная analytics запись не должна блокировать уже безопасно разрешённую навигацию. Переходы
передаются в Telegram идемпотентным event API с durable retry; сбой отражается в lag, а не как ноль
кликов. История повторных hits отделена от уникальных tokens с hits. Bot preview/known automation
отмечаются или исключаются по проверяемому правилу; полнота распознавания человека не обещается.

Start подтверждает Telegram identity входящего. Hit по tracking link подтверждает использование
ссылки конкретной доставки, **не личность открывшего**: ссылку можно переслать. Интерфейс не называет
это доказанным чтением данным человеком. Account linkage, purchase conversion и read completion не
выводятся из этих событий. First/last source — наблюдения, не доказанная причина оплаты.

## Проверка и delivery

[Telegram #26](https://github.com/sachkov-inside/inside-telegram/issues/26) владеет provider delivery;
[Platform #304](https://github.com/sachkov-inside/platform/issues/304) — consumer/UI/MCP и общей
сквозной приёмкой. Native tickets/dependencies находятся в tracker; не дублировать динамические
статусы в этом документе. Реализация каждого приложения обновляет собственные product/technical
context pointers, в том числе прежний bridge-only scope. Этот контракт расширяет будущую
communications поставку и не переписывает исторические bridge решения как будто маркетинг уже был.

Обязательные истории:

1. Обычный, тематический, повторный и auth entry; общий intro один раз при конкурентных входах;
   старые payload, unknown source, отсутствие Account и stopped contact.
2. A/B доставлены; добавлено C ongoing/completed участникам; C delay от publish. Edit/reorder/delete,
   повтор publish, rollback, pause/archive, несколько тем и сохранение history.
3. Stop между частями/до dispatch, delayed steps во время stop, resume без backlog с сохранением
   будущего срока; blocked/unblock; служебный login не возобновляет маркетинг.
4. Текст/entities и каждый media type; video_note+text partial delivery и cancel оставшегося текста с отсчётом следующего шага
   от terminal cancellation; повтор inbound, deleted
   original, broken file_id, stale template edit, чужой ID и revoked author permission.
5. Scheduled broadcast snapshot при launch, union audiences, stop после snapshot и resume до delayed retry без восстановления получателя, поздний контакт,
   повтор launch и cancel во время выполнения; pause/resume не расширяет snapshot.
6. Real PostgreSQL: два workers, crash до/после claim, внешнего эффекта, persisted sent и DB ack;
   429, permanent failure, unknown и явный retry/skip без потери evidence.
7. UI и MCP имеют одинаковые полномочия publish/launch, ordinary user denied; concurrent revision
   conflict, неполный/закрытый free target и безопасная preview/test-send граница.
8. Реальный free Material/Public Product route, tracking hit/duplicate/forwarded token, degraded analytics,
   сохраняющаяся content authorization; sent/click/read/purchase не смешиваются.

Для приложения: repository-local full checks, representative/negative seam fixtures и Standards/Spec
review с dispositions. Для UI: Storybook и live desktop/mobile/keyboard evidence. Соблюдать local
runtime ownership; не запускать общий Docker без его правил. Реальные Telegram smoke только для
явно согласованного test recipient. Production marketing enablement, review из Telegram brief,
релиз и каждый merge остаются отдельными действиями владельца/его явно уполномоченной сессии.
Проектирование завершено после согласования и review этого контракта и конкретных tickets; функция
завершена только после сквозной приёмки, а не после готовности отдельного scheduler или редактора.
