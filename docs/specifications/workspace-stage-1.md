# Этап 1 перестройки рабочей среды: образец на разработке Inside

Статус: принята владельцем 2026-10-02 вместе с пунктами с пометкой «(предложение)». Следующая
стадия — разбивка на задачи; её запускает владелец.

Основание: [задача этапа](https://github.com/KirillSachkov/workspace/issues/1), общая спецификация
и журнал решений рабочей среды (`workspace/docs/spec.md`, `docs/decisions.md`,
`docs/stage-1-context.md`), грилинг этапа 2026-10-02.

Как читать. «Решение N» — номер в журнале решений рабочей среды. «Грилинг» — ответ владельца на
грилинге этапа. **(предложение)** — пункт, которого не было на грилинге: он принят вместе со
спецификацией.

## Результат

`platform` становится образцовой рабочей системой по десяти критериям общей спецификации и домом
процесса разработки Inside. Процесс состоит из чистой копии skills Matt Pocock и короткого
контракта. Состояние задачи — issue, labels и связанный PR. Контроллера tracker, учёта сессий,
locks и `harness health` нет. `telegram` получает копию процесса одной командой. Репозиторий
workspace Inside хранит только продуктовые и юридические документы.

Общая линия (решение 42): где у автора upstream есть готовый ответ, берём его и своё поверх не
строим. Своё добавляем только там, где upstream молчит или сам признаёт дыру.

## Решения

### 1. Skills

- В `platform` лежит чистая копия всех skills upstream из разделов `engineering` и `productivity`
  с ветки `main` на commit `d81f3a1` от 2026-09-29: 27 skills (решения 27, 36; грилинг). На
  2026-10-02 новых commits в upstream нет.
- Сверх upstream остаётся frontend-набор: `impeccable`, `vercel-react-best-practices`,
  `modern-web-guidance`, `playwright-cli` (грилинг). `karpathy-guidelines` остаётся до этапа 4,
  когда его правила переедут в профиль устройства **(предложение)**.
- Уходят: `resolving-merge-conflicts` (удалён в upstream) и все правки форка Inside внутри файлов
  upstream. `CONTEXT.md` переименовывается в `GLOSSARY.md`, как требует upstream.
- **(предложение)** Размещение: `.agents/skills/` — обычный каталог, `.claude/skills` — symlink на
  него. Файл `.agents/skills/UPSTREAM.md` называет commit upstream и каталоги не из upstream.
  Проверка «копия чистая» — `diff -rq` с upstream на записанном commit. Обновление: заменить
  каталоги, посмотреть `git diff`.
- Удаляются `.inside-harness/`, `REGISTRY.md`, lock `product-harness.json` и workflow
  `Inside harness health` (решение 6).
- **(предложение)** Своих skills не больше четырёх (решение 36). Стартовый состав — один:
  `session-cleanup` с командами уборки из нынешнего `WORKFLOW.md`. Остальное своё живёт в коротком
  контракте, потому что автор upstream советует держать постоянное поведение вне `SKILL.md`.

### 2. Короткий контракт процесса

`WORKFLOW.md` сжимается с 450 строк до короткого контракта (решение 12); предел — 150 строк
**(предложение)**. `AGENTS.md` остаётся в пределах 150 строк и теряет managed block. Раздел
«Human communication» из него сохраняется как собственный раздел `AGENTS.md` платформы до этапа 4,
когда правила общения переедут в профиль устройства (приёмка владельца).

Контракт называет, кто запускает стадии (приёмка владельца): грилинг, спецификацию и разбивку на
задачи запускает владелец, каждую отдельной командой. Задача реализации с `ready-for-agent` идёт
от `implement` до готового PR без остановок.

В остальном контракт закрывает только то, о чём upstream молчит или что он сам называет дырой:

| Дыра upstream | Правило контракта |
|---|---|
| `implement` не создаёт ветку и не открывает PR | Ветка `<type>/<issue>-<slug>` от `origin/main` в worktree; после первого commit — draft PR с `Closes #N` |
| Ревью до commit видит пустой diff | Сначала commit, затем ревью от записанной начальной точки |
| Ревью идёт в сессии автора кода | Ревью запускает пишущий агент в отдельном агенте с чистым контекстом: diff, задача, стандарты (грилинг) |
| Замечания ревью никто не обрабатывает, критерия остановки нет | Каждое замечание получает исход: исправлено, вынесено в issue, отклонено с доказательством. После правок — один повторный проход; оставшееся закрывается исходами |
| `implement` не закрывает задачу | Агент отмечает критерии приёмки и доводит PR до зелёного CI на текущем head |
| Связь PR с issue не проверяется | Перед отчётом о готовности агент читает `closingIssuesReferences` PR и сверяет номер задачи |
| Уборки нет | Уборка входит в «готово»: worktree, локальная ветка, контейнеры, временные файлы |

Форму PR задаёт skill `pr` из upstream; собственный шаблон отчёта из 12 разделов уходит
**(предложение)**.

### 3. Потоки и задачи

- Потоков два (решение 25): мелкая правка `issue → implement → review → PR` и фича
  `grilling → spec → tickets → implement → review → PR`.
- Пометки — как в upstream (решение 42). Задача реализации получает `ready-for-agent` и идёт до
  готового PR без остановок. `ready-for-human` — только для того, что делает человек.
- Всё, что требует решения владельца, решается до задач: на грилинге, а вид интерфейса — в
  прототипе (skill `prototype`). Визуальная правка — фича с прототипом.
- Право на merge — строка в теле задачи. Если строки нет, мержит владелец (решение 26; грилинг).
- Размер задачи — один вертикальный срез на одно свежее окно контекста (решение 39).
- Gates владельца: релиз и deploy, публикация, платные действия, credentials, внешние сообщения.
- Labels `tracker:acceptance`, `tracker:gate`, `tracker:paused`, `tracker:auto-complete` удаляются
  вместе с контроллером. Задача, которая ждёт приёмки владельца, остаётся открытой с комментарием,
  что именно он принимает **(предложение)**.

### 4. Занятость задачи

Учёта сессий нет. Задача занята, если на remote есть её ветка или связанный открытый PR. Новая
сессия проверяет это перед первой записью (грилинг). Между стартом и первым push защиты нет:
владелец принял этот риск.

### 5. Доска

- Остаётся одна доска — Developer Pipeline. Human Backlog удаляется (грилинг). Доска курса не
  затрагивается.
- Колонки — только те, что двигают встроенные правила GitHub Projects (грилинг): `Inbox`,
  `In progress`, `Done` **(названия — предложение)**. Колонки `Ready`, `Review`, `Blocked`,
  `Acceptance` убираются: готовность и блокировку показывают labels и native blockers.
- Включаются встроенные правила: `Item added to project` → `Inbox`, `Pull request linked to issue`
  → `In progress`, `Item closed` и `Pull request merged` → `Done`. Сейчас все шесть встроенных
  правил на доске выключены.
- На доске только issues; PR виден через связанную задачу **(предложение)**.
- **Не измерено: автодобавление задач.** Организация на тарифе Free. Критерий: если встроенное
  автодобавление покрывает и `platform`, и `inside-telegram`, используем его. Если покрывает один
  репозиторий, второй добавляет карточку командой `gh project item-add` на шаге создания задачи.

### 6. Что теряется вместе с автоматикой tracker

Список показан владельцу до удаления (решение 29) и принят на грилинге.

| Теряется | Замена |
|---|---|
| Защита от двух писателей (`start` receipt) | Ветка и draft PR, раздел 4 |
| Колонки `Ready`, `Blocked`, `Acceptance` | Labels и native blockers |
| Различие `In progress` и `Review` по draft | Нет; один статус при связи PR с issue |
| Отказ `handoff` без связи PR с issue | Проверка связи в контракте, раздел 2 |
| Раскладка по двум доскам | Одна доска |
| Починка пропущенных событий дважды в час | Нет |
| Доска для `inside-content` и `inside-landing` | Нет |
| Журнал сессий в комментариях задачи | Комментарий агента при остановке и PR |
| Защита `tracker:paused`, автозакрытие родителя | Нет; открытых задач с этими labels нет |
| Отчёт о каждом решении контроллера | Не нужен |

Уже написанные комментарии сессий остаются в задачах как история.

### 7. Замечания владельца к коду

Без журнала, через `retro` из upstream (грилинг). Механическая ошибка становится автоматической
проверкой: тест, линтер, тип, guardrail. Суждение становится правилом в `CODING_STANDARDS.md`,
который читает ревьюер. Жёсткого предела размера нет. Когда файл длиннее 200 строк, `docs:check`
печатает предупреждение, и заводится задача на перевод правил в проверки
**(место предупреждения — предложение)**.

### 8. Проверка

«Готово» означает зелёную команду `pnpm check` на финальном head с настоящим exit code
**(выбор команды — предложение)**. `pnpm check:full` и Compose smoke остаются проверкой перед
выпуском.

Правила из отчётов (решение 39; грилинг):

1. Скрипты не маскируют exit code и работают под bash 3.2 macOS: без `wait -n`, без пустых
   массивов под `set -u`.
2. Перед deploy агент называет ожидаемый простой.
3. После deploy выполняется проверка из runbook выпуска, и её результат входит в отчёт.
4. Связь PR с issue проверяется перед отчётом о готовности.
5. До commit идут проверки затронутого; полный прогон — один раз на финальном head.
6. Стенд, поднятый агентом по просьбе владельца, перезапускается без вопроса.
7. `lint` и `typecheck` зелёные перед любым отчётом о готовности.

### 9. Мерила критериев 7, 8 и 10

- **Критерий 7.** Поправка владельца в задаче этапа привела к новой проверке или новому правилу в
  `CODING_STANDARDS.md` через `retro`; порог предупреждения — 200 строк.
- **Критерий 8.** Оба агента в новой сессии называют один и тот же список skills, и задача
  реализации с `ready-for-agent` проходит в каждом до готового PR.
- **Критерий 10.** PR идёт по форме skill `pr`; итог в чате не длиннее десяти строк со ссылками.

Проверяется на четырёх настоящих задачах этапа.

## Порядок работ

Удаление идёт сразу, не дожидаясь живых задач (грилинг). Три живых worktrees и восемь открытых PR
`platform` не затрагиваются; их задачи доделываются уже без `start` receipt.

1. Копия upstream, размещение skills, удаление locks и `health` в `platform`.
2. Короткий `WORKFLOW.md`, `AGENTS.md`, правила из отчётов, `GLOSSARY.md`.
3. Автоматика tracker. Сначала запись контроллера выключается переменной `INSIDE_TRACKER_APPLY` во
   всех репозиториях, иначе плановая сверка в workspace перепишет статусы. Затем сокращаются
   колонки и включаются встроенные правила. Затем один PR в каждом репозитории удаляет контроллер,
   учёт сессий и `docs/agents/tracker-automation.md`.
4. Перенос и закрытие задач workspace, удаление доски Human Backlog, сжатие workspace.
5. Копия в `telegram`, чистка `workshop-cases`.
6. Четыре настоящие задачи, повторный отчёт `/insights`, приёмка владельцем.

Секреты `INSIDE_PROJECT_TOKEN` и `HARNESS_ROLLOUT_TOKEN` отзывает владелец.

## Критерии готовности

- `platform` проходит десять критериев общей спецификации; критерии 7, 8 и 10 — по разделу 9.
- Пройдено четыре настоящие задачи: мелкая правка, фича с прототипом и задача реализации в одном
  агенте, задача реализации в другом.
- Workflows контроллера tracker и учёта сессий удалены в `platform`, `telegram`, `workshop-cases`
  и workspace. Статус задачи на доске меняется от PR встроенными правилами.
- В репозитории workspace нет harness-пакета и открытых задач. В `platform`, `telegram` и
  `workshop-cases` нет locks и `health`.
- Файлы процесса в `telegram` побайтно равны файлам в `platform`.
- `diff -rq` копии skills с upstream на записанном commit не показывает расхождений.
- Владелец принял этап.

## Вне объёма

- CI/CD и совместные релизы `platform` и `telegram`.
- Правка содержимого skills upstream.
- Профиль устройства и три правила общения: этап 4.
- `inside-content`, `inside-landing`, `ai-engineering`: этапы 2 и 4.
- Перенос продуктовых документов workspace в другой репозиторий.

## Риски

- **Проверки документации завязаны на удаляемые файлы.** `pnpm docs:check` и тесты контрактов в
  `scripts/` могут ссылаться на `tracker-automation.md`, managed block и шаблон PR. Правятся в том
  же PR, что и удаление.
- **Ревью в чистом контексте в Codex.** Не измерено, запускает ли Codex отдельного агента так же,
  как Claude Code. Критерий: если нет, ревью идёт отдельным запуском `codex exec` с тем же входом.
- **Доска расходится с фактами.** Починки пропущенных событий больше нет. Источник истины — issue
  и PR, доска только показывает.
- **Копия в `telegram` разойдётся.** Сдерживается одной командой копирования и побайтной сверкой.
- **Незакрытая локальная работа.** Ветка `prototype/380-guest-home-variants` с 22 commits не имеет
  копии на remote. Этап её не трогает.
