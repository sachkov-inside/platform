# Страница продукта из данных Guide

Владелец 17.09.2026 решил, что страница продукта строится из данных, а не из кода
([Platform #671](https://github.com/sachkov-inside/platform/issues/671)). До этого текст страницы
«AI-first разработка» жил в web, а особое оформление выбиралось сравнением адреса
`slug === "working-with-agents"`. Правка текста требовала выпуска сайта, Obsidian и сайт расходились,
а смена адреса молча возвращала общий шаблон.

## Решение

Описание продукта — часть оригинала в Inside Content (`guide.yaml`, ключ `page`) и переносится в
Platform той же source-scoped синхронизацией, что и уроки. `Guide` хранит два новых поля:

- `presentation` — имя оформления из реестра в коде: `default` или `ai-first-process`. Значение
  выбирает, какой набор компонентов рисует страницу и карточку Главной. Сравнений адреса в web нет.
- `page` — версионируемое описание страницы (`jsonb`, `null` — описания нет): необязательная
  подпись карточки Главной (`card`) и упорядоченный список типизированных блоков (`blocks`).
  Границы: до 16 блоков, до 12 пунктов в блоке, короткое поле 200 и длинное 4000 символов, всё
  описание до 32 КиБ, вводный блок `hero` не повторяется.

Блок имеет устойчивый `id` и один из видов: `hero` (лид и короткие пункты), `cards` (надзаголовок,
заголовок, лид, карточки с необязательной подписью `detail_label`/`detail`, в Platform — `detailLabel`/`detail`, заметка), `text`
(абзацы), `steps` (нумерованные этапы и подпись ссылки на программу), `list` (короткие пункты) и
`trial` (приглашение к бесплатным урокам). Каждое написанное поле показывают оба оформления; подпись без значения схема не принимает. Блок
`trial` — приглашение к бесплатным урокам, поэтому он появляется только у продукта, где такие уроки
есть. Пустая
строка означает ненаписанное поле. Оформление рисует каждый вид; `id` позволяет ему узнать знакомый блок и добавить ему свою
иллюстрацию, а внутри блока иллюстрации и значки идут по порядку пунктов. Иллюстрации, значки и кнопки навигации остаются в коде оформления.

Сроки доступа и сопровождения не пишутся в тексте: автор ставит `{access_term}` и `{support_term}`,
а web подставляет подписи из действующей оферты (`@inside/legal/purchase-terms`). Цена, тарифы и
доступ остаются решениями Platform и в описание не входят.

`presentation`, `page` и `slug` меняются только маршрутом `POST /authoring/import/guides/update` с
тем же `sourceId`; редактор и MCP их не пишут, как и остальные перенесённые поля. Версия `Guide`
покрывает их вместе с названием и описанием.

### Идентичность

Постоянный ключ продукта — `sourceId` (`inside-content:<id>`) и UUID `Guide`, который журнал
переноса хранит для этого ключа. `slug` — изменяемый адрес: в `guide.yaml` он задаётся
необязательным `slug`, а без него равен `id`. Закрепление на Главной, главы, состав, артефакты и
прогресс читателей ссылаются на UUID, поэтому смена адреса их не теряет. Старый адрес после смены не
открывается.

### Неизвестное оформление и непроходимое описание

Перенос проверяет оформление и всё описание до первой записи одним обращением:
`POST /authoring/import/guides/validate` прогоняет ту же схему Platform, которая потом пишет
данные, поэтому реестр и правила живут в одном месте, а не копируются в перенос. Отказ называет
продукт и место ошибки. Экспортёр Inside Content держит свои проверки формы и список оформлений,
чтобы назвать ошибку сразу при сборке пакета; решает всё равно Platform.

Пакет, который не называет описание, оформление или адрес, оставляет их прежними: старый пакет не
стирает страницу и не переводит продукт на другой адрес. Снять описание можно явным `page: null`.
Адрес проверяется только когда пакет его называет; новый продукт с непригодным ключом останавливает
перенос на создании записи, то есть до первого материала.
Если база всё же содержит значение, которого не знает текущий web (например, после отката выпуска),
сайт показывает общий шаблон и пишет предупреждение в журнал сервера. Описание, которое не проходит схему, читателю не
показывают: предупреждение об этом пишет сервер при чтении сохранённого описания. Продукт вовсе без
описания — обычный случай и предупреждением не является.

### Сохранённое описание, которое больше не проходит схему

Такое описание читателю не показывают, сервер пишет о нём запись для оператора, а редакторский
список отмечает продукт полем `pageRejected`. Перенос считает это несовпадением и заменяет описание,
поэтому мусор не остаётся в базе навсегда.

### Две схемы одного описания

Схема Platform — единственная, которая решает, что принять и записать. Web держит свою, более
мягкую: он читает сохранённое описание как внешнее значение и обязан показать общий шаблон, когда
данные новее выпуска сайта. Поэтому web не повторяет лимиты и не считается вторым владельцем
правил; проверка на пригодность к записи всегда происходит на стороне Platform.

### Общий шаблон

`default` без `page` показывает прежнюю страницу с введением `audience`/`outcome`/`prerequisites`/
`scope`, которое по-прежнему пишет редактор Platform. С `page` общий шаблон рисует блоки простыми
разделами вместо введения.

## Последствия

- Правка текста страницы — это коммит в Inside Content и перенос; пересборка web не нужна.
- Новое оформление — это значение реестра в backend и web и его компоненты; схема блоков общая.
- Список продуктов (`pnpm authoring:products`) показывает `sourceId`, адрес, оформление,
  закрепление и число уроков по выбранной цели.
- Перенос на production остаётся отдельным решением владельца (#468).

## Проверки

- Схема блоков и реестр оформлений — `apps/backend/src/modules/materials/domain/guide-page.ts` и
  его тест с отрицательными примерами.
- Импорт и смена адреса — интеграционный тест `import-source-guide`.
- Реестр web — тест выбора оформления, в том числе неизвестного значения, и stories обоих оформлений.
- Перенос — `pnpm test:authoring`.
