# Термины: контракт и тестовый пакет #443

Цель #443 состоит в том, чтобы Platform принимала одну запись определения и сохраняла в Material ссылку на её постоянный ID.
Название термина и видимая фраза могут различаться. Авторские оригиналы остаются в Inside Content.
Источник задачи: [Platform #443](https://github.com/sachkov-inside/platform/issues/443),
общий план: [workspace #156](https://github.com/sachkov-inside/workspace/issues/156).

## Состояние поставки

Этот checkpoint содержит схему определения, правила разрешения ссылок и переносимые тестовые заметки.
Текущий importer ещё не принимает определения и не создаёт карточки Reader.
Не передавайте этот пример в production и не публикуйте его как авторский словарь.

| Граница | Этот checkpoint | Остаток #443 |
|---|---|---|
| Определение | Одна строгая схема, постоянный UUID, название, варианты написания и авторский текст | Хранение, версии и API |
| Wiki-ссылка | Разбор цели и видимой фразы, ошибки дубля, неоднозначности, отсутствия и недоступности | Подключение к Markdown parser и package v2 |
| Structured body | Форма ссылки определена ниже | Общая mark-схема, acceptance/render и editor open/save |
| Публичное чтение | В исходную ссылку попадает только ID; публичная проверка отклоняет непубликуемый термин | Реальные `ContentAccess`, публикация, кеш и Reader |
| Авторский пример | Пять определений, два Material и отдельный подробный Material | Изолированный сквозной импорт и проверка интерфейса |

Исполняемые источники этого этапа:
[`termDefinitionSchema`](../../../packages/material-blocks/src/term-definition.ts) и
[`term-references.mjs`](../../../tools/authoring/term-references.mjs).
Проверки используют [`term-definition.test.mjs`](../../../tools/authoring/term-definition.test.mjs)
и [`term-references.test.mjs`](../../../tools/authoring/term-references.test.mjs).

## Одна запись определения

| Поле | Смысл |
|---|---|
| `id` | Постоянный UUID термина; переименование заметки его не меняет |
| `title` | Название; непустой текст, до 200 символов |
| `aliases` | Варианты написания; до 50 непустых строк, каждая до 200 символов |
| `definition` | Авторское краткое определение; непустой обычный текст, до 2000 символов |
| `example` | Необязательный обычный текст примера; до 1000 символов |
| `materialId` | Необязательный UUID подробного Material |

У определения нет тела Material, локального пути vault или авторского флага доступа.
Публикация и версия принадлежат записи Platform и проверяются отдельно.
Текст определения не извлекается из первого абзаца подробного Material.
Если подробного Material нет, определение остаётся самостоятельным.

Значение `available` в подготовке ссылок сообщает вызывающий код после разрешённого чтения цели.
Его нельзя брать из авторского пакета. По умолчанию разрешаются только опубликованные определения.
`allowUnpublished` предназначен для авторского просмотра; он не разрешает недоступную цель.
Эти чистые правила не заменяют проверку доступа в приложении.

## Разметка в Obsidian

В [примере](example/Материал%20A.md) автор открывает заметку термина через wiki-ссылку:

```markdown
[[Деплой]]
[[Деплой|развёртывание]]
```

Цель связывается с `title` или одним из `aliases`. Поиск не зависит от регистра и формы Unicode.
Видимая фраза хранится отдельно. Совпадение варианта с названием той же записи не создаёт неоднозначности.
Если название подходит двум записям, перенос должен остановиться.

Подготовленная функция также разрешает явную цель `term:UUID`:

```markdown
[[term:44300000-0000-4000-8000-000000000001|развёртывание]]
```

Это явная форма Platform для устранения неоднозначности; переход по ней внутри Obsidian не проверен.
Для обычной работы с заметками используйте название или вариант написания.
Ссылки на подробные материалы сохраняют обычную Markdown-форму:

```markdown
[Первый деплой на сервер](Первый%20деплой%20на%20сервер.md)
```

Текущий путь [#289](https://github.com/sachkov-inside/platform/issues/289) использует
`tools/authoring/markdown.mjs` и таблицу `materials[].links` из package v1/v2.
В Content `markdown_dependencies` читает обычные link/image tokens, а не wiki-ссылки.
Подключение wiki-ссылок требует capability `terms-v1` в существующем package v2.
Пока такой capability не объявлен получателем, пакет должен отклоняться до записи.

Подготовленный разбор отклоняет пустую цель, пустую фразу, несколько разделителей `|`,
перенос строки, вложенные скобки и ссылки на заголовок или блок.
Встраивание заметок и произвольные плагины Obsidian не входят в #443.
Markdown parser должен сохранить wiki-текст в коде и обработать экранирование;
это проверяется после подключения функции к настоящему преобразованию Markdown.

## Связь с MaterialBody

Следующий этап добавляет mark `term` с единственным атрибутом `termId`:

```json
{
  "type": "text",
  "text": "развёртывание",
  "marks": [
    {
      "type": "term",
      "attrs": { "termId": "44300000-0000-4000-8000-000000000001" }
    }
  ]
}
```

В документ не копируются название, определение и пример. Два Material используют одну запись термина.
Обычная mark `link` остаётся обычной ссылкой. `readerBlocks` сохраняют преимущество перед сырым Markdown.
Связи должны сохраняться также внутри структурированных частей квиза.

## Повтор, конфликты и доступ

Полный перенос должен проверить все цели до первой записи, включая подробные Material.
Он использует существующие preview/apply, журнал операций и защиту неизвестной версии.
Повтор по тому же ID обновляет определение, а не создаёт копию.
Ручная правка с неизвестной версией вызывает конфликт и сохраняется.
Проверка реального PostgreSQL должна доказать повтор, rollback и конкурентную запись.

Reader загружает текущее опубликованное определение, поэтому изменение видно во всех Material со ссылкой.
Проверка кеша должна охватить два Material и снятие определения с публикации.
Карточка не читает protected body. Подробная ссылка открывает Material через действующий `ContentAccess`.
Закрытый или неопубликованный подробный Material не становится доступным через карточку.

## Пример и происхождение текста

Каталог [example](example/) можно открыть отдельно в Obsidian. Все заметки помечены `fixture: true`
и `publication_state: draft`. Их UUID предназначены только для изолированных тестовых данных.
[Заметки терминов](example/Термины/) являются тестовыми оригиналами;
[`definitions.json`](example/definitions.json) содержит их экспортированный снимок для проверок схемы.
В runtime не используются пути этих заметок.

| Термин | Происхождение определения |
|---|---|
| Деплой | Дословная формулировка из #443 |
| CI, релиз | Выдержки из [«Как устроены CI и CD»](https://github.com/sachkov-inside/inside-content/blob/291f6b86a165f81da8a1465186e4630d579cee9e/guides/01.%20AI-first%20разработка/07.%20Проверки%20в%20CI/31.%20Как%20устроены%20CI%20и%20CD.md), без Markdown-выделения |
| Образ, окружение | Ячейки таблицы из [«Docker: образы, Compose и окружения»](https://github.com/sachkov-inside/inside-content/blob/291f6b86a165f81da8a1465186e4630d579cee9e/guides/01.%20AI-first%20разработка/08.%20Первый%20воспроизводимый%20релиз/36.%20Docker:%20образы,%20Compose%20и%20окружения.md) |

Выдержки проверены по Git commit `291f6b86a165f81da8a1465186e4630d579cee9e`.
Текущие оригиналы и авторское одобрение остаются в Content.
Синтетические Material A/B проверяют связи; они не являются принятым уроком или новым каноническим словарём.

Лёгкая проверка из корня Platform:

```bash
node --test tools/authoring/term-references.test.mjs tools/authoring/term-definition.test.mjs
```

Второй файл использует собственные установленные зависимости и собранный `@inside/material-blocks`.
Первый файл использует только стандартную библиотеку Node.js.
Эта команда подтверждает схему и чистые правила; она не подтверждает импорт, редактор или Reader.

## Инструкция автору после сквозной проверки контракта

Перед новой записью найдите существующий термин и подробные материалы.
Сохраните постоянный ID, когда меняете название, варианты, определение или пример.
Отметьте первое содержательное употребление; повторяйте отметку только в самостоятельном длинном разделе.
Объяснение, необходимое для текущего шага, оставьте в самом Material.
Проверьте ошибки и версии в preview перед apply.
Публикацию выбирайте отдельно; заметка или её редакционная стадия не публикуют определение автоматически.

Применение этого формата к каноническому Content требует отдельного handoff после сквозного доказательства #443.
Массовая разметка архива и генерация определений при чтении не входят в контракт.
