# Термины: контракт и тестовый пакет #443

Цель #443 состоит в том, чтобы Platform принимала одну запись определения и сохраняла в Material ссылку на её постоянный ID.
Название термина и видимая фраза могут различаться. Авторские оригиналы остаются в Inside Content.
Источник задачи: [Platform #443](https://github.com/sachkov-inside/platform/issues/443),
общий план: [workspace #156](https://github.com/sachkov-inside/workspace/issues/156).

Targeted backend typecheck дал exit 0 после codegen; прежние 14 diagnostics исчезли без обходов source/config.

Проверки настоящего PostgreSQL, доступа и кеша остаются обязательными. Интерфейс Reader ещё не реализован.

## Одна запись определения

| Поле | Смысл |
|---|---|
| `id` | Постоянный UUID термина; переименование заметки его не меняет |
| `title` | Название; непустой текст, до 200 символов |
| `aliases` | Варианты написания; до 50 непустых строк, каждая до 200 символов |
| `definition` | Авторское краткое определение; непустой обычный текст, до 2000 символов |
| `example` | Необязательный обычный текст примера; до 1000 символов |
| `materialId` | Необязательный UUID подробного Material |

У определения нет тела Material, локального пути vault или авторского флага доступа.
Публикация и версия принадлежат записи Platform и проверяются отдельно.
Текст определения не извлекается из первого абзаца подробного Material.
Если подробного Material нет, определение остаётся самостоятельным.

Значение `available` в чистой подготовке ссылок сообщает вызывающий код. Авторский пакет не задаёт это поле.
Loader считает доступными определения внутри самого пакета; право записи проверяет authoring API целевого runtime.
По умолчанию чистый resolver разрешает только опубликованные определения.
`allowUnpublished` предназначен для авторского просмотра; он не разрешает недоступную цель.
Эти чистые правила не заменяют проверку доступа в приложении.

## Разметка в Obsidian

В [примере](example/Материал%20A.md) автор открывает заметку термина через wiki-ссылку:

```markdown
[[Деплой]]
[[Деплой|развёртывание]]
```

Цель связывается с `title` или одним из `aliases`. Поиск не зависит от регистра и формы Unicode.
Видимая фраза хранится отдельно. Совпадение варианта с названием той же записи не создаёт неоднозначности.
Если название подходит двум записям, перенос должен остановиться.

Подготовленная функция также разрешает явную цель `term:UUID`:

```markdown
[[term:44300000-0000-4000-8000-000000000001|развёртывание]]
```

Это явная форма Platform для устранения неоднозначности; переход по ней внутри Obsidian не проверен.
Для обычной работы с заметками используйте название или вариант написания.
Ссылки на подробные материалы сохраняют обычную Markdown-форму:

```markdown
[Первый деплой на сервер](Первый%20деплой%20на%20сервер.md)
```

Текущий путь [#289](https://github.com/sachkov-inside/platform/issues/289) использует
`tools/authoring/markdown.mjs` и таблицу `materials[].links` из package v1/v2.
В Content `markdown_dependencies` читает обычные link/image tokens, а не wiki-ссылки.
Platform принимает wiki-ссылки через capability `terms-v1` в существующем package v2.
Пакет объявляет `requiredFeatures: ["terms-v1"]` и массив `terms`:

```json
{
  "sourceId": "deploy",
  "sourcePath": "terms/deploy.md",
  "publicationState": "draft",
  "definition": {
    "id": "44300000-0000-4000-8000-000000000001",
    "title": "Деплой",
    "aliases": ["deploy"],
    "definition": "Развёртывание выбранной версии приложения в конкретном окружении — например, на тестовом сервере"
  }
}
```

Это запись внутри `terms`, а не полный envelope пакета.
Текущий Content exporter этот массив не создаёт; его канонические оригиналы и инструменты здесь не изменены.
`materialId`, если указан, должен называть существующий Material целевого runtime.
Source preflight отклоняет отсутствующий подробный Material до импорта определения.

Подготовленный разбор отклоняет пустую цель, пустую фразу, несколько разделителей `|`,
перенос строки, вложенные скобки и ссылки на заголовок или блок.
Встраивание заметок и произвольные плагины Obsidian не входят в #443.
Markdown parser сохраняет wiki-текст в code fences, inline code и экранированном тексте.
Это проверено через настоящий `convertMarkdown`. Term reference внутри обычной ссылки отклоняется.

## Связь с MaterialBody

Общая схема добавляет mark `term` с единственным атрибутом `termId`:

```json
{
  "type": "text",
  "text": "развёртывание",
  "marks": [
    {
      "type": "term",
      "attrs": { "termId": "44300000-0000-4000-8000-000000000001" }
    }
  ]
}
```

В документ не копируются название, определение и пример. Два Material используют одну запись термина.
Обычная mark `link` остаётся обычной ссылкой. `readerBlocks` сохраняют преимущество перед сырым Markdown.
Общий renderer сохраняет term ID также внутри структурированных частей квиза.
Server Save/Validate проверяет существование определения; опубликованный Material требует опубликованного определения.

## Повтор, конфликты и доступ

CLI проверяет ссылки и версии перед новыми term writes через существующие preview/apply и журнал операций.
Первый import передаёт `expectedTermVersion: null`; обновление передаёт известную версию.
Journal replay сохраняет исходные request и idempotency key. Повтор не создаёт новую версию определения.
Ручное сохранение меняет `termVersion` и сбрасывает source revision; CLI обнаруживает чужую версию до перезаписи.
Source API также проверяет версию в транзакции и блокирует изменение владельца source ID.
Эти операции пока проверены на уровне чистых правил и CLI transport contracts.
Проверка реального PostgreSQL должна доказать повтор, rollback и конкурентную запись.

`GET /terms/:termId` читает текущее опубликованное определение и объявляет `private, no-store`.
Материал хранит только ID, поэтому его сохранённое тело не требует копирования определения при обновлении.
Reader UI ещё должен подключить этот endpoint и обновлять свой клиентский кеш.
Проверка кеша должна охватить два Material и снятие определения с публикации.
Карточка не читает protected body. Подробная ссылка открывает Material через действующий `ContentAccess`.
Закрытый или неопубликованный подробный Material не становится доступным через карточку.

Authoring API использует trusted Account и `materials:manage`:

| Метод и путь | Результат |
|---|---|
| `POST /authoring/import/terms/validate` | Проверка source ownership и текущая версия без записи |
| `POST /authoring/import/terms/apply` | Import с `expectedTermVersion` и idempotency key |
| `POST /authoring/terms/save` | Ручная правка с той же защитой версии |
| `GET /authoring/terms` | Определения, включая drafts; страницы по 100 записей, `cursor` |
| `GET /authoring/terms/:termId` | Определение и текущая версия для автора |

Наличие API source не подтверждает запуск этих endpoints или обязательные PG/HTTP security checks.

## Storybook proof и контракт отображения

Source stories `Proofs/Material Terms` подготовлены в собственном worktree #443.
Они используют авторские fixtures этого пакета и development-only presentation interface.
Состояния охватывают hover/focus, mobile tap, два Material с одной записью, узкий экран,
200% text zoom, loading, недоступное определение и dependency failure.
Actual Storybook rendering/build, catalog/docs MCP и визуальная приёмка ещё не выполнены.
Этот proof не подключён к production API, кешу или редактору.

Reader и authoring preview явно сохраняют фразу и `data-term-id` в DOM.
Два focused SSR contract tests подтверждают сохранение UUID, фразы и обычной ссылки без копии определения.
Это закрывает прежние TS7030 в ветках mark-renderer; полноценная интерактивная карточка остаётся следующим этапом #443.
Общая схема редактора принимает mark, но реальный editor open/save ещё требует проверки и UI интеграции.

Лёгкая проверка из корня Platform:

```bash
node --test tools/authoring/term-references.test.mjs tools/authoring/term-definition.test.mjs
```

Второй файл использует собственные установленные зависимости и собранный `@inside/material-blocks`.

Эта команда подтверждает схему и чистые правила. Дополнительные native tests проверяют Markdown, loader и CLI transport.
Они не заменяют реальные PG checks, редактор, Reader или полную проверку `pnpm check`.

## Инструкция автору после сквозной проверки контракта

Перед новой записью найдите существующий термин и подробные материалы.
Сохраните постоянный ID, когда меняете название, варианты, определение или пример.
Отметьте первое содержательное употребление; повторяйте отметку только в самостоятельном длинном разделе.
Объяснение, необходимое для текущего шага, оставьте в самом Material.
Проверьте ошибки и версии в preview перед apply.
Публикацию выбирайте отдельно; заметка или её редакционная стадия не публикуют определение автоматически.

Применение этого формата к каноническому Content требует отдельного handoff после сквозного доказательства #443.
Массовая разметка архива и генерация определений при чтении не входят в контракт.
